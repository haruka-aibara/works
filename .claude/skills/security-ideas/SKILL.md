# セキュリティのアイデアを出す

## 狙い

読んだ人が**「ああ、その視点はなかった」**と思うアイデアを出す。
よくある対策の一覧や、ドキュメントを読めば分かる「この機能を使おう」は価値がない。
ユーザーは AWS セキュリティの DevOps エンジニアなので、教科書的な話はすでに知っている前提で考える。

### 組み合わせを狙う

例：`time_rotating` とドリフト通知を組み合わせると、ローテーションのリマインダーになる。
`time_rotating` の期限が来ると差分が出て、ドリフトの通知がそのまま「apply してローテーションして」の合図になる。
どちらの機能も、それぞれのドキュメントには載っている。けれど、**組み合わせるとこう使える、とはどこにも書いていない**。だから価値がある。

単機能の説明は公式ドキュメントを読めば済む。複数を組み合わせた使い方になると、どこかに書かれている確率が一気に下がる。
新しい機能や知られていない仕様を探すより、**よく知られたものを並べて、別々の用途のつもりで作られたものが噛み合う点**を探すほうが、「その視点はなかった」に届きやすい。
組み合わせる数は 2 つに限らない。3 つ以上が噛み合うなら、なおよい。
5 本のうち 3 本はこの形を狙う。残りの 2 本で、手口や仕組みの裏側など別の種類を混ぜる。
組み合わせの 3 本も、扱う分野（IAM・ネットワーク・ログ・IaC など）は 1 本ずつ散らす。

## 1 回の出し方

- **5 本を、それぞれ別の種類から**出す。種類の例：攻撃の手口、ポリシー評価など仕組みの裏側、コスト、法令・データの所在、設計・DR、インシデント対応の準備、監視の監視、後片付け、上限・クォータ、人・組織の動き、端末、サプライチェーン、生成 AI、時間がたつと危なくなるもの
- 表にする。列は「種類」と「アイデア」の 2 つ
- 確かめていないことは、表のあとに「確かめていないこと」として箇条書きでまとめる。本文に「（はず）」を挟まない

「じっくり」「1 本でいいから深く」と言われたら、5 本ではなく [`references/deep-dive.md`](references/deep-dive.md) の手順で 1 本だけ出す。

### 前の反応に引っぱられない

「これいい」「こういう方向がほしい」は、**その 1 本への評価であって、次の 5 本の型を決めるものではない。**
好評だった型に次の 5 本を寄せると、ユーザーは「1 回いいって言うとそれ系ばかり出す」と感じる。実際にそう言われている。
次の回も、種類から散らし直す。

## 1 本の具体度

目安は「攻撃者が盗んだ鍵で S3 のオブジェクトを **SSE-C で自分の鍵に暗号化し直して上書きし**、身代金を取る。使っていないなら SSE-C を拒否しておく」くらい。
1 本ごとに、**どのサービスの・どの設定で・何が起きて・どう直すか**まで書けるものだけを出す。

具体度の手本は、種類のちがう次の 4 本だけ読めば足りる。`ideas/` 全部を読む必要はない（増え続けるうえ、出来にばらつきがある）。

- `ideas/2026-10-02-Terraformの差分が出たら鳴らす.md`（組み合わせ。後半の `time_rotating` の節）
- `ideas/2026-10-03-アラート用SNSトピックに購読を足されると検知が筒抜けになる.md`（手口と固め方）
- `til/2026-10-02-塞いだEC2でもDNS経由で外に出られる.md`（仕組みの裏側）
- `ideas/2026-10-02-stateに秘密を残さないのをレビューに頼らず強制する.md`（守らせ続ける仕組み）

書けないものは出さない。たとえば次は抽象的すぎて刺さらなかった。

- 「お金の視点で守る順番を決める」
- 「防御側の製品が標的になる」
- 「外からの偵察でどこまで分かるか」

### 常識すぎないか

出す前に「わざわざ ideas に書くレベルか」で振り落とす。
次は、ユーザーから「常識すぎる」と言われたもの。

- EKS のノードの IMDS ホップ制限を 1 にする
- Lambda の秘密は環境変数ではなく Secrets Manager に置く
- `value_wo` を使えば state に秘密が残らない（機能の紹介で止まっている）

機能の話で止まるなら、**それを全員に守らせ続ける仕組み**（ポリシー・CI・検知）まで落とす。
たとえば「write-only 引数を使う」ではなく「plan の JSON にポリシーを当てて禁止し、provider が対応したら必須に上げる」。
ただし、これも 1 本の深め方であって、5 本全部をこの型にしない。

### 検知の話は、まずマネージド

検知を自作する案は、GuardDuty・CloudTrail Insights・Security Hub CSPM・IAM Access Analyzer などで既に拾えないかを先に調べる。
調べられるなら Web 検索で finding の種類まで確かめる。

考え方は 2 層。

- **広く拾う層**はマネージドに任せる。中身は分からないが、自分では書けない範囲を見てくれる
- **「これだけは必ず知りたい」層**は自作する。マネージドが拾っていそうでも、拾うと保証できないなら自作で二重にする（例：GuardDuty の detector 削除は、GuardDuty 自身は通知できない）

## 出さないもの

- このリポジトリのコードや設定を見て「ここを直そう」という話。ユーザーが求めているのは一般的な AWS セキュリティのアイデア
- 「この操作を Deny する」系の個別ネタを何本も並べること。まとめるなら 1 本にする
- `ideas/` と `til/` にすでにあるネタ、この会話でもう出したネタを同じ切り口で出し直すこと。出す前に両方のファイル名を見ておく
- `rejected.md`（このスキルと同じディレクトリ）にあるボツ案。出す前に必ず読む

ユーザーが「ボツ」「微妙」「んー」のように、出した回をまるごと退けたら、その回の 5 本を `rejected.md` に足す。
特定の 1 本だけを退けたなら、その 1 本だけを足す。
書いたらコミットと push までしてよい。

手口を書くときは、リスクが伝わる粒度にとどめる。手順書のような書き方はしない。主題は守り方と気づき方に置く。

## ネタが薄くなってきたら

同じような「サービスの設定の落とし穴」が続き始めたら、自分で分野を広げて出し直す。
ユーザーに「どの分野がいい？」と聞き返さない。広く考えて出すのがこのスキルの仕事で、聞き返したら「それを考えるのが君の仕事」と言われた。

広げる先の例：実際のインシデント事例、生成 AI、コンテナ、組織・マルチアカウント、インシデント対応、ID 連携、規制・監査、矛盾する要件をどう両立させるか。

## ideas/ と til/ に書き留めるとき

ユーザーが「書いといて」「入れて」と言ったものだけを書く。勝手に書かない。

書く前に、それが**アイデアか、知識か**を分ける。
「同じアカウント内ならバケットポリシーだけで許可が成立する」のような、知らなかった仕様や仕組みの説明は知識であって、アイデアではない。
知識は `ideas/` ではなく `til/`（Today I Learned）に、同じ形式で書く。

- `ideas/YYYY-MM-DD-名前.md`（知識なら `til/`）、1 行目に `tags:`、**1500 文字以内**（`wc -m` で確かめる）
- このリポジトリのモジュール名・ワークスペース名などを出さず、どの環境にも当てはまる書き方にする
- 文中に「（はず）」を挟まず、末尾の「〜は未確認」の 1 行にまとめる
- 検知の話なら、マネージドで拾えるものを先に書き、自作は足りない分だけにする
- `ideas/` と `til/` のルールは `docs/reference/運用ルール.md` も参照

コミットと push はしてよいが、**PR のマージは、明示的に頼まれたときだけ**。
一度「マージして」と言われても、そのあと PR の中身が大きく変わったなら、マージ前にもう一度確かめる。
