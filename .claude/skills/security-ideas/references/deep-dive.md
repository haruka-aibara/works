# じっくり 1 本を出す

5 本をぱっと出すのではなく、時間をかけて**刺さる 1 本**だけを出すときの手順。
「じっくり」「1 本でいいから深く」と言われたとき、または毎朝の自動実行で使う。

SKILL.md の「狙い」「1 本の具体度」「常識すぎないか」「検知の話は、まずマネージド」「出さないもの」は、ここでもそのまま守る。
違うのは、たくさん出してから削り、残ったものを裏取りし、**考えた本人ではない審査役**が通したものだけを出すこと。

## 0. 材料をそろえる

考え始める前に、次を読む。

- **ユーザーの過去の反応**：`rejected.md` と `ideas/`・`til/` のファイル名。自動実行なら、渡されたフィードバックの一覧（採用・ボツ・反応なしと、ユーザーのコメント）も読む
- **手本**：SKILL.md の「1 本の具体度」にある 4 本
- **新しい材料**：自動実行なら、渡された AWS の直近のアップデート一覧。対話なら、思い当たる最近のアップデートを挙げる

反応の一覧からは、「何が採用され、何がボツになったか」の傾向を 3 行で書き出しておく。
これを、あとの審査の物差しにする。

## 1. 広げる（候補 30 本）

サブエージェントを 3 つ並べて立て、それぞれ別の立場で 10 本ずつ出させる。
1 人で出すと、同じ傾向のネタに寄るため。

| 立場 | 考えること |
|---|---|
| 攻撃者 | 盗んだ権限で、守る側が想定していない使い方をする。正規の機能を正規の手順で使って害をなす |
| 監査人・運用者 | 設定したまま時間がたつと崩れるもの、守らせ続けられていないもの、組織の動きで穴が開くもの |
| 新機能の目利き | アップデート一覧から 1 つ選び、昔からある機能と組み合わせたときに起きることを考える。新機能は「組み合わせるとこうなる」がまだどこにも書かれていない |

どの立場でも、半分以上は「組み合わせ」にする。
一言ずつでよく、ここでは質を気にしない。

## 2. 削る（5 本まで）

各候補に次の 5 つで ○ × をつけ、1 つでも × なら落とす。

| 基準 | × になる例 |
|---|---|
| 既出でない | `ideas/`・`til/`・`rejected.md`・フィードバックの一覧と同じネタ、同じ切り口の言い換え |
| 常識でない | AWS セキュリティの DevOps エンジニアなら知っている。Security Hub CSPM のコントロールや AWS のベストプラクティス文書にそのまま載っている |
| 機能の紹介で止まっていない | 「〇〇を使おう」で終わる。守らせ続ける仕組み・組み合わせ・裏側の仕組みのどれにも届いていない |
| 具体的に書ける | どのサービスの・どの設定で・何が起きて・どう直すかの、どれかが埋まらない |
| 明日やれる | 大規模な組織変更や製品導入が前提で、1 人の DevOps エンジニアが手を付けられない |

1 本も残らなければ、1 に戻る。

## 3. 裏取りする

残った候補それぞれについて、公式ドキュメントで次を確かめる。

- 書いた挙動が本当にその仕様か（API 名・条件キー・イベント名・上限値）
- GuardDuty・Security Hub CSPM・IAM Access Analyzer・Config のマネージドルールなどで、もう拾えていないか
- AWS のブログやドキュメントに、同じ組み合わせがそのまま書かれていないか

仕様が違えば直すか落とす。
マネージドでもう拾えるなら、足りない分だけの話に絞れないか考え、絞れなければ落とす。

## 4. 審査させる

**新しいサブエージェント**を審査役として立てる。
考えた過程は渡さず、次だけを渡す。

- 候補の本文（何が起きるか・どう直すか・なぜ見落とされるか）
- SKILL.md と `rejected.md`
- 0 で書き出した「採用とボツの傾向」と、フィードバックの一覧

審査役には、ユーザーとしてこの候補を Slack で読んだときの反応を、次の 5 段階で予想させる。

| 点 | 予想される反応 |
|---|---|
| 5 | 「その視点はなかった」。すぐ試したくなる |
| 4 | 「なるほど」。ideas/ に書き留めたくなる |
| 3 | 「知ってはいたけど、言われると確かに」 |
| 2 | 「それは知ってる」「常識すぎる」 |
| 1 | 「抽象的」「機能の紹介だよね」「うちでやる意味ある？」 |

点と一緒に、いちばん強い反論を 1 つ言わせる。
**4 点未満は落とす。**
4 点以上でも、反論への答えが本文に入っていなければ、足してからもう一度審査させる。

## 5. 1 本に絞って磨く

4 点以上の中から、いちばん点の高い 1 本を選ぶ。
選んだ 1 本は、次の 3 つがそろうまで書き直す。

- **何が起きるか**：どのサービスの・どの設定で・何が起きるか。読んだ人が自分の環境に当てはめられる粒度
- **どう直すか / どう気づくか**：明日そのまま手を付けられる粒度。検知ならマネージドで拾える分を先に書く
- **なぜ見落とされるか**：ドキュメントのどこにも「組み合わせるとこうなる」と書かれていない、など。これがアイデアの価値そのもの

4 点以上が 1 本もなければ、1 に戻る。
2 周しても出なければ、**その日は見送る**。数合わせで弱い 1 本を出すと、全体の信用が落ちる。

## 出すときに添えるもの

- 審査役の点と、いちばん強かった反論への答え
- 裏取りに使った URL
- 確かめきれなかったこと
- 落とした候補のうち、惜しかったもの 2〜3 本と、落とした理由（一言）
