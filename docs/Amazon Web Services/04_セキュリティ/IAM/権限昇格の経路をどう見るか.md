# 権限昇格の経路をどう見るか

2026-10 時点の整理。

## 権限昇格の経路とは

1 つずつは弱い権限でも、組み合わせると自分より強いロールになれる道。

例：`dev` ロールに `iam:PassRole`（Resource が `*`）と `lambda:CreateFunction` がある。
`dev` は管理者ロールを付けた Lambda を作り、その中で好きな操作を実行できる。
`dev` 自身は何もできないのに、Lambda を経由して管理者になれる。

同じ型の例：

- `iam:CreatePolicyVersion`：自分に付いたポリシーの新しい版を `*` で作る
- `iam:UpdateAssumeRolePolicy`：強いロールの信頼ポリシーに自分を足す
- `ec2:RunInstances` と `iam:PassRole`：強いロールを付けた EC2 の中で認証情報を取る

ポリシーを 1 つずつレビューしても気づけない。
権限が別々の PR や別々のポリシーで足されると、組み合わせとして見る人がいない。

この考え方は attack path analysis（攻撃経路分析）と呼ばれる。
Active Directory の BloodHound が有名にしたもので、AWS の IAM に持ち込んだのが PMapper。

## 誰が見るか

各チームは自分のロールをレビューする。
チームをまたいで連鎖し、最終的に管理者につながるかは、セキュリティ担当が横断で見る。

## 検出の手段

| 手段 | 何がわかるか | 弱いところ |
|---|---|---|
| [pathfinding.cloud](https://pathfinding.cloud/)（Datadog、2025-12） | 経路の一覧。65 本超。ID 付きで、`paths.json` で機械的に読める | カタログであって、スキャナではない |
| PMapper | ロール同士の関係をグラフにして、連鎖をたどる | 更新が止まり気味。新しい経路が入っていない |
| Cloudsplaining | ポリシーの中の危ない権限の組み合わせを洗い出す。ポリシーの JSON を入力にできる | ロールをまたいだ連鎖は見えない |
| 新しめの OSS（Heimdall・aws-iam-paths・cloud-audit など） | pathfinding.cloud 級の経路数をうたう | 小さなプロジェクトで、成熟度は不明 |
| IAM Access Analyzer の internal access findings（2025-06） | SCP・RCP・ID ポリシーを合わせて、重要な S3・DynamoDB・RDS スナップショットに誰が届くかを毎日出す | 「届くか」までで、経路は出さない |
| 商用 CNAPP（Wiz・Orca など） | attack path 機能として作り込まれている | 有料 |

Datadog によると、pathfinding.cloud の経路のうち 4 割は、調べたどの OSS ツールでも検出できなかった。
OSS で機械的に網羅できるものは、意外とない。

理由：

- AWS の権限評価（SCP・RCP・permission boundary・セッションポリシー・リソースポリシー・条件キー）を正しく再現するのが重い
- 新しいサービスが出るたびに、「ロールを渡して何かを実行させる」経路が増える
- 攻撃経路の分析は商用製品の目玉機能なので、作り込まれたものは商用の中にある

### ツールを信じてよいかを測る

[Pathfinding Labs](https://securitylabs.datadoghq.com/articles/introducing-pathfinding-labs/) は、わざと経路を仕込んだ環境の集まり。
sandbox アカウントに deploy してツールに探させれば、何本拾えるかを自分で測れる。

### AI に聞く

IAM を全部列挙して AI に「昇格につながるものは？」と聞くのはアリ。
経路の知識は持っていて、文脈を読んで判断でき、一覧にない経路を推論で見つける可能性もある。

ただし、そのままだと次の弱さがある。

- アカウントが大きいと、IAM の出力が数 MB になり、見落としが増える
- 何段もたどる探索は苦手で、取りこぼしや、存在しない経路のでっち上げが起きる
- SCP や条件キーで実際には Deny される経路を、通ると言いがち
- 毎回答えが変わるので、定期的な検知には不安定

使うなら、役割を分ける。

| 役割 | 担当 |
|---|---|
| 候補を漏れなく挙げる | グラフで機械的に探すツール |
| 本当に危ないか、なぜか、どう直すかを説明する。一覧にない経路も考える | AI |
| AI が主張した経路を 1 段ずつ検証する | `iam simulate-principal-policy` |

AI に simulate を呼ぶツールを持たせ、自分で確かめながら進めさせると、でっち上げを消せる。
AI だけでやる場合も、Pathfinding Labs で何本見つけられるかを先に測っておく。

## 結論：見つけるより、材料の権限を絞る

経路の大半は、少数の危ない権限を部品にしている。

- `iam:PassRole`（Resource が `*`）
- `iam:CreatePolicyVersion` / `iam:Put*Policy` / `iam:Attach*Policy`
- `iam:UpdateAssumeRolePolicy`
- `iam:CreateAccessKey` / `iam:CreateLoginProfile`
- `sts:AssumeRole`（Resource が `*`）

これらを SCP か permission boundary で、IaC の実行ロールなど例外以外に禁止する。
材料がなければ経路は組み立てられないので、検出が不完全でも困らない。
例外のロールだけを、人か AI が重点的に見る。

PR の時点で止めるなら、Terraform の plan から取り出したポリシーに、Access Analyzer の custom policy checks（`CheckAccessNotGranted`）を当てる。
禁止する権限の一覧は、`paths.json` から生成する。
