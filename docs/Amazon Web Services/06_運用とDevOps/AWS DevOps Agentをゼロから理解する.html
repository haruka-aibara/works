AWS DevOps Agent をゼロから理解する

「深夜にアラームが鳴ってから復旧するまで、実際は何に時間を使っているのか」という手前の話から始め、5 ステップで AWS DevOps Agent の位置づけまでたどり着きます。

この記事の目的

AWS DevOps Agent の解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「自律的にインシデントを調査し、根本原因を特定して緩和計画を提示するエージェント型 SRE サービスです」という、中級者向けの前提から始まるからです。その一語一語が、現場のどの面倒を消すために出てきたのかが分からないまま、機能の箇条書きだけが増えていきます。

そこでこの記事は、あえて遠回りします。「障害対応の時間はどこに消えているのか」という、いちばん手前の話から始めて 5 ステップで進みます。ゴールは機能を暗記することではなく、DevOps Agent が誰の、どの手間を肩代わりする道具なのかを自分の言葉で説明できることです。

この記事の道のり

  1. STEP 1障害対応で本当に時間を食うところ
  2. STEP 2調査の材料は最初から散らばっている
  3. STEP 3調べる仕事を回すエージェント
  4. STEP 4起点・記録・人の承認
  5. STEP 5AWS DevOps Agent として組み立てる

STEP 4 まではすべて前提知識です。本題の AWS DevOps Agent は STEP 5 だけですが、そこに至る 4 ステップがないと「自律調査」「根本原因分析」「緩和計画」がばらばらの機能の暗記になります。

STEP 1：障害対応で本当に時間を食うところ

  1. STEP 1障害対応で本当に時間を食うところ
  2. STEP 2調査の材料は最初から散らばっている
  3. STEP 3調べる仕事を回すエージェント
  4. STEP 4起点・記録・人の承認
  5. STEP 5AWS DevOps Agent として組み立てる

深夜 2 時、「API のエラー率が 5% を超えた」というアラームが鳴ります。起こされた当番が最初にやることは、直すことではありません。「何が起きているのか」を突き止めることです。

アラームが教えてくれるのは症状だけです。エラー率が上がったこと自体は分かっても、原因がデータベースの接続枯渇なのか、直前のデプロイなのか、依存している外部 API なのかは分かりません。そこから当番は、メトリクスを見て、ログを絞り込んで、デプロイ履歴を確認して、と画面を渡り歩きます。

確認問題 では、アラームをもっと細かく作り込めば、この時間は短くなるでしょうか。

答えを見る

短くなりません。むしろ増えます。 アラームが教えるのは症状であって原因ではないので、細かくすればするほど「同時に鳴った 8 つのアラームのうち、どれが原因でどれが結果か」を仕分ける仕事が増えます。詰まっているのは検知ではなく、散らばった材料を突き合わせる作業です。では、その材料はどこにあるのでしょうか。

STEP 2：調査の材料は最初から散らばっている

  1. STEP 1 ✓障害対応で本当に時間を食うところ
  2. STEP 2調査の材料は最初から散らばっている
  3. STEP 3調べる仕事を回すエージェント
  4. STEP 4起点・記録・人の承認
  5. STEP 5AWS DevOps Agent として組み立てる

原因究明に必要な材料は、実はすでに全部そろっています。足りないのはデータではなく、それを突き合わせる人手です。

メトリクスは CloudWatch に、ログもそこに、リクエストの経路は X-Ray のトレースに、誰がいつ設定を変えたかは CloudTrail に、いつ何をデプロイしたかは CI/CD パイプラインに、対処手順は Runbook に、去年の同じ障害は課題管理システムに。当番はこれを頭の中で 1 本の時間軸に並べ直しています。

確認問題 材料が散らばっているのが問題なら、全部を 1 枚のダッシュボードに集めれば解決するでしょうか。

答えを見る

見る場所は減りますが、仕事は減りません。 ダッシュボードは決めた指標を並べるだけで、「今回はどこを深掘りするか」を判断してくれません。障害のたびに見るべき場所は変わるので、結局その場でクエリを書いて絞り込むことになります。足りないのは表示ではなく、次に何を調べるかを決める判断です。それを人以外にやらせられるでしょうか。

STEP 3：調べる仕事を回すエージェント

  1. STEP 1 ✓障害対応で本当に時間を食うところ
  2. STEP 2 ✓調査の材料は最初から散らばっている
  3. STEP 3調べる仕事を回すエージェント
  4. STEP 4起点・記録・人の承認
  5. STEP 5AWS DevOps Agent として組み立てる

ここでいうエージェントは、質問に答えるチャットとは別のものです。目標を渡すと、自分でツールを呼び、結果を見て次の一手を決める、というループを回し続けるプログラムを指します。

当番がやっている「メトリクスを見る → 怪しい時間帯を絞る → その時間帯のログを引く → デプロイ履歴と突き合わせる」という流れは、まさにこのループです。1 回の判断ごとに使うツールが変わり、前の結果が次の入力になります。

確認問題 同じことは、生成 AI のチャットにログを貼り付けて相談しても実現できるのでは？

答えを見る

途中までは同じですが、起点が違います。 チャットに貼るには「どのログを貼るか」を人が先に決める必要があり、その判断こそが STEP 2 で詰まっていた部分です。エージェントは自分でツールを呼べるので、材料を集めるところから始められます。ただし、そのためには 何を起点に動き出すかと、どこまで自分で決めてよいかを先に決めておく必要があります。

STEP 4：起点・記録・人の承認

  1. STEP 1 ✓障害対応で本当に時間を食うところ
  2. STEP 2 ✓調査の材料は最初から散らばっている
  3. STEP 3 ✓調べる仕事を回すエージェント
  4. STEP 4起点・記録・人の承認
  5. STEP 5AWS DevOps Agent として組み立てる

調査を代わりにやらせるには、ループの前後に 3 つの約束事が要ります。

起点は、いつ動き出すかです。監視のように常時張り付くのではなく、アラームが発報した、Webhook が叩かれた、チケットが起票された、人が調べてと頼んだ、といった出来事をきっかけに 1 回分の調査が始まります。

記録は、何を見てどう考えたかの筋道を残すことです。結論だけ出されても、当番はそれを信じてよいか判断できません。「このメトリクスを見て、この時間帯に絞って、このログを引いた」という手順が残っていて初めて、人がその推論を検証できます。

承認は、直す操作を人が握ることです。原因が分かった後の「対処する」は、環境を変える行為です。ここを自動にしてしまうと、間違った仮説がそのまま本番への変更になります。

確認問題 原因まで特定できるなら、そのまま自動で直させたほうが復旧は速いのでは？

答えを見る

速いのは、原因の判定が正しかった場合だけです。 間違っていれば、障害中の本番環境に見当違いの変更が入り、状況はさらに読めなくなります。調査は空振りしても損失が小さく、対処は外すと損失が大きい——非対称なので、自動化する範囲も左右で変えます。ここまでの 4 ステップが、そのまま AWS のサービスとして組み上がったものが次の話です。

STEP 5：AWS DevOps Agent として組み立てる

  1. STEP 1 ✓障害対応で本当に時間を食うところ
  2. STEP 2 ✓調査の材料は最初から散らばっている
  3. STEP 3 ✓調べる仕事を回すエージェント
  4. STEP 4 ✓起点・記録・人の承認
  5. STEP 5AWS DevOps Agent として組み立てる

AWS DevOps Agent は、ここまでの 4 ステップをそのまま実装したマネージドサービスです。re:Invent 2025 でプレビュー発表され、2026 年 3 月に一般提供が開始されました。位置づけは「経験のある DevOps エンジニアと同じ手順で調査をする、常駐のチームメイト」です。

STEP 1〜4 との対応で見ると、そのまま重なります。

ここまでの話AWS DevOps Agent での姿
散らばった材料（STEP 2）アカウント関連付けと各種コネクタ。リソースとその関係（トポロジ）と過去のインシデントを学習して土台にする
調査ループ（STEP 3）自動インシデント調査。調査の途中経過に会話で割り込める調査チャットもある
起点（STEP 4）CloudWatch アラーム、Webhook、チケット、オペレーターアプリからの手動依頼
記録（STEP 4）推論の手順と実行したアクションを残すジャーナル。API 呼び出し自体は CloudTrail にも残る
承認（STEP 4）出力は緩和計画まで。環境を変える操作にはアカウント関連付けに登録した昇格ロールが必要で、承認を挟む

ここまでは障害が起きた後の話ですが、DevOps Agent にはもう一方の使い方があります。過去のインシデントの傾向を横断で見て、可観測性の穴・構成の弱点・デプロイパイプラインの改善点を推奨として出す機能です。「毎回このメトリクスがなくて調査が止まる」という事実は、調査を積み重ねた側にしか見えません。

料金はエージェントが働いた時間に対する秒課金で、GA 時点では 1 エージェント秒あたり 0.0083 USD（約 0.5 USD/分）です。有効にしておくだけでは課金されず、調査 1 回が数分なら数 USD という単位になります。利用できるリージョンは 6 つで、東京リージョンが含まれます。

権限設計を先に決める。 調査用ロールに与える読み取り権限の範囲が、そのままエージェントに見える範囲になります。逆に、昇格ロールを登録しなければ「調べるだけで何も変えない」状態に固定できます。まずこの状態から始めて、どこまで任せるかは実績を見てから広げるほうが安全です。

確認問題 DevOps Agent を有効にすれば、それだけで障害対応の時間は短くなるでしょうか。

答えを見る

材料がつながっていなければ短くなりません。 エージェントが見られるのは、人が見られるものと同じです。ログが出ていない、リソースの関係が分からない、デプロイ履歴が AWS 側から追えない——そういう状態では、人と同じところで行き詰まります。効果が出る前提は STEP 2 の材料がそろっていることで、そこが弱いなら、まず整えるべきは可観測性のほうです。

まとめ：そのまま使える説明テンプレート

30 秒版

AWS DevOps Agent は、障害の一次調査を代わりにやる AWS のマネージドサービスです。アラームや Webhook を起点に自分で動き出し、メトリクス・ログ・トレース・変更履歴・デプロイ履歴を横断して突き合わせ、根本原因の候補と緩和計画を出します。ただし環境は自分では変えません。実行するかどうかは人が決めます。料金はエージェントが働いた秒に対してかかり、置いておくだけなら無料です。

2 分版（30 秒版に足す分）

解こうとしている問題は、障害対応の時間の大半が「直す」ではなく「何が起きているか突き止める」に消えている、という点です。必要な材料は CloudWatch や CloudTrail、CI/CD にすでにありますが、それを 1 本の時間軸に並べ直す作業を毎回人がやっています。DevOps Agent はここを肩代わりします。

仕組みは、仮説を立てる → ツールを呼ぶ → 結果で絞る、というループです。呼べるツールは読み取り中心で、AWS 側は関連付けたアカウントの IAM ロール経由、AWS の外は Datadog・GitHub・ServiceNow などのコネクタ経由でつながります。推論の手順はジャーナルとして残るので、人が結論を検証できます。

環境を変える操作には別途、昇格ロールと承認が要ります。調査は外しても損失が小さく、対処は外すと大きいので、自動化する範囲を左右で変えている、という設計です。もう一方の使い道として、調査の積み重ねから可観測性やパイプラインの改善点を推奨する機能もあります。

よくある誤解

「AI が障害を自動で復旧してくれるサービス」

既定では復旧しません。出てくるのは原因の候補と緩和計画で、実行するには昇格ロールの登録と人の承認が要ります。「無人で直る」ではなく「一次調査が終わった状態で起こされる」が実態に近い姿です。

「監視サービスなので、CloudWatch の代わりになる」

常時見張る役目は CloudWatch のままです。DevOps Agent はアラームなどを起点に呼ばれて動くので、検知の仕組みがないと起点がありません。置き換わるのではなく、検知の後ろに足されます。

「有効にすれば勝手に環境を学んでくれるので、準備は要らない」

接続した先しか見えません。ログが出ていない、CI/CD がつながっていない、といった穴はそのまま調査の穴になります。導入前にやることは、どの材料をつなぐかを決めることです。
