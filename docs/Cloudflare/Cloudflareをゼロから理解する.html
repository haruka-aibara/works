Cloudflare をゼロから理解する

「ブラウザはどうやってサーバにたどり着くのか」から始めて、5 ステップで「Cloudflare を通すと何が起きるのか」までたどり着きます。

この記事の目的

Cloudflare の解説を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「CDN であり、DNS であり、WAF であり、DDoS 対策であり、エッジでコードも動く」という機能の一覧から始まります。数十のプロダクト名が並び、それぞれの説明は正しいのに、読み終わっても「結局これは何なのか」「なぜ 1 社がこれを全部やれるのか」が残ります。土台がひとつ抜けているからです。

そこでこの記事は、あえて遠回りします。「ブラウザはどうやってサーバにたどり着くのか」というところから始めて、5 ステップで Cloudflare の全体像までたどり着きます。ゴールは用語を覚えることではなく、Cloudflare を自分の言葉で説明できるようになることです。最後に、そのまま口に出せる説明テンプレートを用意しました。

この記事の道のり

  1. STEP 1サーバへの行き方
  2. STEP 2間に代理を立てる
  3. STEP 3代理を世界中に置く
  4. STEP 4通り道だから止められる
  5. STEP 51 リクエストの旅

STEP 4 まではすべて「通り道に居るとはどういうことか」の話です。機能の一覧が出てくるのは STEP 5 だけですが、そこに至る 4 ステップがないと、なぜ 1 社がこれだけの機能を持てるのかが分かりません。逆に言えば、STEP 4 まで進めば STEP 5 は部品を順番に並べるだけの作業に感じられるはずです。

STEP 1：ブラウザはどうやってサーバにたどり着くか

  1. STEP 1サーバへの行き方
  2. STEP 2間に代理を立てる
  3. STEP 3代理を世界中に置く
  4. STEP 4通り道だから止められる
  5. STEP 51 リクエストの旅

アドレスバーに example.com と入力したとき、ブラウザはまず「その名前のサーバはどの IP アドレスか」を DNS に尋ねます。答えが返ってきたら、その IP に対して直接つなぎにいきます。ここまでが、あらゆる Web アクセスの出発点です。

ここで注目してほしいのは、ブラウザが接続先を決めた根拠が DNS の答えただ一点だということです。ブラウザは「203.0.113.10 が本当に example.com のサーバか」を自分で確かめていません。DNS がそう答えたから、そこへ行っただけです。

確認問題 サーバを別のデータセンターに引っ越して IP が変わったとき、世界中のユーザーに何か作業をお願いする必要がありますか。

答えを見る

ありません。DNS の答えを新しい IP に書き換えれば、それ以降のアクセスは自動的に新しい場所へ向かいます。

これを裏返すと、もっと面白いことが言えます。DNS の答えを「自分のサーバ以外の何か」に向けることもできるということです。次のステップはここから始まります。

STEP 2：間に代理を立てる

  1. STEP 1 ✓サーバへの行き方
  2. STEP 2間に代理を立てる
  3. STEP 3代理を世界中に置く
  4. STEP 4通り道だから止められる
  5. STEP 51 リクエストの旅

DNS の答えを、自分のサーバではなく代理のサーバの IP にしてみます。ブラウザは何も知らずにその代理へつなぎます。代理は受け取ったリクエストを自分のサーバ（これをオリジンと呼びます）に取りに行き、返ってきたものをブラウザへ返します。これがリバースプロキシで、Cloudflare を使うというのは、この代理を Cloudflare に任せることです。

ここが Cloudflare を理解する上での最大の山場です。Cloudflare の機能は、ほぼすべて「通信の通り道に居る」ことから導かれます。サーバにエージェントを入れる必要も、アプリのコードを書き換える必要もありません。DNS の答えを差し替えて経路を変えただけだからです。

逆に言うと、オレンジ雲にしていないレコードには Cloudflare の機能は何も効きません。「WAF を有効にしたのにブロックされない」「キャッシュが効かない」の原因の多くはこれです。通っていないものは守れません。

確認問題 代理サーバが東京に 1 台だけあるとします。ロンドンのユーザーにとって、この構成は速くなるでしょうか。

答えを見る

むしろ遅くなります。ロンドンからわざわざ東京の代理まで行き、そこからオリジンへ、という遠回りが増えるだけです。おまけに、その 1 台が落ちればサイト全体が落ちます。

代理は「間に挟まるもの」である以上、ユーザーの近くにいなければ損になる。次のステップはこの問題を解きます。

STEP 3：代理を世界中に置く

  1. STEP 1 ✓サーバへの行き方
  2. STEP 2 ✓間に代理を立てる
  3. STEP 3代理を世界中に置く
  4. STEP 4通り道だから止められる
  5. STEP 51 リクエストの旅

Cloudflare は世界 300 都市以上にサーバ群を置いています。これをエッジと呼びます。ここで問題になるのは「ユーザーをどうやって最寄りのエッジに案内するか」です。DNS で国ごとに違う IP を返す方法もありますが、Cloudflare が使っているのは Anycast です。

Anycast は、同じ IP アドレスを世界中の拠点から同時に広告するやり方です。ネットワークの経路制御はもともと「その宛先への一番近い道」を選ぶので、結果としてユーザーは自動的に最寄りのエッジに着きます。DNS の答えは世界中どこでも同じ 1 つで構いません。

エッジは、一度オリジンから取ってきたファイルを手元に保存しておきます。これがキャッシュで、いわゆる CDN の正体です。次に誰かが同じファイルを要求したら、オリジンに行かずにその場で返せます。

ただし Cloudflare は既定では .js や .css、画像など拡張子で判断できる静的ファイルだけをキャッシュします。HTML や API のレスポンスは既定ではキャッシュされません。ユーザーごとに中身が違う可能性があるからです。

確認問題 「全部キャッシュすれば最速になるのでは？」という発想には何が抜けているでしょうか。

答えを見る

ログイン後のページを他人に配ってしまいます。「A さん向けのマイページ」をキャッシュすると、次に来た B さんにそれが返ります。中身がユーザーごとに変わるものはキャッシュできません。

つまり、ログインや決済のような本当に守りたいリクエストほど、キャッシュを素通りしてオリジンに届くということです。そこは無防備なのでしょうか。次のステップへ。

STEP 4：通り道だから、止められる

  1. STEP 1 ✓サーバへの行き方
  2. STEP 2 ✓間に代理を立てる
  3. STEP 3 ✓代理を世界中に置く
  4. STEP 4通り道だから止められる
  5. STEP 51 リクエストの旅

通り道に居るということは、オリジンに届く前に中身を見て、捨てられるということです。防御機能はここから出てきます。

  • DDoS 緩和：大量のパケットを送りつける攻撃は、世界中のエッジに分散して着弾します。オリジンの細い回線ではなく Cloudflare の巨大な容量で受け止めるため、オリジンには何も届きません
  • WAF：SQL インジェクションや XSS を狙うリクエストを、HTTP の中身を見て判定し、オリジンに渡す前にブロックします
  • Bot 対策・レート制限：同じ IP からログインを連打する、といった1 本では違法でないが量が異常な通信を止めます

ここで 1 つ、どうしても避けて通れない話があります。中身を見るには、暗号を解かなければなりません。HTTPS の通信は、Cloudflare を挟むと 1 本ではなく 2 区間に分かれます。

モード区間 B（Cloudflare → オリジン）評価
Flexible暗号化しない（平文の HTTP）使わない。ブラウザには鍵マークが出るのに、後半が平文
Full暗号化するが、証明書を検証しない途中で別のサーバにすり替えられても気づけない
Full (strict)暗号化し、証明書も検証するこれを選ぶ。オリジンには Cloudflare 発行のオリジン証明書を置けばよい

もう 1 つ、構成上どうしても残る穴があります。攻撃者がオリジンの IP を知ってしまえば、Cloudflare を通さずに直接つなげることです。DNS の答えを差し替えただけで、オリジンは今も公開されたままだからです。

オレンジ雲にしてもオリジン IP は自動では隠れません。過去の DNS 履歴、メールヘッダ、証明書の透明性ログなどから割れます。Cloudflare を入れた直後にやることは、上の①〜③のいずれかで直接接続を塞ぐことです。ここを放置すると、防御は「迂回できる防御」のままになります。

確認問題 WAF でブロックされるはずのリクエストが、たまたまキャッシュ済みの URL 宛てだったとします。キャッシュから応答が返ってしまうでしょうか。

答えを見る

返りません。WAF の判定はキャッシュを見るより前に行われるので、ブロックされたリクエストはキャッシュにもオリジンにも到達しません。

この「どちらが先か」は設定が効く／効かないを左右します。最後のステップで、1 本のリクエストが通る順番をまとめて見ます。

STEP 5：1 リクエストの旅

  1. STEP 1 ✓サーバへの行き方
  2. STEP 2 ✓間に代理を立てる
  3. STEP 3 ✓代理を世界中に置く
  4. STEP 4 ✓通り道だから止められる
  5. STEP 51 リクエストの旅

ここまでの部品を、1 本のリクエストが通る順番に並べます。これが Cloudflare の全体像です。

⑤ の Workers は、通り道でコードを実行する仕組みです。オリジンに行く前にリダイレクトする、ヘッダを書き換える、A/B テストで振り分ける、といったことがサーバを持たずにできます。さらに、オリジンを一切持たずに Workers だけで API を組むこともできます。

そして Cloudflare の他の製品も、すべてこの図の変形として読めます。社内アプリの前に通り道を置いて認証を挟めば Zero Trust（Access）になり、オリジンから外向きに接続を張れば Tunnel、通り道に置くファイル置き場が R2 です。入口は常に「DNS の答えを差し替えて、通り道になる」の一点です。

確認問題（考察） ある日サイトが表示されなくなりました。オリジンは正常に動いています。DNS のレコードを一時的にグレー雲（プロキシ無効）に戻すと、何が起きて、何が起きなくなるでしょうか。

答えを見る

ブラウザがオリジンに直接つなぐ STEP 1 の状態に戻るので、Cloudflare 側の問題が原因ならサイトは復旧します。切り分けの手段として有効です。

同時に、WAF も DDoS 緩和もキャッシュも Workers も全部止まります。オリジン IP も公開されます。加えて、STEP 4 の①でファイアウォールを Cloudflare の IP だけに絞っていた場合は、今度は誰も到達できません。「通り道を外す」は、速度と防御の両方を同時に外す操作です。

まとめ：そのまま使える説明テンプレート

30 秒版

Cloudflare は、DNS の答えを自分たちの IP に差し替えることで、サイトへの通信を全部いったん自社のネットワークに通す仕組みです。世界 300 都市以上に同じ IP を持つ拠点があり、ユーザーは最寄りに着きます。通り道に居るので、そこでキャッシュを返せば速くなり、攻撃を落とせば守れる。CDN も WAF も DDoS 対策も、全部その応用です。

2 分版（30 秒版に足す分）

通信は 2 区間に分かれます。ブラウザ〜Cloudflare と、Cloudflare〜オリジンです。中身を検査する以上エッジで一度復号されるので、後半区間の設定は Full (strict)、つまり暗号化と証明書検証の両方を有効にします。

注意点として、オリジンのサーバ自体は公開されたままなので、IP が知られると通り道を迂回して直接叩かれます。Cloudflare の IP レンジだけを許可するか、Tunnel で受信ポートを閉じるところまでやって、はじめて防御が成立します。

リクエストが通る順番は、DDoS 緩和 → WAF → キャッシュ → Workers → オリジンです。ブロックされたものはキャッシュにもオリジンにも届かず、キャッシュにヒットしたものはオリジンに届きません。

よくある誤解

「Cloudflare = CDN」

CDN は結果のひとつです。入口は DNS とリバースプロキシで、キャッシュはその上に乗っている機能にすぎません。この順番で捉えないと、なぜ同じ会社が DNS もゼロトラストもやっているのかが説明できなくなります。

「オレンジ雲にすればオリジンは隠れる」

隠れるのは DNS の答えだけです。サーバは今日も 203.0.113.10 で待ち受けています。過去の DNS 履歴や証明書の透明性ログから IP は割れるので、オリジン側のファイアウォールを閉じるまでが作業です。

「プロキシを有効にすれば、どんな通信も守られる」

オレンジ雲が通すのは HTTP / HTTPS の標準的なポートだけです。SSH や任意の TCP は、そのままでは通りません（Spectrum や Tunnel など別の仕組みを使います）。「Cloudflare を入れたからサーバは安全」ではなく、「Web の通り道が守られた」が正確な言い方です。
