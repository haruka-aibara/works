# 人間の指摘で AI レビューを育てる

AI レビューを入れても、人間のレビュアーが毎回同じ種類の指摘をしているなら、AI はその観点を知らないままになっている。
人間の指摘を AI の観点ファイル（`REVIEW.md` やレビュー用プロンプト）に還元し、
指摘されるたびに AI が見る範囲が広がっていく仕組みを考える。

## 基本のループ

```
人間がPRで指摘
  → AI が見逃した指摘だけを抽出
  → 一般化して観点の候補にする
  → 人間が採用・却下（PR で承認）
  → 観点ファイルに追記
  → 次の PR から AI が見る
  → 決定的に検査できるものは lint / ポリシーに昇格して観点から消す
```

肝は「吸収する」より「吸収したものを捨てる」ほうにある。
観点は足すだけだと肥大化し、AI の精度が落ちる。

## アイデア

### 1. AI が見逃した指摘だけを学習対象にする

人間のコメントのうち、同じ PR で AI がすでに指摘していたものは学ぶ必要がない。
「人間は指摘したが AI は黙っていた」差分だけを拾う。
同じ箇所・同じ趣旨かの突き合わせは AI に判定させる。

### 2. 週次で集めて観点追加の PR を自動で作る

マージ済み PR のレビューコメントを週 1 で集め、AI が観点の候補にまとめて PR を出す。
人間はその PR をレビューするだけでよく、観点の追加にも人間の承認が挟まる。
各観点には元になった PR コメントのリンクと追加日を付ける。

### 3. 2 回出たら観点にする

1 回きりの指摘は、その PR 固有の事情であることが多い。
同じ趣旨の指摘が 2 回出たら昇格、という閾値を置くと、個別事情が観点に紛れ込みにくい。
1 回目は「候補」として溜めておく。

### 4. 指摘の場でその場で一般化を提案させる

人間が指摘したスレッドに AI が「この観点を一般化するとこうなります。観点に入れますか？」と返信し、
レビュアーが 👍 したら採用候補にする。
週次でまとめて聞くより、指摘した本人の記憶が新しいうちに意図を確かめられる。

### 5. 観点ごとに当たり率を測って弱い観点を消す

AI の指摘が修正されたか（resolve されて差分が入った）、無視・却下されたかを観点ごとに数える。
却下が多い観点は書き方を直すか消す。
長く一度も発火していない観点も、もう起きない問題なら消す。

### 6. lint・ポリシーに昇格させたら観点から消す

AI の観点は「機械で決定的に検査できるようになるまでの中継地点」と捉える。
tflint・semgrep・Conftest などで書けるものは書き、書けたら観点ファイルから消す。
AI に残るのは、文脈や意図を読まないと判断できない観点だけになる。

### 7. 元の指摘を回帰テストにする

観点の元になった PR の差分を評価セットとして残し、
観点ファイルやモデルを変えたときに AI がまだその指摘をできるかを再生して確かめる。
観点を整理・削除したときに、意図せず見えなくなったものを検出できる。

### 8. パスごとに観点を分ける

Terraform の指摘は `modules/` に、記事の指摘は `docs/` に、というように観点を置き場所で分ける。
全観点を毎回読ませるより、関係するものだけ読ませたほうが精度もコストもよい。

## 気をつけること

- **個人の好みが固定化する**：特定の人の癖が観点になると、チームの合意ではないものが強制される。採用は PR で人間が承認する
- **矛盾する指摘**：人によって逆のことを言う場合がある。候補の段階で既存観点との矛盾を AI に検出させる
- **プロンプトインジェクション**：PR コメントは外部から書き込める。観点の材料にするのは信頼できるレビュアーのコメントだけに絞る
- **肥大化**：足す仕組みだけ作ると必ず膨らむ。5・6 の「消す仕組み」とセットで入れる

## 最初の一歩

全部作らずに、2（週次で集めて PR）だけ手で回してみる。
人間のコメントを集めて AI に「AI が見逃したものを観点にして」と頼み、出てきた候補を目で見る。
候補の質が低いなら 1・3 の絞り込みを足す、という順で育てる。
