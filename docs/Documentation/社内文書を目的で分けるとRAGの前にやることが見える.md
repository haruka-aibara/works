# 社内文書を目的で分けると、RAG の前にやることが見える

「社内文書を AI に読ませれば、聞けば答えが返ってくる」という話はよく出る。

ただ、社内文書の多くは古い。
古い文書を RAG で引いても、古い答えが返ってくるだけで意味がない。

しかも RAG を通すと、古い手順が出典付きのきれいな文章で返ってくる。
人が検索していた頃は更新日や書きぶりで「古そうだ」と疑えたが、その手がかりが消える。

**古い文書は、検索よりも RAG のほうが害が大きい。**

では文書を最新に保てばいいのか。
その前に、**そもそも文書は何のためにあるのか**から考えると整理がつく。

## 文書の目的は4つ

| 目的 | 中身 | 例 | 「古い」とは |
|---|---|---|---|
| 伝える | 知っている人がいないときに、知らない人に伝える | 手順書・構成図・設計の説明 | 元が変わったのに追いついていない |
| 決める | 後で揉めないように合意を固定する | 規程・ルール・契約・合意した仕様 | 古くならない。有効か、改訂・失効したか |
| 残す | 何があったか、なぜそうしたかを残す | 議事録・ADR・インシデント記録 | 古くならない。その時点の記録 |
| 考える | 書くことで考えを整理する | 検討メモ・設計の下書き | 書き終えた時点で役目が終わっている |

**古い文書の問題は、ほぼ「伝える」の文書だけで起きる。**

「決める」は有効か失効か、「残す」は日付付きの記録、「考える」は書き捨て。
どれも「最新に保つ」ものではない。

## 設計やコーディングを文書に起こしたものはキャッシュ

**ただの設計やコーディングを人間向け文書に起こしたものは、実質的にキャッシュであり、実態を見ればいいだけ。**

キャッシュなので、実態が変わると古くなる。
「古い文書をどう最新に保つか」は、キャッシュをどう更新するかの話で、そもそも実態を見に行けば要らない。

これまで文書に起こしていたのは、実態（コード・IaC・設定）を人が読むのが大変だったから。
今は AI に実態を読ませて、聞かれたときに説明させればいい。

### 同じ文書でも、時期で目的が変わる

設計書がわかりやすい。

- **実装前**：「こう作る」と決めるための文書。目的は「決める」「考える」で、キャッシュではない
- **実装後**：「どう作ったか」の部分は、コードのキャッシュになる。「なぜそうしたか」の部分は「残す」になる

設計書が古くなって困るのは、実装後も「どう作ったか」を最新の説明として持ち続けるから。
実装が終わったら、「なぜ」だけを ADR などの記録に移し、残りは閉じる。

## RAG がうまくいかない理由

社内の Wiki には、この4種類が区別なく混ざっている。
あるページが、古いかもしれないキャッシュなのか、今有効な決まりなのか、過去の記録なのか、書き捨てのメモなのか、ページを見ても分からない。

RAG はそれを全部「今の正解」として同じ扱いで引く。
過去の議事録に書かれた案も、失効した規程も、書きかけのメモも、今の答えの材料になる。

**問題は古さだけでなく、目的の区別がないこと**にある。

## RAG の前にやること

| 目的 | やること |
|---|---|
| 伝える | 減らす。AI に実態（コード・設定）を直接読ませる。人の頭にしかないことは、オーナーと最終確認日を出す |
| 決める | 有効か失効かを明示する。改訂したら旧版を失効にする |
| 残す | 日付付きの記録として扱う。答えに使うときは「◯年◯月時点の記録」と出す |
| 考える | 書き終えたら閉じる。結論は「決める」か「残す」に移す |

目的が分かれていれば、RAG 側でも扱いを変えられる。
「決める」は有効なものだけ、「残す」は日付付きで、「考える」は引かない、「伝える」は元を読む。

どれにも当てはまらない、オーナーも名乗り出ないページは、[いらないページを消せる状態を作る](いらないページを消せる状態を作る.md) の「消してよいか」の定例に流す。

## 気をつけること

- **AI に実態を読ませるのは、権限を渡すこと。**
  本番の設定やログを読める AI は、それ自体が守る対象になる。
  読み取り専用に絞る、読める範囲を分ける、呼び出しを記録する
- **監査で文書を求められるものは残る。**
  ISMS のように文書化そのものが要求されるものは「決める」「残す」として扱う
- **実態を読めない相手には書く。**
  社外・契約先・AI の権限を持たない人に渡すものは、「伝える」の文書として書くしかない。
  その場合は渡した時点のスナップショットとして扱う

## まとめ

- 文書の目的は、伝える・決める・残す・考えるの4つ
- ただの設計やコーディングを人間向け文書に起こしたものは、実質的にキャッシュであり、実態を見ればいいだけ
- RAG がうまくいかないのは、4つが区別なく混ざり、全部が「今の正解」として引かれるから
- RAG の前に、文書を目的で分ける
