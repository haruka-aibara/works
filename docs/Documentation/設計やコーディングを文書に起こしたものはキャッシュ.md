# 設計やコーディングを文書に起こしたものはキャッシュ

「社内文書を AI に読ませれば、聞けば答えが返ってくる」という話はよく出る。

ただ、社内文書の多くは古い。
古い文書を RAG で引いても、古い答えが返ってくるだけで意味がない。

しかも RAG を通すと、古い手順が出典付きのきれいな文章で返ってくる。
人が検索していた頃は、更新日や書きぶりで「古そうだ」と疑えたが、その手がかりが消える。

## 文書に起こしたものはキャッシュ

**ただの設計やコーディングを人間向け文書に起こしたものは、実質的にキャッシュであり、実態を見ればいいだけ。**

キャッシュなので、実態が変わると古くなる。
古い社内文書を RAG で読ませるのは、古いキャッシュを読ませているのと同じ。

「古い文書をどう最新に保つか」は、キャッシュをどう更新するかの話で、そもそも実態を見に行けば要らない。

これまで文書に起こしていたのは、実態（コード・IaC・設定）を人が読むのが大変だったから。
今は AI に実態を読ませて、聞かれたときに説明させればいい。

### 設計書も、実装したらキャッシュになる

実装前の設計書は「こう作る」と決めるためのもので、キャッシュではない。

実装が終わると、「どう作ったか」の部分はコードのキャッシュになる。
設計書が古くなって困るのは、実装後もそれを最新の説明として持ち続けるから。

実装が終わったら、「なぜそうしたか」だけを ADR などの記録に移し、残りは閉じる。

### 例：Terraform モジュールの README

これまでのモジュールの README には、入力・出力の一覧と how to use の説明がよく書かれていた。
どちらも実態のキャッシュで、`variables.tf` と `outputs.tf`、コードを見ればわかる。

README に残すのは、コードを見てもわからないことだけにする。

- **何のためのモジュールか（intent）**：何を実現したいか、何は意図的にやらないか
- **なぜこの作りか**：ほかのやり方を選ばなかった理由
- **コードの外にある前提**：先に手でやっておく設定、apply の順番、決まったリージョンでしか動かない、など
- **ハマりどころ**：destroy すると中身ごと消える、作り直しになる変更がある、など

how to use を残したいなら、説明文ではなく `examples/` に置いて CI で実際に動かす。
壊れたら CI が落ちるので、キャッシュと違って古くならない。

terraform-docs などで自動生成する入出力表も古くはならないが、AI がコードを読める前提なら置く理由は薄い。

## 逆に、いる文書

いるのは、実態を見ても分からないもの。

- **意図（intent）**：何を実現したいか、成功の条件、やらないこと。
  コードからは「何をしているか」は読めても、「何をするはずだったか」は読めない。
  意図がないと、今の挙動がバグなのか仕様なのか、AI も人も判断できない。
- **なぜ・経緯**：選んだ理由と、検討して捨てた案（ADR）。
  捨てた案はコードに残らないので、書いておかないと同じ案が何度も出てくる。
- **制約**：法令・契約・SLA・セキュリティ要件、触ってはいけないもの。
  システムの外から来る条件なので、実態をいくら読んでも出てこない。
- **業務・用語**：業務の前提、顧客の事情、社内用語の意味。
- **判断基準**：障害時に何を優先するか、どこまでなら自分で決めてよいか。

### intent が言われる理由

AI にコードを書かせると、人が直接書くのは意図のほうになる。
コードは意図から AI が生成するものになるので、人が責任を持って保守するのは意図、という考え方。

仕様を先に書いて AI に実装させる spec-driven development（GitHub の Spec Kit、AWS の Kiro など）や、`AGENTS.md` のような AI 向けの指示ファイルも同じ流れにある。

### 意図の文書はキャッシュではない

意図はコードの上流にあるので、コードとずれていても文書が古いとは限らない。
コードのバグか、意図の改訂漏れのどちらかで、ずれは検知して直す対象になる。

**実態を書き写した文書は要らなくなり、実態の上流にある意図を書くのが人の仕事になる。**

## RAG に読ませるもの

RAG に読ませるなら、キャッシュではなく、実態と、実態から読めないものにする。

- 実態：コード・IaC・設定を AI に直接読ませる
- 実態から読めないもの：意図・なぜ・制約など

キャッシュの文書は、読ませる前に減らす。
オーナーも名乗り出ないページは、[いらないページを消せる状態を作る](いらないページを消せる状態を作る.md) の「消してよいか」の定例に流す。

## 気をつけること

- **AI に実態を読ませるのは、権限を渡すこと。**
  本番の設定やログを読める AI は、それ自体が守る対象になる。
  読み取り専用に絞る、読める範囲を分ける、呼び出しを記録する。
- **監査で文書を求められるものは残る。**
  ISMS のように文書化そのものが要求されるものは、「AI に聞けば分かる」では通らない。
- **実態を読めない相手には書く。**
  社外・契約先・AI の権限を持たない人に渡すものは、書き写すしかない。
  その場合は、渡した時点のスナップショットとして扱う。

## まとめ

- ただの設計やコーディングを人間向け文書に起こしたものは、実質的にキャッシュであり、実態を見ればいいだけ
- 古い社内文書を RAG で読ませるのは、古いキャッシュを読ませているのと同じ
- いるのは実態から読めないもの。中心は意図（intent）で、実態の上流にある意図を書くのが人の仕事になる
