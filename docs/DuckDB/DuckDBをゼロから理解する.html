DuckDB をゼロから理解する

「手元にある大きなファイルをどう集計するか」という手前の話から始め、5 ステップで DuckDB の使いどころまでたどり着きます。

この記事の目的

DuckDB の解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「DuckDB は列指向・ベクトル化実行の組み込み型 OLAP データベースです」という、中級者向けの前提から始まるからです。その一語一語が、どの面倒を消すために出てきたのかが分からないまま、特徴の箇条書きだけが増えていきます。

そこでこの記事は、あえて遠回りします。「大きなファイルをどう集計するか」という、いちばん手前の話から始めて 5 ステップで進みます。ゴールは特徴を暗記することではなく、DuckDB がどの手間をなくした道具なのかを自分の言葉で説明できることです。

この記事の道のり

  1. STEP 1大きなデータの集計で詰まる場所
  2. STEP 2サーバーを立てないデータベース
  3. STEP 3列で持ち、まとめて処理する
  4. STEP 4ファイルをそのままテーブルにする
  5. STEP 5DuckDB として組み立てる

STEP 4 まではすべて前提知識です。本題の DuckDB は STEP 5 だけですが、そこに至る 4 ステップがないと「組み込み型」「列指向」「ファイルを直接クエリ」がばらばらの特徴の暗記になります。

STEP 1：大きなデータの集計で詰まる場所

  1. STEP 1大きなデータの集計で詰まる場所
  2. STEP 2サーバーを立てないデータベース
  3. STEP 3列で持ち、まとめて処理する
  4. STEP 4ファイルをそのままテーブルにする
  5. STEP 5DuckDB として組み立てる

1 か月分のアクセスログが、CSV で 8 GB 手元にあります。「先月いちばん多く叩かれた URL を、日別に上位 10 件出してほしい」と頼まれました。

表計算ソフトで開こうとすると、行数の上限に引っかかるか、そもそも開けません。スクリプトで 1 行ずつ読んで数える方法なら動きますが、数十分かかります。しかも分析は一度で終わりません。「エラーだけに絞って」「先々月と比べて」と条件が変わるたびに、また数十分待つことになります。

やりたいことは、突きつめれば 絞る・まとめる・つなぐ の 3 つです。これは SQL がいちばん短く書ける仕事です。

確認問題 では PostgreSQL を 1 台立ててこの CSV を取り込めば、問題は解決するでしょうか。

答えを見る

解決はします。ただし割に合いません。 この分析のためだけにサーバーを用意し、8 GB を取り込む時間をかけ、来月また別のファイルで同じことをやります。使いたいのは SQL であって、サーバーの運用ではありません。「SQL は使いたいが、サーバーは立てたくない」——これが次の話です。

STEP 2：サーバーを立てないデータベース

  1. STEP 1 ✓大きなデータの集計で詰まる場所
  2. STEP 2サーバーを立てないデータベース
  3. STEP 3列で持ち、まとめて処理する
  4. STEP 4ファイルをそのままテーブルにする
  5. STEP 5DuckDB として組み立てる

PostgreSQL や MySQL はサーバー型です。データベースは常駐するプロセスとして動き、こちらは接続してから SQL を送ります。データはそのサーバーの管理下にあるので、使う前に必ず取り込みが要ります。複数人・複数アプリで同じデータを共有するには理にかなった形ですが、1 人が手元のファイルを集計したいだけなら重い仕組みです。

もう一つの形が組み込み型です。データベースがライブラリとして、こちらのプログラムと同じプロセスの中で動きます。接続先はホスト名ではなくファイルパス（あるいはメモリ上だけの一時的な領域）です。先例は SQLite で、DuckDB も同じ形をとります。

pip install duckdb して import duckdb と書いた瞬間、データベースエンジンは自分のプロセスの中にいます。コマンドラインで使う場合も、依存関係のない実行ファイルが 1 つあるだけです。

確認問題 組み込み型でよいのなら、すでにある SQLite を使えば済むのではないでしょうか。

答えを見る

済みません。得意な仕事が違います。 SQLite は「1 件の行を読む・書く」処理のために作られています。1 億行の合計を出すような集計を投げると、極端に時間がかかります。同じ組み込み型でありながら中身がまったく違う——その違いが次のステップです。

STEP 3：列で持ち、まとめて処理する

  1. STEP 1 ✓大きなデータの集計で詰まる場所
  2. STEP 2 ✓サーバーを立てないデータベース
  3. STEP 3列で持ち、まとめて処理する
  4. STEP 4ファイルをそのままテーブルにする
  5. STEP 5DuckDB として組み立てる

集計のクエリには、はっきりした癖があります。行はほぼ全部見るのに、列はごく一部しか見ないということです。SELECT path, count(*) FROM logs GROUP BY path は、30 列あるテーブルの 1 列しか使いません。

ところが行指向のデータベースは、1 行分をひとかたまりにして置きます。1 列だけ欲しくても、行ごと読むしかありません。列指向は逆に、同じ列の値をまとめて置きます。必要な列だけを読めるうえ、同じ列は値の傾向がそろうので圧縮もよく効きます。

速さの理由はもう一つあります。DuckDB は 1 行ずつ処理を進めるのではなく、数千行を 1 かたまり（ベクトル）にして処理します。既定では 2048 行単位です。1 行ごとに関数を呼び出す形に比べて、呼び出しの手間や条件分岐が激減し、CPU のキャッシュにも載りやすくなります。

この「列で持つ」「かたまりで処理する」の 2 つが、同じ SQL でも桁違いに速くなる中身です。1 件ずつの読み書きに強い OLTP 型（SQLite や PostgreSQL の主戦場）に対して、集計に強い OLAP 型がここにあたります。

確認問題 列指向で速くなるのは分かりました。では 8 GB の CSV を DuckDB のデータベースファイルに取り込めば、STEP 1 の悩みは解決するでしょうか。

答えを見る

半分だけ解決します。 集計は速くなりますが、「取り込む」という工程が残っています。一度きりの集計のために取り込みを待つのは、STEP 1 で PostgreSQL を立てるのが割に合わなかったのと同じ理由で面倒です。次のステップが、この工程そのものを消します。

STEP 4：ファイルをそのままテーブルにする

  1. STEP 1 ✓大きなデータの集計で詰まる場所
  2. STEP 2 ✓サーバーを立てないデータベース
  3. STEP 3 ✓列で持ち、まとめて処理する
  4. STEP 4ファイルをそのままテーブルにする
  5. STEP 5DuckDB として組み立てる

DuckDB では、CSV・Parquet・JSON といったファイルをテーブル名の位置にそのまま書けます。STEP 1 の依頼は、取り込みなしでこう書けます。

SELECT path, count(*) AS hits
FROM 'logs/2026-08-*.csv'
GROUP BY path
ORDER BY hits DESC
LIMIT 10;

拡張子から読み方が決まり、CSV なら区切り文字・ヘッダの有無・各列の型が推測されます。* を使えば複数ファイルがまとめて 1 つのテーブルになります。読むのは必要な列と行だけで、Parquet ならファイル内の統計情報を見て不要な部分を飛ばします。

Python から使う場合は、メモリ上の DataFrame も同じくテーブル名として書けます。渡す・変換するという手順がありません。

import duckdb, pandas as pd

df = pd.read_csv("sales.csv")
duckdb.sql("SELECT region, sum(amount) FROM df GROUP BY region").df()

書き出しも SQL のままです。COPY (SELECT ...) TO 'summary.parquet' (FORMAT parquet) と書けば、集計結果をそのまま次の処理に渡せる形で保存できます。

確認問題 ファイルを直接読めるなら、DuckDB のデータベースファイル（.duckdb）は何のためにあるのでしょうか。

答えを見る

同じデータを何度も使うときのためです。 データベースファイルに入れておけば、列指向で圧縮され統計情報も付いた形で持てるので、繰り返しのクエリはさらに速くなります。ビューや複数テーブルの関係もそこに保存できます。一度きりの集計はファイル直読み、何度も使うなら取り込む、という使い分けになります。

STEP 5：DuckDB として組み立てる

  1. STEP 1 ✓大きなデータの集計で詰まる場所
  2. STEP 2 ✓サーバーを立てないデータベース
  3. STEP 3 ✓列で持ち、まとめて処理する
  4. STEP 4 ✓ファイルをそのままテーブルにする
  5. STEP 5DuckDB として組み立てる

ここまでの 3 つを重ねると、DuckDB の姿になります。自分のプロセスの中で動き（STEP 2）、列指向とベクトル化で集計が速く（STEP 3）、手元のファイルや DataFrame をそのままテーブルとして扱える（STEP 4） SQL エンジンです。オープンソースで、コマンドライン・Python・R・Java・ブラウザ（WebAssembly）など、いろいろな場所に同じエンジンが載ります。

実際の作業は、だいたいこの流れになります。

1 手元や S3 のファイルを FROM に書いて、まず LIMIT 5 で中身を確かめる
2 絞る・まとめる・つなぐを SQL で書き、条件を変えながら試す
3 結果を DataFrame で受け取るか、Parquet に書き出して次の処理へ渡す

SQL の書き味にも工夫があります。SELECT * EXCLUDE (password) で列を除いたり、GROUP BY ALL で集計キーの書き写しを省いたりできます。標準 SQL の範囲を超えた便利な構文が用意されているので、試行錯誤の 1 回あたりが短くなります。

そして、向く場面と向かない場面がはっきりしています。ここが実務でいちばん効く判断材料です。

場面向くか理由
手元や S3 の大きなファイルを集計・変換する向く準備なしで SQL が書ける。ここが本領
データ処理バッチの前処理、CI でのデータ検証向く実行環境に入れるものが 1 つで済む
多人数が同時に読み書きする業務アプリの DB向かない1 つのデータベースファイルに書き込めるプロセスは同時に 1 つ
1 件の更新が毎秒何千件も走る処理向かない集計向けの設計で、行単位の更新は得意ではない

置き換える対象を間違えない。 DuckDB が置き換えるのは、業務アプリのデータベースではありません。「分析のためだけに立てていた DB」や「遅い前処理スクリプト」のほうです。

確認問題 メモリが 16 GB のノート PC で、100 GB の Parquet を集計できるでしょうか。

答えを見る

条件しだいで、できることが多いです。 必要な列と行だけを読む仕組み（STEP 3・STEP 4）が効くので、100 GB のうち実際に読む量はずっと小さくなります。かたまり単位で処理し、足りなければディスクに退避しながら進めます。ただし何でも通るわけではなく、巨大な結合などは限界に当たります。そこから先は分散処理エンジンの領域です。

まとめ：そのまま使える説明テンプレート

30 秒版

DuckDB は、集計に特化したオープンソースのデータベースです。いちばんの特徴はサーバーを立てないこと。ライブラリとしてアプリと同じプロセスの中で動くので、インストールしたらすぐ SQL が書けます。中身は列指向で、数千行をまとめて処理するので集計が速い。しかも CSV や Parquet をそのままテーブルとして FROM に書けるため、取り込みの工程が要りません。手元の大きなファイルを SQL で集計したいとき用の道具です。

2 分版（30 秒版に足す分）

背景にあるのは、「SQL は使いたいが、そのためにサーバーを立てて取り込む手間は払いたくない」という場面です。組み込み型という形はそこを解きます。先例の SQLite と同じ形ですが、SQLite は 1 件ずつの読み書き（OLTP）向けで、集計は苦手です。

DuckDB はそこを OLAP 向けに作り替えています。データを列ごとにまとめて置くので、30 列のうち 1 列しか使わない集計では 1 列分しか読みません。処理も 1 行ずつではなく 2048 行のかたまり単位で進めます。この 2 つで集計が桁違いに速くなります。

さらに読み先が自由です。ローカルのファイル、S3 上のファイル、メモリ上の DataFrame、DuckDB 自身のデータベースファイルを同じ SQL で扱えます。一方で、1 つのデータベースファイルに書き込めるプロセスは同時に 1 つなので、多人数が同時に更新する業務アプリの DB としては使いません。置き換わるのは分析用に立てていた DB や、遅い前処理スクリプトのほうです。

よくある誤解

「SQLite の新しい版のようなもので、置き換えられる」

形（組み込み型）は同じですが、想定する仕事が逆です。SQLite は 1 件ずつの読み書き、DuckDB は大量行の集計に向いています。アプリの設定や履歴を保存する用途なら SQLite のままが適切です。

「大きなデータを扱うのだからクラスタが要る」

DuckDB は 1 台のマシンで動きます。数十 GB 規模なら、分散エンジンを立てるより手元の 1 台で済ませたほうが速く、簡単です。分散が必要になるのはもっと先です。

「使う前にデータを取り込む必要がある」

取り込みは選択肢の一つであって、必須ではありません。ファイルをそのまま FROM に書けます。何度も同じデータを使うときだけ、取り込んだほうが得になります。
