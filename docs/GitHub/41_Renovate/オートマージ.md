# Renovate のオートマージ

## 何が起きるか

`automerge: true` を付けた更新は、Renovate が PR を作り、チェックが全部成功したらマージする。
1 つでも失敗したらマージせず、普通の PR として残る（このとき初めてレビュアーやアサインが付く）。

PR 本文に「Automerge: Enabled」と出ていれば、設定は効いている。

## マージを判断するのは誰か

| 経路 | 条件 | 何を見てマージするか | いつ |
|---|---|---|---|
| GitHub の auto-merge | `platformAutomerge: true`（既定）かつリポジトリの「Allow auto-merge」が有効 | ブランチ保護の必須チェックだけ | 必須チェックが通った直後 |
| Renovate 自身 | 上のどちらかが無効 | ブランチの全チェック | 次の Renovate の実行時（1 回で 1 本ずつ） |

GitHub の auto-merge は必須チェックしか見ない。
ブランチ保護で必須チェックを設定していないと、CI が走り終わる前や失敗していてもマージされうる。
Renovate のドキュメントでも、`platformAutomerge` を使うなら「Require status checks before merging」を有効にするよう書かれている。

Renovate 自身がマージする場合は、マージ前にブランチがベースに追いついている必要があり、1 回の実行で 1 本しかマージしない。
数時間かかるのは正常。

## チェックがないとマージされない

Renovate は、ステータスチェックが成功していることを確認してからマージする。
チェックが 1 つもないと成功を確認できないので、いつまでもマージしない。

テストがなくてもマージさせたいなら `ignoreTests: true` を入れるが、壊れた更新がそのまま main に入る。

paths で絞ったワークフローも同じで、走らなかったチェックは「成功」にならない。
ブランチ保護の必須チェックに入れていると、GitHub の auto-merge も永久に待つ。

## minimumReleaseAge との組み合わせ

`minimumReleaseAge: "3 days"` を付けると、公開から 3 日経つまで `renovate/stability-days` が pending になる。
既定の `internalChecksFilter: "strict"` では、待ち期間を過ぎるまでブランチも PR も作られない。

GitHub の auto-merge は PR を作った時点で仕掛けられ、`renovate/stability-days` は必須チェックではない。
それでも PR 自体が待ち期間後にしか作られないので、先走ってマージされることはない。

サプライチェーン攻撃で乗っ取られたバージョンは、数日以内に見つかって取り下げられることが多い。
オートマージするなら、待ち期間を付けておくと「公開直後の悪いバージョンを無人で取り込む」事故を減らせる。
`config:best-practices` が入れる 3 日待ちは npm だけなので、ほかのデータソースには自分で付ける。

## 待ち期間が効かない更新がある

`minimumReleaseAge` は、データソースが返す公開日時を見ている。
その日時が攻撃者に書き換えられる、または古いまま変わらない更新では、待ち期間は素通りになる。

GitHub Actions（`github-tags` データソース）の公開日時は、タグが指すコミットの日時か annotated tag の日時。
GitHub Release があれば、その公開日時と比べて新しいほうを使う。
コミットの日時は push する側が自由に決められる。

2026 年 3 月の `aquasecurity/trivy-action` の侵害では、既存のバージョンタグのほとんどが悪性コミットに付け替えられた。
コミットの日付は 2021 年などに偽装され、バージョン番号は変わっていない。
Renovate から見ると、これは「同じバージョンでコミットだけ変わった」digest 更新になる。
公開日時は元のタグ（か元の Release）のままなので、3 日待ちはすでに過ぎている扱いになる。

つまり digest 更新をオートマージしていると、付け替えられたタグを公開直後に無人で取り込む。
SHA でピンしていても、ピンを書き換える PR を自動でマージしたら意味がない。

## このリポジトリの方針：自動マージしない

このリポジトリでは自動マージを使わず、`renovate.json` で `automerge: false` にしている。
Terraform が主で、CI で見ているのは `terraform fmt` 程度しかない。
チェックが緑でも動く保証にならないうえ、main は HCP Terraform が auto apply するので、マージがそのまま本番への反映になる。

代わりに、PR ごとに当番を 1 人アサインして、その人が目視でレビューしてマージする。
しくみと Slack の設定は [当番制とSlack通知](当番制とSlack通知.md)。

以前は `hands-on/**` と、ワークフローの action・lint ツールの minor / patch を自動マージしていた。
いまは待ち期間（公開から 3 日）だけ残し、マージは当番がする。

digest 更新の PR が来たら、メンテナが意図して付け直したのか、リリースノートやアドバイザリで確かめる。
理由が見つからなければマージしない。
PR には `security` ラベルと確認点が付く。

minor / patch でも、Release を作らずにタグだけ打つ action は、偽装したコミット日時がそのまま公開日時になる。
3 日待ちは「Release を作る action なら効く」くらいの守りと考える。
`permissions` を最小にして、ワークフローに渡すシークレットを絞るのが本命の対策。
