Go をゼロから理解する

「書いたプログラムは、相手のマシンでどうやって動くのか」から始めて、5 ステップで「Go とはどういう言語なのか」までたどり着きます。

この記事の目的

Go の入門記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの入門記事は「goroutine が軽量」「例外がない」「インタフェースは暗黙的に実装される」といった他の言語との差分の一覧から始まります。一つ一つの説明は正しいのに、読み終わっても「で、なぜこの言語を選ぶのか」「なぜこんな作りになっているのか」が残ります。Go の機能はほとんどが 1 つの目的から出ているのに、その目的が先に説明されないからです。

そこでこの記事は、あえて遠回りします。「プログラムが相手のマシンで動くまでに何が要るのか」というところから始めて、5 ステップで Go の全体像までたどり着きます。ゴールは文法を覚えることではなく、Go を自分の言葉で説明できるようになることです。最後に、そのまま口に出せる説明テンプレートを用意しました。

この記事の道のり

  1. STEP 1動くまでに要るもの
  2. STEP 21 個のファイルになる
  3. STEP 3読める状態を強制する
  4. STEP 4同時に動かす
  5. STEP 530 行のサーバ

STEP 4 までは「Go がどんな問題を解こうとしている言語なのか」の話です。通しのコードが出てくるのは STEP 5 だけですが、そこに至る 4 ステップがないと、なぜ Go のコードがあの書き方になっているのかが分かりません。逆に言えば、STEP 4 まで進めば STEP 5 は部品を並べるだけに感じられるはずです。

STEP 1：プログラムは、相手のマシンでどうやって動くのか

  1. STEP 1動くまでに要るもの
  2. STEP 21 個のファイルになる
  3. STEP 3読める状態を強制する
  4. STEP 4同時に動かす
  5. STEP 530 行のサーバ

手元で動いたスクリプトを同僚に渡したら動かなかった、という場面があります。処理系のバージョンが違う、ライブラリを入れていない、OS が違う。原因はばらばらに見えますが、根っこは 1 つです。「ソースコードを渡す」という行為が、相手のマシンに処理系と依存ライブラリが揃っていることを前提にしているからです。

もう 1 つの道があります。あらかじめ CPU が直接実行できる形に変換した実行ファイルを作って、それを渡す方法です。この変換がコンパイルで、Go はこちら側の言語です。

確認問題 「自分の PC では動くのに、相手の PC では動かない」を避けるために、①の方式で配る側ができることは何でしょうか。

答えを見る

バージョンを指定した手順書を書く、依存ライブラリの一覧を添える、仮想環境を使ってもらう——どれも「相手に正しく準備してもらう」お願いです。準備を相手任せにしないところまで踏み込んだのが、環境ごと箱に詰める コンテナです。

ここで別の解き方もあります。準備するものを、そもそも無くしてしまうという方向です。次のステップはここから始まります。

STEP 2：go build は「1 個のファイル」を吐く

  1. STEP 1 ✓動くまでに要るもの
  2. STEP 21 個のファイルになる
  3. STEP 3読める状態を強制する
  4. STEP 4同時に動かす
  5. STEP 530 行のサーバ

Go のプログラムは、こう書きます。

// hello.go
package main        // main パッケージ ＝ 実行できるプログラム、という印

import "fmt"        // 使うものだけを明示的に読み込む

func main() {       // main 関数から始まる
	fmt.Println("hello")
}
$ go run hello.go     # ビルドして即実行（手元での確認用）
hello

$ go build hello.go   # 実行ファイルを作る
$ ./hello
hello

できた hello は、hello と表示するだけのプログラムなのに 1〜2 MB あります。太っているのではなく、動くのに必要なものが全部中に入っているからです。あなたのコード、使った標準ライブラリ、そして Go のランタイム（メモリを自動で回収する GC や、STEP 4 で出てくるスケジューラ）。これを 1 つにまとめることを静的リンクと呼びます。渡された側に Go は要りません。

これはコンテナの作り方にも効きます。ビルド用のイメージで実行ファイルを作り、それを空っぽのイメージにコピーするだけで動きます。

FROM golang:1 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app .

FROM scratch          # OS のファイルが 1 つも入っていないイメージ
COPY --from=build /app /app
ENTRYPOINT ["/app"]

例外：C のライブラリを呼び出す機能（cgo）を使うと、実行ファイルはシステムのライブラリに依存します。上の CGO_ENABLED=0 はそれを明示的に切って、完全に自己完結した 1 ファイルにするための指定です。

確認問題 配布が 1 ファイルで済むのは分かりました。では、配布さえ解決するなら、書く言語は何でもよいのではないでしょうか。

答えを見る

配布だけを見ればそうです。しかしコードは、書いたあとも人が読み、直し続けるものです。Go が Google で作られた動機は、速いプログラムを書くことよりも、大量のコードを大人数で触り続けても壊れない状態を保つことにありました。

そこで言語側に仕掛けが入ります。次のステップはその話です。

STEP 3：読める状態を、言語とツールが強制する

  1. STEP 1 ✓動くまでに要るもの
  2. STEP 2 ✓1 個のファイルになる
  3. STEP 3読める状態を強制する
  4. STEP 4同時に動かす
  5. STEP 530 行のサーバ

他人が書いたコードを読むときに時間を食うのは、たいていロジックそのものではありません。「この変数には何が入るのか」「この書き方は流儀なのか意味があるのか」「この処理はどこで失敗して、失敗したらどこへ行くのか」です。Go はこの 3 つを書き手の心がけではなく、言語とツールで潰しに行きます。

① 型は必ず決まっている

変数や関数の引数・戻り値の型はコンパイル時に確定します。毎回書くのは面倒なので、:= で初期値から推論させます。推論であって、動的型ではありません。

name := "prod"          // string と決まる（あとから数値は入らない）
count := 0              // int と決まる
var timeout time.Duration = 5 * time.Second   // 明示して書くこともできる

func lookup(id string, retry int) (string, error) { ... }
// ↑ この 1 行が、そのまま「何を渡すと何が返るか」の仕様になる

② 書式に流儀を持ち込ませない

インデント、改行位置、括弧の付け方は gofmt（go fmt）が機械的に 1 つの形へ直します。設定項目はほぼありません。「どう書くか」がレビューの議題にならないので、レビューは中身の話だけになります。

③ 中途半端な状態をコンパイラが通さない

使っていない変数、使っていない import は警告ではなくエラーです。ビルドが通りません。

./main.go:4:2: declared and not used: count

④ 失敗は、戻り値として受け取る

Go には例外（try / catch）がありません。失敗しうる関数は、結果と一緒に error というただの値を返します。呼び出した側は、その場で確かめます。

func readConfig(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		// %w で「元の失敗」を包んだまま、文脈を足して返す
		return nil, fmt.Errorf("設定ファイルを開けません: %w", err)
	}
	defer f.Close()   // この関数を抜けるとき、どの経路でも必ず閉じる

	return io.ReadAll(f)
}

確認問題 if err != nil が 3 回も 4 回も続くのは、単に冗長なだけではないでしょうか。

答えを見る

冗長です。Go 自身もそれを認めたうえで採用しています。得られるのは、失敗しうる箇所が省略できない行として全部見えること。例外方式では、書く量は減る代わりに「この行から飛ぶかどうか」が読んでも分かりません。

なお、想定外の状態（プログラムの前提が壊れた場合など）には panic もあります。ただし日常的な失敗は error で返すのが Go の流儀です。

ここまでで「失敗の扱い」は分かりました。では、失敗はしないが時間がかかる処理——たとえば 100 台のサーバに HTTP を投げる——はどうでしょう。1 回 200 ミリ秒なら、順番にやると 20 秒です。次のステップはここです。

STEP 4：同時に動かす

  1. STEP 1 ✓動くまでに要るもの
  2. STEP 2 ✓1 個のファイルになる
  3. STEP 3 ✓読める状態を強制する
  4. STEP 4同時に動かす
  5. STEP 530 行のサーバ

HTTP のリクエストやデータベースへの問い合わせは、ほとんどの時間が待ちです。待っている間に次を投げられれば、全体は待ち時間の一番長いものとほぼ同じで終わります。

Go では、関数呼び出しの前に go を付けるだけで別の流れとして走り出します。これが goroutine です。結果の受け渡しには channel を使います。

func check(urls []string) {
	ch := make(chan string)        // 文字列を運ぶ channel

	for _, u := range urls {
		go func(u string) {        // go を付けた ＝ ここは別の流れになる
			resp, err := http.Get(u)
			if err != nil {
				ch <- u + " : NG"   // channel へ送る
				return
			}
			defer resp.Body.Close()
			ch <- fmt.Sprintf("%s : %d", u, resp.StatusCode)
		}(u)
	}

	for range urls {
		fmt.Println(<-ch)          // 終わったものから受け取る
	}
}

goroutine は OS のスレッドではありません。数 KB のスタックで始まり、足りなくなれば伸びます。数万個作っても破綻しないのは、Go のランタイムが少数の OS スレッドに載せ替えながら動かしているからです。ある goroutine が通信の待ちに入ったら、その隙に別の goroutine をスレッドへ載せます。

確認問題（考察） channel を使わず、複数の goroutine から同じ map に直接結果を書き込んだら何が起きるでしょうか。

答えを見る

データ競合が起きます。Go の map は同時書き込みを検知すると実行時にプログラムを落とします。運が悪いと、テストでは通って本番の負荷で初めて落ちます。

Go にはこれを検出する道具が標準で付いています。go test -race / go run -race を付けると、競合したアクセスを実行時に報告します。直し方は、channel で渡すか、sync.Mutex で守るかです。

これで部品は揃いました。最後に、全部が同時に出てくるプログラムを 1 本見ます。

STEP 5：30 行のサーバに、ここまでの全部が出てくる

  1. STEP 1 ✓動くまでに要るもの
  2. STEP 2 ✓1 個のファイルになる
  3. STEP 3 ✓読める状態を強制する
  4. STEP 4 ✓同時に動かす
  5. STEP 530 行のサーバ

HTTP サーバを立てます。追加のライブラリは 1 つも入れません。net/http は標準ライブラリです。

// main.go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/hello", func(w http.ResponseWriter, r *http.Request) {
		name := r.URL.Query().Get("name")
		if name == "" {
			http.Error(w, "name is required", http.StatusBadRequest)
			return
		}
		fmt.Fprintf(w, "hello, %s\n", name)
	})

	log.Println("listening on :8080")
	log.Fatal(http.ListenAndServe(":8080", nil))   // 戻り値はいつも error
}
$ go mod init example.com/hello   # モジュールを作る（go.mod ができる）
$ go build -o app .               # 実行ファイル 1 個
$ ./app

このプログラムには、ここまでの 4 ステップがそのまま入っています。

コードの中の要素対応する話
go build -o app . の出力 1 個STEP 2：静的リンク。コンテナにも scratch で入る
func(w http.ResponseWriter, r *http.Request)STEP 3：型が決まっている。ハンドラの形が仕様になる
log.Fatal(http.ListenAndServe(...))STEP 3：失敗は例外ではなく戻り値の error
同時に来たリクエストが並行に処理されるSTEP 4：接続ごとに goroutine が立つ

周りの道具も標準で付いてくる

Go は言語だけでなく、開発に要る道具が最初から同梱されています。何を入れるかを選ぶ手間が小さい、というのが実務での効き方です。

  • 依存管理：go mod init で go.mod を作り、go get で追加します。使ったバージョンとハッシュが go.mod / go.sum に記録されます
  • テスト：xxx_test.go を置いて go test ./...。テストフレームワークを選ぶ必要がありません
  • 静的チェック：go vet（怪しい書き方の検出）、go test -race（データ競合の検出）
  • 互換性：Go 1 互換性の約束により、Go 1 系で書いたコードは以降のバージョンでもビルドできることが方針として掲げられています

なぜインフラ系のツールは Go で書かれているのか

Docker、Kubernetes、Terraform、Prometheus——これらが揃って Go なのは偶然ではありません。①配るのは 1 ファイルでよく、②ネットワーク待ちの並行処理が中心で、③多人数が長期間触り続ける。この 3 つが重なる領域で、Go はほぼそのまま答えになっています。

確認問題（考察） では逆に、Go を選ばないほうがよい場面はどこでしょうか。

答えを見る

たとえばデータ分析や機械学習です。ライブラリの層の厚さで Python に勝てません。また、GC の一時停止すら許されない極限の低レイテンシ処理や、メモリを細かく制御したい領域では C / C++ / Rust が候補になります。数行で済む書き捨ての自動化も、シェルや Python のほうが素直です。

Go が効くのは、長く動かすサーバ、配布する CLI、複数人で触り続けるコード。STEP 1 から積み上げてきた通り、言語の設計自体がそこに向いています。

まとめ：そのまま使える説明テンプレート

30 秒版

Go は、ビルドすると依存を全部含んだ実行ファイル 1 個ができるコンパイル言語です。相手のマシンに処理系もライブラリも要りません。文法は意図的に小さく、書式は gofmt が統一し、使っていない変数はコンパイルエラーになります。そして go を付けるだけで並行処理が書けます。「大人数で長く触るサーバやツールを、確実にビルドして配る」ための言語です。

2 分版（30 秒版に足す分）

実行ファイルには標準ライブラリとランタイム（GC・スケジューラ）まで入るので、FROM scratch のコンテナでも動きます。GOOS と GOARCH を変えれば、Mac の手元から Linux の ARM 向けも作れます。

例外はありません。失敗しうる関数は結果と error を並べて返し、呼び出し側は if err != nil でその場で分岐します。行数は増えますが、失敗しうる箇所と失敗後の行き先がコード上に必ず現れます。

並行処理の単位は goroutine で、OS スレッドではありません。数 KB から始まり、ランタイムが少数の OS スレッドに載せ替えるので数万個動かせます。値の受け渡しは channel を使い、共有変数を奪い合わない形にします。競合は -race で検出できます。

よくある誤解

「Go は速い言語」

何が速いのかを分けて考える必要があります。コンパイルは速く、起動も速く、待ちの多い並行処理は書きやすい。一方で実行速度そのものは、GC がある以上 C や Rust に及ばない場面があります。Go の「速さ」の実感は、実行時間よりビルドから配布までが速いことから来ていることが多いです。

「goroutine はスレッドの別名」

別物です。OS スレッドは 1 つ作るのに MB 単位のスタックを取りますが、goroutine は数 KB から始まり、ランタイムがスレッドに載せ替えます。ただし無限ではありません。goroutine を作った分だけメモリは増えますし、相手側の同時接続数やファイルディスクリプタの上限は別途効きます。

「シンプル ＝ 機能が少ないから簡単」

Go のシンプルさは「入門しやすくするための引き算」ではなく、書き手の自由度を削って読み手の負担を下げる設計判断です。ジェネリクスが長く入らなかったのも、書式に設定項目がないのも同じ思想の表れです。「便利な書き方がない」と感じたときは、たいてい意図的に外されています。

次の一歩

この記事では意図的に触れなかった話です。

  • メソッドとインタフェース：Go のインタフェースは「実装します」と宣言せず、必要なメソッドが揃っていれば満たされます。テストで差し替える設計の土台になります
  • 値・ポインタ・スライス・map：代入や関数呼び出しで何がコピーされるのか。初学者がつまずく場所はだいたいここです
  • context：リクエストのキャンセルやタイムアウトを goroutine の連なり全体に伝える仕組み
  • ジェネリクス：型を引数として受け取る関数・型の書き方
  • テストの型：入力と期待値を並べて回す table driven test という定番の書き方
  • 手を動かす場合：A Tour of Go（ブラウザだけで一通り触れる）→ Go by Example（やりたいことから逆引き）→ Effective Go（書き方の作法）の順が入りやすいです
