Helm をゼロから理解する

「Kubernetes にアプリを入れるとは YAML を何枚も適用することだ」というところから始めて、5 ステップで「helm upgrade の 1 回で何が起きているのか」までたどり着きます。

この記事の目的

Helm の解説を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「Kubernetes のパッケージマネージャです」から始まり、チャート・テンプレート・リリース・リポジトリという用語が一気に並びます。それぞれの説明は正しいのに、読み終わっても「結局 kubectl apply と何が違うのか」「クラスタ側に何が増えたのか」が残ります。土台がひとつ抜けているからです。

そこでこの記事は、あえて遠回りします。「Kubernetes にアプリを入れるとは、そもそも何をすることか」から始めて、5 ステップで Helm の全体像までたどり着きます。ゴールは用語を覚えることではなく、Helm を自分の言葉で説明できるようになることです。最後に、そのまま口に出せる説明テンプレートを用意しました。

この記事の道のり

  1. STEP 1YAML が散らばる
  2. STEP 2穴あきにして値を外に出す
  3. STEP 3チャートという 1 つの箱
  4. STEP 4入れた事実を記録する
  5. STEP 5upgrade 1 回の中身

STEP 4 まではすべて「まとまりをどう作るか」の話です。実際のコマンドの中身が出てくるのは STEP 5 だけですが、そこに至る 4 ステップがないと、なぜ Helm が「テンプレートエンジン」でも「デプロイスクリプト」でもなく両方なのかが分かりません。

STEP 1：Kubernetes にアプリを入れるとは、YAML を何枚も適用すること

  1. STEP 1YAML が散らばる
  2. STEP 2穴あきにして値を外に出す
  3. STEP 3チャートという 1 つの箱
  4. STEP 4入れた事実を記録する
  5. STEP 5upgrade 1 回の中身

Web アプリを 1 つ動かすだけでも、Kubernetes に書くものは 1 枚では済みません。Pod を並べる Deployment、宛先になる Service、設定を渡す ConfigMap、外から入れるための Ingress。それぞれが独立したオブジェクトで、kubectl apply -f で 1 枚ずつ送り込みます。

確認問題 「このアプリ、もう要らないので消しておいて」と頼まれました。クラスタを見て、消すべきものが分かりますか。

答えを見る

確実には分かりません。ラベルや名前の規則を手がかりに探すことはできますが、それは人間の運用ルールであってクラスタが保証しているものではありません。誰かが途中で足した Secret や CronJob は、規則から外れていれば取り残されます。

つまり足りないのは「一式」という単位です。ではその単位を作るとして、環境ごとに違う値はどう扱えばよいでしょうか。次のステップはここから始まります。

STEP 2：穴あきにして、値を外に出す

  1. STEP 1 ✓YAML が散らばる
  2. STEP 2穴あきにして値を外に出す
  3. STEP 3チャートという 1 つの箱
  4. STEP 4入れた事実を記録する
  5. STEP 5upgrade 1 回の中身

同じアプリを dev・staging・本番に置くと、YAML のセットが 3 つに増えます。ところが中身を見比べると、違うのはレプリカ数・イメージのタグ・ホスト名など数行だけです。残りは完全な複製で、共通部分を直すたびに 3 箇所を直すことになります。

そこで、変わる部分を穴にして、値を別ファイルに出します。穴あきの YAML をテンプレート、埋める値をvalues と呼びます。Helm のテンプレートは Go のテンプレート構文で、{{ .Values.〜 }} がその穴です。

確認問題 テンプレートと値を分けました。これで「アプリ一式を他のチームに渡す」ことはできるようになったでしょうか。

答えを見る

まだです。渡された側は「どのファイルがこのアプリの一部か」「どの値を指定できるのか」「これはバージョンいくつなのか」が分かりません。テンプレート群と既定値とメタ情報を、ひとつの決まった形に収める必要があります。

その決まった形が、次のステップで出てくるチャートです。

STEP 3：チャート＝配れる 1 つの箱

  1. STEP 1 ✓YAML が散らばる
  2. STEP 2 ✓穴あきにして値を外に出す
  3. STEP 3チャートという 1 つの箱
  4. STEP 4入れた事実を記録する
  5. STEP 5upgrade 1 回の中身

チャートは、テンプレート・既定値・メタ情報を決まった構造に収めたディレクトリです。構造が決まっているから、中身を知らなくても「これは Helm のチャートだ」と分かり、圧縮して配れて、バージョンを付けられます。

チャートはリポジトリから取ってきて使うこともできます。helm repo add で HTTP のリポジトリを登録するか、OCI レジストリ（コンテナイメージと同じ置き場）から oci:// で直接引きます。他人が作った ingress-nginx や external-secrets を入れる、という使い方が実務では最初の接点になります。

Terraform を使っているなら、ほぼモジュールと同じものだと考えて差し支えありません。チャートがモジュール、values が variables、Helm リポジトリや OCI レジストリが Terraform Registry です。バージョンを固定して取り込み、入力値だけ差し替えて使い回す、という付き合い方もそのままです。

違うのは状態の持ち方です。Terraform は tfstate をどこに置くか自分で決めますが、Helm は次のステップで見るとおり、前回送った内容をクラスタ内に自動で貯めます。また terraform plan に当たる標準コマンドはなく、helm template で生成結果を読むか helm-diff プラグインを足すことになります。

確認問題 helm install したあと kubectl get deployment で見えるのは、普通の Deployment ですか。それとも Helm 専用の何かですか。

答えを見る

普通の Deployment です。Helm がやったのは、穴を埋めた YAML を API サーバに送ることだけ。できあがるものは手書きの YAML を kubectl apply した場合と変わりません。

では、クラスタは「この一式を Helm が入れた」ことをどこで覚えているのでしょうか。覚えていなければ、アンインストールもロールバックもできないはずです。次のステップはここです。

STEP 4：入れた事実を、クラスタに記録する

  1. STEP 1 ✓YAML が散らばる
  2. STEP 2 ✓穴あきにして値を外に出す
  3. STEP 3 ✓チャートという 1 つの箱
  4. STEP 4入れた事実を記録する
  5. STEP 5upgrade 1 回の中身

チャートをクラスタに入れたものをリリースと呼びます。リリースには名前があり、helm install myapp ./myapp の myapp がそれです。同じチャートから名前違いのリリースをいくつでも作れます。

そして Helm は、install / upgrade のたびに「そのとき送ったマニフェストと使った値の一式」を Secret としてクラスタに保存します（sh.helm.release.v1.<リリース名>.v<番号>）。この番号がリビジョンです。STEP 1 で足りなかった「まとまりの単位」は、この記録として実現されています。

確認問題 helm upgrade したら、前まであった Ingress がクラスタから消えていました。バグでしょうか。

答えを見る

バグではなく、仕様どおりの動きです。Helm は前のリビジョンのマニフェストと今回のマニフェストを比べ、今回生成されなかったものを削除します。values で ingress.enabled: false になっていた、といったことが起きています。

kubectl apply -f にはこの挙動がありません。ファイルを消しても、クラスタ上のオブジェクトは残ったままです。この差が、Helm が「まとまりを管理している」ことの具体的な中身です。

では、その比較と適用は 1 回のコマンドの中でどういう順番で起きるのでしょうか。最後のステップで通して見ます。

STEP 5：helm upgrade --install の 1 回で何が起きるか

  1. STEP 1 ✓YAML が散らばる
  2. STEP 2 ✓穴あきにして値を外に出す
  3. STEP 3 ✓チャートという 1 つの箱
  4. STEP 4 ✓入れた事実を記録する
  5. STEP 5upgrade 1 回の中身

ここまでの部品がそろったので、実際に打つコマンドを 1 本見ます。upgrade --install は「無ければ入れる、有れば上げる」という書き方で、CI から何度流しても同じ結果になるためよく使われます。

helm upgrade --install myapp ./myapp \
  -f values-prod.yaml \
  --set image.tag=1.4.1 \
  -n myapp --create-namespace

②の結果はクラスタに触らずに確認できます。他人のチャートを初めて入れるときは、まずこれを読むのが安全です。

helm template myapp ./myapp -f values-prod.yaml | less

CRD だけは例外です。チャートの crds/ に置かれた CustomResourceDefinition は、インストール時に作られるだけで、upgrade でも uninstall でも Helm は触りません。CRD を含むチャート（cert-manager など）を上げるときは、リリースノートに従って CRD を別途更新する必要があります。

確認問題 他人のチャートを helm pull で落とし、中の values.yaml を直接書き換えて運用しています。何が起きますか。

答えを見る

チャートを新しいバージョンに上げた時点で、その変更は消えます。書き換えたのは配布物そのものだからです。自分の設定は別ファイルに書いて -f で渡し、チャート本体は受け取ったまま差し替えられる状態にしておきます。

考えてみる：同じチャートから app-a と app-b の 2 リリースを同じクラスタに入れられるでしょうか。（名前空間が分かれていれば通常は可能ですが、CRD や ClusterRole のようにクラスタ全体で 1 つしか存在できないものを含むチャートでは衝突します。何が名前空間スコープで何がクラスタスコープかが、そのまま答えになります。）

まとめ：そのまま使える説明テンプレート

30 秒版

Helm は、Kubernetes の YAML を「穴あきのテンプレート＋値」に分けて 1 つのディレクトリ（チャート）にまとめ、それを手元で展開してクラスタに適用するツールです。適用のたびに「送ったマニフェスト一式」を Secret に記録するので、アプリ単位でのアップグレード・ロールバック・アンインストールが成立します。パッケージマネージャと呼ばれるのは、この 2 つ、テンプレート化と履歴管理があるからです。

2 分版（30 秒版に足す分）

展開はすべて手元で終わります。Helm 3 にクラスタ常駐のコンポーネントはなく、権限は kubeconfig のままです。できあがるのも普通の Deployment や Service で、Helm 専用のオブジェクトは増えません。

kubectl apply -f との決定的な違いは、前回送った内容を覚えていることです。今回生成されなかったオブジェクトは削除されますし、前リビジョン・現物・今回の 3 者比較で差分を作るので、手動変更を踏み潰しにくくなっています。

実務での事故はたいてい値の優先順位です。チャート同梱の values.yaml を -f が上書きし、それを --set が上書きします。入れる前に helm template で展開結果を読むのが確実です。例外は crds/ の CRD で、これは install 時にしか作られず upgrade でも削除でも触られません。

よくある誤解

「Helm はクラスタ側で動いている」

Helm 2 の頃はそうでした（Tiller）。Helm 3 では廃止され、テンプレート展開も差分計算も手元のバイナリが行います。したがって「Helm に権限を与える」という作業はなく、あなたの kubeconfig でできることしかできません。

「helm rollback すれば元どおりになる」

戻るのはマニフェストだけです。実行済みのデータベースマイグレーション、PersistentVolume の中身、外部サービスに作られたリソースは戻りません。ロールバックは「宣言の巻き戻し」であって「時間の巻き戻し」ではない、と考えておくと事故を防げます。

「チャートを使えば設定が簡単になる」

他人のチャートは、多数の利用者の要望を飲み込んだ結果として values が数百行あるものも珍しくありません。何を指定できるかを読む手間は残りますし、チャート作者の設計に合わない使い方をすると、かえって遠回りになります。自分たちのアプリが Deployment 1 つと Service 1 つなら、素の YAML のままで十分なこともあります。

次の一歩

この記事では意図的に触れなかった話です。

  • Kustomize との使い分け：穴あきテンプレートで埋めるか、完成した YAML にパッチを当てるか、という思想の違い

  • チャートを作る側の話：_helpers.tpl での命名の共通化、helm lint、依存チャート（subchart）への値の渡し方
  • フック：マイグレーション用 Job を upgrade の前後に差し込む仕組み
