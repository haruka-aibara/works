
# CloudWatch Logs のロググループでログ保護をどう満たすか

ISMS（ISO/IEC 27002 8.15 ログ取得）の「ログの保護（改ざん防止、アクセス制限）」を、
ロググループではどう実装・説明するかの整理。
S3 ならバケットポリシーと Object Lock で説明できるが、ロググループには同じ形の仕組みがない。

## 結論

ロググループそのものを改ざんできなくするのではなく、次の 3 点で説明するのが一般的。

1. ログイベントは API で書き換えられない（**何もしなくてもそうなっている**）
2. 残る改ざん経路（削除・保持期間の短縮・偽ログの書き込み）を IAM で塞ぎ、CloudTrail で追えるようにする
3. 「絶対に消せない」保証が要るログだけ S3（Object Lock）に複製し、ロググループは検索用の置き場と割り切る

## そもそも身内しか触らないログをなぜ守るのか

- 侵入者は身内の権限（漏れた認証情報・乗っ取ったロール）で入ってきて、痕跡を消す
- ログは身内の操作の証拠。操作した本人が消せると証拠にならない（「自分はやっていない」と示す材料にもなる）
- 一番多いのは事故（保持期間の設定ミス、`terraform destroy` の巻き込み）

ロググループは中身を書き換えられないので、要は「消されなければよい」。

## 何もしなくても効いているもの

- **ログイベントを更新・個別削除する API がない**。ロググループ・ログストリーム単位の削除か、保持期間切れでしか消えない。「中身を書き換える」改ざんは API 上できない
- **IAM はデフォルト拒否**。明示的に許可していないプリンシパルは読めない
- **保存時暗号化は常に有効**（AWS 管理の鍵）
- **ロググループの削除・保持期間変更は CloudTrail の管理イベント**として記録される（イベント履歴で 90 日遡れる）

つまり S3 と違って「バケットポリシーで塞ぐ」相当の追加作業をしなくても、
中身の書き換えは起きない。問題は削除と権限の広すぎる人。

## 残る改ざん経路と塞ぎ方

| 経路 | 使われる API | 塞ぎ方 |
|---|---|---|
| ロググループ・ストリームごと消す | `logs:DeleteLogGroup` / `logs:DeleteLogStream` | 人間のロールから明示 Deny。Terraform の実行ロールだけに残す |
| 保持期間を短くして自然消滅させる | `logs:PutRetentionPolicy` / `logs:DeleteRetentionPolicy` | 同上。保持期間は Terraform で固定し、Config ルール `cw-loggroup-retention-period-check` で下回りを検知 |
| 転送を止めて以降を残さない | `logs:DeleteSubscriptionFilter` | 同上（S3 へ転送している場合のみ） |
| 暗号化キーを外す・無効化する | `logs:DisassociateKmsKey` / KMS 側の `DisableKey` | CMK を使う場合のみ。キーポリシーで管理者を分ける |
| 偽のログを書き足す | `logs:PutLogEvents` | 人間のロールから明示 Deny（AdministratorAccess 等には含まれている）。書き込み元（Lambda・EC2 等）のロールには対象ロググループの ARN だけを許可する |

Deny を入れる場所は、単一アカウントなら IAM ポリシーか Permissions Boundary。
マルチアカウントなら SCP が定番だが、ここでは単一アカウント前提で考える。

検知は「ロググループの削除」と「保持期間の変更」を EventBridge で拾って通知する程度で足りる。
Terraform 以外から起きることはないはずなので、起きたら対応必須の新規検出として扱える。

## アクセス制限（読む側）

- 基本は IAM の identity policy で `logs:GetLogEvents` / `logs:FilterLogEvents` / `logs:StartQuery` を必要な人に絞る
- S3 のバケットポリシーのように**リソース側で読み手を絞りたい**なら、CMK（KMS カスタマーマネージドキー）で暗号化してキーポリシーで `kms:Decrypt` を絞るのが定番。IAM で広く読める人がいても、キーポリシーで弾ける
- 個人情報などが混ざるなら、データ保護ポリシーでマスクし、`logs:Unmask` を持つ人だけが生値を見られるようにする

CMK は鍵管理と費用が増えるので、全ロググループには入れない。機密度の高いロググループだけに絞る。

## 敵対的に見ると

- **単一アカウントでは、管理者は Deny ごと外せる**。IAM の Deny は「うっかり」と「権限の小さい人」への対策で、管理者の悪意には効かない
- これを塞げるのは、別アカウントへの複製か、S3 Object Lock のコンプライアンスモードだけ。ロググループ単体では原理的に無理
- なので、監査証跡として本当に守る必要があるログ（CloudTrail など）は、**ロググループではなく S3 側で改ざん防止を担保する**。CloudTrail ならログファイル検証 + Object Lock で説明できる（[ログファイル検証を定期実行する](../../ideas/2026-09-26-CloudTrailログファイル検証を定期実行する.md)）
- アプリログのように「消されても監査上の致命傷にならない」ものは、IAM の Deny + 保持期間固定 + 削除検知で十分と説明してよい

## ISMS で説明するときの書き方（案）

- アクセス制限：IAM で閲覧権限を業務上必要な者に限定。機密ログは KMS キーポリシーで復号者を限定
- 改ざん防止：ログは書き込み後に変更できない仕組みのサービスに保存。削除・保持期間変更は権限を限定し、操作は CloudTrail に記録して通知
- 重要ログ（監査証跡）：変更不可設定（Object Lock）の S3 に保存し、整合性検証を実施
