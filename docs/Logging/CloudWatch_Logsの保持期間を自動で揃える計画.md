# CloudWatch Logs の保持期間を自動で揃える計画

個人情報の漏洩が続いていて、「もう攻撃されない」と期待して防ぐだけでは足りなくなっている。
漏れたときの被害は、漏れた時点で持っていたデータの量で決まる。
理由もなく無期限で残っているログを減らすのは、安く確実に被害を小さくできる手段になる。

この計画は CloudWatch Logs のロググループから始める。
S3 は期限なしが正しいバケット（静的ファイルなど）もあり、同じやり方をそのまま当てられないので後回しにする。

## 最終形

- ロググループの保持期間を、決めた値（例：30 日）へ自動で揃える
- 専用のタグ（例：`retention-extended`）が付いたものだけ、揃える対象から外す
- 作る人に覚えてもらうルールはない

3 種類のロググループは、それぞれこうなる。

| 種類 | どうなるか |
|---|---|
| Terraform 管理外（Lambda が自動で作ったものなど） | 誰も直さず放置されていたものが揃う |
| Terraform 管理で、期限が誤っているもの | 揃えた結果がドリフトとして持ち主に届き、持ち主がコードに取り込む |
| 本当に延ばしたいもの | 持ち主がタグを付けて延ばす。付けた本人が理由を説明できる |

## 進め方

### フェーズ 0：決める

- デフォルトの保持日数
- 延長用のタグの名前
- この仕組みを持つ担当（作る人ではなく、1 つのチームが持つ）

### フェーズ 1：棚卸し

ロググループを、名前・保持期間・サイズ（`storedBytes`）・作成日つきで一覧にする。
1 アカウント・1 リージョンならコンソールの「保持」列をソートするだけで済む。
アカウントやリージョンが多ければ、`aws logs describe-log-groups` をループで回す。

次に、Terraform の state にあるロググループ名と突き合わせ、管理外のものを分ける。
管理外のものは、さらに 3 つに分ける。

| 分類 | 見分け方 | 次にやること |
|---|---|---|
| 親が消えた孤児 | `/aws/lambda/関数名` の関数がもう存在しない、など | フェーズ 2 で消す |
| もう書かれていない | 最後の書き込みが古い（例：90 日以上前） | フェーズ 2 で消す |
| 今も書かれている | 最近も書き込みがある | フェーズ 3 で持ち主に確認する |

この時点で「管理外が○件、うち孤児が○件、合計○ GB」という数字が出る。
次のフェーズを進める説明に使う。

### フェーズ 2：いらないものを消す

消す候補の一覧を、持ち主ごとに名指しで送る。
「○日に消します。要るなら言ってください」と期限を付け、返事がなければ消す。
消したものは戻らないので、ここだけは必ず確認を挟む。

### フェーズ 3：検知だけの期間

残ったロググループのうち、保持期間がデフォルトより長いもの（無期限を含む）を一覧にする。
持ち主ごとに「このロググループは○日に 30 日になります。延ばすならタグを付けてください」と名指しで伝える。
期間は数週間とる。

### フェーズ 4：自動で揃えるのを始める

- 既存のもの：一度だけ一括で揃える
- 新しく作られるもの：作成イベント（`CreateLogGroup`）を EventBridge で拾い、その場で揃える

新しく作られたロググループには、まだ 30 日より古いログがない。
なので作成時に揃えても、消えるログは 1 件もない。
確認が要るのは既存のものだけで、それはフェーズ 3 で済ませている。

### フェーズ 5：定常運用

- 自動で揃える処理が失敗したら、アラームで気づけるようにする
- 延長タグが付いたものの一覧を、年に 1 回見直す

## 想定される突っ込みと答え

### そもそも論

**「防ぐほうが先じゃない？」**
防ぐ対策は続ける。
これは別の軸で、破られたときに漏れる量を減らす。
防御は破られる確率を下げるだけでゼロにはできないが、持っていないデータは、どう破られても漏れない。

**「ログを消したら、インシデントのときに調べられなくない？」**
調査で遡る期間に合わせてデフォルトを決める。
CloudTrail や VPC フローログのように長く要るものは、タグで延ばす。
問題にしているのは「要る期間を誰も決めていない無期限」で、要るログを消すことではない。

**「監査や法令で保存義務があるやつは？」**
それこそタグで延ばす対象になる。
義務があるという根拠が、そのまま延ばす理由の説明になる。

**「CloudWatch Logs に個人情報なんて入ってなくない？」**
入っていないと言い切れる人はほとんどいない。
アプリのログには、リクエストの中身やエラー時の入力値がそのまま出やすい。
気になるなら、CloudWatch Logs のデータ保護ポリシーで実際に含まれているかを調べられる。

**「コスト削減の話と何が違うの？」**
目的は漏洩時の被害を減らすことで、コストが下がるのは副次効果。
ただ、コストが下がることは進める説明の材料に使える。

### やり方

**「Config ルールで検知するだけでよくない？」**
検知だけだと、直す人がいなくて不合格の一覧が積み上がる。
作る人の多くはセキュリティに関心がなく、頼まれても直さない。
何もしなくても揃う形にしないと続かない。

**「マネージドルールの `cw-loggroup-retention-period-check` で足りない？」**
このルールは下限しか見ず、「失効しない」を合格にする。
ログを長く残すための監査ルールなので、持ちすぎを見つける目的とは向きが逆になる。

**「自動で変えるのは怖くない？」**
期限を縮めると古いログが消え、戻せない。
だから既存のものは、フェーズ 3 で名指しで確認してから揃える。
新しく作られるものは、消えるログがないので怖くない。

**「Terraform とぶつからない？」**
Terraform 管理のものは、揃えた結果がドリフトとして出る。
それが持ち主に「期限が基準と違う」と伝わる合図になる。
持ち主はコードに取り込むか、本当に要るならタグを付ける。
ドリフトに気づく仕組みと組み合わせる（[Terraform の差分が出たら鳴らす](../../ideas/2026-10-02-Terraformの差分が出たら鳴らす.md)）。

**「ドリフトを無視して apply したら、元に戻って揃え直しの繰り返しにならない？」**
なる。
ただ、往復が続くあいだはドリフト通知が鳴り続けるので、放置はされにくい。
実際の運用でどう転ぶかは、始めてから見る。

**「各 Terraform で `ignore_changes` を書けばぶつからないのでは？」**
各自に書かせる時点で守られない。
作る人に何もさせないのがこの計画の前提なので、採らない。

**「タグを付ければ何でも延ばせる。抜け道じゃない？」**
抜け道でいい。
延ばしたものはタグで全部一覧にでき、誰がいつ付けたかも CloudTrail に残る。
乱用は年 1 回の見直しで拾う。
タグを付けられる人を SCP で絞る手もあるが、重くなるので最初はやらない。

**「タグを付け忘れてたら？」**
既存のものは、フェーズ 3 で名指しで確認するので付け忘れに気づける。
新しく作ったものは、作った直後は消えるログがないので、あとから付けても失うものはない。

**「全員に周知すれば済むのでは？」**
全体へのお知らせは読まれない。
持ち主ごとに、対象のロググループを名指しで伝える。

**「デフォルトは何日にすればいい？」**
障害調査で実際に遡った期間を目安に決める。
迷うなら長めから始めて、あとで縮めてもよい。
縮めるのは簡単だが、消したログは戻らない。

### 運用

**「誰がこの仕組みを持つの？」**
1 つのチーム（セキュリティ担当など）が持つ。
中身は「作成イベントで揃える処理」と「失敗のアラーム」だけなので、保守は小さい。

**「揃える処理が止まっても気づけないのでは？」**
失敗はアラームで気づけるようにする（[セキュリティ通知の EventBridge は FailedInvocations にアラームを張る](../../ideas/2026-10-03-セキュリティ通知のEventBridgeはFailedInvocationsにアラームを張る.md)）。

**「揃える処理の権限が強すぎない？」**
必要なのは `logs:PutRetentionPolicy` と、タグを読む権限くらい。
ログを読む権限も、消す権限も持たせない。

**「Lambda が自動で作るロググループは、消してもまた作られない？」**
作られる。
それで正しい。作られた時点で揃うので、無期限にはならない。

**「サブスクリプションで S3 や OpenSearch にも流しているなら、意味なくない？」**
流し先にも同じ量のデータがある。
流し先は別途棚卸しして、同じ考え方で期限を決める。

**「孤児と判定して消したら、実は使ってたら？」**
消す前に名指しで確認し、期限を置く。
孤児は親のリソースがないことで判定するので、誤判定は少ない。

## 確かめていないこと

- 最後に書き込まれた日時は `describe-log-groups` では取れない。`describe-log-streams` を最終イベント時刻で並べて 1 件取る方法になるが、この時刻はおおよその値とされている
- 保持期間を縮めたとき、古いログが消えるまでにどれくらい時間がかかるか
- Config の `AWS::Logs::LogGroup` の設定項目で、保持日数とタグの両方を参照できるか
