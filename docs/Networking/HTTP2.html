HTTP/2 を図で理解する

1本のコネクションを多重化して、HTTP/1.1 の「順番待ち」を消したプロトコル。

何が問題だったのか

ページが遅い。個々の応答は速いのに、画像・CSS・JS が数十個あって全体が遅い。原因は HTTP/1.1 の構造にある——1本のコネクションでは、前のレスポンスが返るまで次のリクエストを送れない。

仕組み：フレームとストリーム

HTTP/2 はテキスト形式をやめ、フレームという固定構造の単位で送る。ヘッダは HEADERS フレーム、ボディは DATA フレーム。そして各フレームはストリーム ID を持つ。

ヘッダ圧縮（HPACK）

Cookie や User-Agent は、毎リクエストほぼ同じ内容が繰り返し送られる。HPACK は既出のヘッダをテーブルのインデックス参照に置き換える。

実質使われなくなった機能

機能意図現状
ストリーム優先度「CSS を画像より先に」と重み付けする実装差が大きく、RFC 9113 で非推奨扱い
サーバプッシュHTML を返すついでに CSS も送るキャッシュ済みでも送るため無駄が多く、Chrome が 2022 年に既定で無効化。代替は 103 Early Hints

つまり実務で効いているのは多重化とヘッダ圧縮の2つと考えてよい。

限界：TCP の HoL は残っている

HTTP レベルの順番待ちは消えたが、その下の TCP はバイト列の順序保証をするため、パケットが1つ落ちると無関係なストリームまで全部待たされる。

運用で押さえること

  • HTTP/1.1 向けの最適化を消す：ドメインシャーディング、CSS スプライト、過剰なバンドルは残っていると足を引っ張る。
  • 有効化は端点だけで済むことが多い：ALB / CloudFront / nginx などフロント側で有効にすれば、バックエンドは HTTP/1.1 のままでよい。
  • 効果はリソース数に比例する：リクエストが数個しかない API では体感差はほぼ出ない。効くのは細かいリソースが多いページ。

セキュリティ視点

多重化は「1本のコネクションで大量のリクエストを投げられる」ことでもあり、そのまま攻撃側の効率にもなる。

HTTP/2 Rapid Reset（CVE-2023-44487）

リクエストを送った直後に RST_STREAM でキャンセルする——これを繰り返すと、サーバの同時ストリーム上限にカウントされないまま処理だけを積み上げられる。2023 年に観測史上最大級の DDoS に使われた。対策はサーバ／ミドルウェアのパッチ適用と、ストリームリセットのレート制限。

ダウングレード時のリクエストスマグリング（H2.CL / H2.TE）

フロントが HTTP/2、バックエンドが HTTP/1.1 という一般的な構成では、変換時のヘッダ解釈の差が悪用されうる。フロント側で Content-Length と Transfer-Encoding の整合性を検証しているかを確認する。

提案するときの言い方——「HTTP/2 は表示速度の改善策だが、同時に1コネクションあたりの負荷特性が変わる。WAF やレート制限の閾値がコネクション数・リクエスト数の前提で組まれているなら、見直しが要る」。
