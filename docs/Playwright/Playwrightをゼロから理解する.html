Playwright をゼロから理解する

ブラウザが何をしているかの話から始めて、5 ステップで「API のない画面作業を自動化する」までたどり着きます。

この記事の目的

Playwright の解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「ロケータを自動待機で解決する E2E テストフレームワーク」という説明から始まります。この説明が成立するのは、E2E・ロケータ・待機という言葉がすでに体に入っている人だけです。しかも記事の多くはテストの話で終わるので、毎月の画面作業を自動化したいという動機で読みに来た人は、自分の用件との距離が最後まで縮まりません。

そこでこの記事は、あえて遠回りします。ブラウザが画面を組み立てる仕組みから始めて、5 ステップで「手作業運用の自動化」までたどり着きます。ゴールは用語を覚えることではなく、Playwright で何が置き換えられて何が置き換えられないかを自分の言葉で説明できるようになることです。最後に、そのまま口に出せる説明テンプレートを用意しました。

この記事の道のり

  1. STEP 1画面は人が見る前提でできている
  2. STEP 2ブラウザを外から動かす
  3. STEP 3自動化の最大の敵は「待つこと」
  4. STEP 4壊れにくい指し方とログイン状態
  5. STEP 5手作業運用を自動化する

STEP 4 まではすべて前提知識です。手作業運用の自動化そのものの話は STEP 5 だけですが、そこに至るまでの 4 ステップがないと「なぜ自動化したジョブは半年後に壊れるのか」が分かりません。逆に言えば、STEP 4 まで進めば STEP 5 はほとんど自明に感じられるはずです。

STEP 1：画面は人が見る前提でできている

  1. STEP 1画面は人が見る前提でできている
  2. STEP 2ブラウザを外から動かす
  3. STEP 3自動化の最大の敵は「待つこと」
  4. STEP 4壊れにくい指し方とログイン状態
  5. STEP 5手作業運用を自動化する

まず、これから何を自動化しようとしているのかを具体的にします。運用の現場にはこういう作業が残っています。

ここで最初の疑問が出ます。この程度なら curl で済むのではないか、と。実際、対象が API を持っているなら curl で済みます。済まないのは、対象が管理コンソールの「画面」しか提供していない場合です。

もうひとつ、認証があります。ログインしてから見る画面は、ログイン後に発行されたセッション情報を持っていることが前提です。人はブラウザがそれを勝手に保持してくれるので意識しませんが、自動化する側は「誰としてアクセスするか」を毎回用意しなければなりません。

つまり、画面しかない相手を自動化するには、本物のブラウザに開かせて、人と同じ経路をたどらせるのがいちばん確実です。ここまでが Playwright の手前の話です。

確認問題 1 ログイン画面に ID とパスワードを curl で POST して Cookie を受け取り、それを付けて一覧ページを取りにいく——この方針はどこで行き詰まりますか。

答えを見る

2 か所で行き詰まります。1 つ目は、ログインフォームが CSRF トークンや画面上でしか発行されない値を要求する場合で、その値は画面を組み立てないと手に入りません。2 つ目は、Cookie が取れても一覧ページの中身は JavaScript が後から描くので、受け取った HTML には入っていない点です。

どちらも「画面を組み立てる処理を自分で肩代わりしていない」ことが原因です。であれば、組み立てる装置ごと動かせばいい。次はその装置——ブラウザを外から動かす話です。

STEP 2：ブラウザを外から動かす

  1. ✓ STEP 1画面は人が見る前提
  2. STEP 2ブラウザを外から動かす
  3. STEP 3自動化の最大の敵は「待つこと」
  4. STEP 4壊れにくい指し方とログイン状態
  5. STEP 5手作業運用を自動化する

ブラウザには、外部のプログラムから操作を受け付ける口が用意されています。開発者ツールが使っているのと同じ仕組みで、「このページを開け」「この座標をクリックしろ」「今の DOM を返せ」といった命令をやり取りできます。Playwright は、この口を使ってブラウザを操るプログラムです。

導入は 2 コマンドです。npm パッケージを入れ、続けて操作対象のブラウザ本体を落とします。Playwright は OS にインストール済みの Chrome を使うのではなく、動作を検証したバージョンのブラウザを自前で持ちます。実行環境によって挙動が変わらないのはこのためです。

$ npm init playwright@latest     # プロジェクトに導入（設定ファイルごと作られる）
$ npx playwright install          # 操作対象のブラウザ本体を取得

最初のスクリプトはこれだけです。ページを開いて、画面を画像で保存します。

import { chromium } from 'playwright';

const browser = await chromium.launch();          // 画面を出さずに起動
const page = await browser.newPage();
await page.goto('https://example.com/');
await page.screenshot({ path: 'shot.png', fullPage: true });
await browser.close();

画面を出さずに動かすモードをヘッドレスと呼びます。人の画面を占領しないので、サーバ上で動かせます。開発中は chromium.launch({ headless: false }) にすると実際の操作が目で見えるので、最初はこちらから始めるのが分かりやすいです。

確認問題 2 このスクリプトは 10 回動かせば 10 回とも同じ結果になりそうに見えます。実際にはどんなときに落ちますか。

答えを見る

スクリーンショットを撮る瞬間に、まだ欲しい内容が描かれていないときです。goto はページの読み込みを待ちますが、その後に JavaScript が API を呼んで表を描くなら、画像には空の枠しか写りません。ネットワークが遅い日だけ失敗する、という形で表面化します。

これは Playwright に限らず、画面の自動化でいちばん多い失敗です。次の STEP で正面から扱います。

STEP 3：自動化の最大の敵は「待つこと」

  1. ✓ STEP 1画面は人が見る前提
  2. ✓ STEP 2ブラウザを外から動かす
  3. STEP 3自動化の最大の敵は「待つこと」
  4. STEP 4壊れにくい指し方とログイン状態
  5. STEP 5手作業運用を自動化する

人が手作業でやるとき、待ち時間を意識することはありません。表が出るまで目で見て待ち、出たら次に進むからです。スクリプトにはその目がないので、「出たかどうか」を誰かが判定する必要があります。

ここで最初に思いつくのが「5 秒待つ」という固定待ちですが、これは両方向に外れます。

Playwright は、クリックや入力のたびに対象の状態を確認してから実行します。DOM に存在するか、見えているか、アニメーションが止まって位置が固定されたか、操作可能か（disabled でないか）、そして他の要素に覆われていないか。これらを満たすまで短い間隔で再確認し、既定では最大 30 秒待ちます。この仕組みを自動待機と呼びます。

覆われていないかの確認は、地味ですが効きます。ダイアログや読み込み中のオーバーレイが上に乗っているとき、人なら「まだ押せない」と分かりますが、座標クリックは黙ってオーバーレイを押してしまいます。

この仕組みが働くのは、ロケータという形で対象を指したときです。ロケータは要素そのものではなく「この条件で探す」という手順の記述で、使う瞬間に毎回探し直されます。だから、探した後で画面が描き直されても壊れません。

// 「請求」という名前のリンクを押し、表が出るまで待ってから撮る
await page.getByRole('link', { name: '請求' }).click();
await expect(page.getByRole('table')).toBeVisible();   // 条件が満たされるまで再試行
await page.screenshot({ path: 'billing.png', fullPage: true });

expect(...) の確認も、失敗したらすぐ諦めるのではなく、条件を満たすまで再試行します。「表示されていること」を待ち合わせの手段として書けるわけです。

やりがちな回避策 どうしても安定しないとき、click({ force: true }) で確認を飛ばしたくなります。これは「押せない状態のものを押す」ことなので、原因を隠すだけです。押せない理由（ローディング中・別要素が覆っている）を突き止めるほうが結局は早く終わります。

確認問題 3 自動待機があるなら、要素の指し方は何でもよいはずです。ところが「画面をちょっと直したら自動化が止まった」は頻発します。なぜでしょうか。

答えを見る

自動待機が面倒を見るのは「見つけた要素が操作できる状態になるまで」であって、そもそも見つけられるかどうかは別問題だからです。指し方が画面の作りに依存していると、見た目が同じでも中身の構造が変われば見つからなくなり、30 秒待ったすえに失敗します。

つまり待ちの次の課題は、何を手がかりに要素を指すかです。次の STEP へ。

STEP 4：壊れにくい指し方とログイン状態

  1. ✓ STEP 1画面は人が見る前提
  2. ✓ STEP 2ブラウザを外から動かす
  3. ✓ STEP 3待つこと
  4. STEP 4壊れにくい指し方とログイン状態
  5. STEP 5手作業運用を自動化する

要素の指し方には 2 系統あります。構造で指す（3 番目の div の中の 2 番目のボタン）か、役割と表示名で指す（「書き出し」という名前のボタン）かです。

Playwright はこの「役割と名前で指す」方を標準の書き方として用意しています。使う順の目安は次のとおりです。

書き方指すもの向いている場面
getByRole('button', { name: '書き出し' })役割＋表示名第一候補。人が画面を説明するときの言い方に近い
getByLabel('メールアドレス')ラベル付きの入力欄フォームの入力
getByText('前月比')表示されている文字見出しや本文の存在確認
getByTestId('export-btn')自分で付けた印自社アプリで、上の方法では一意に絞れないとき

とはいえ、他社の管理画面を相手に「何が role になっているか」を読み解くのは骨が折れます。ここで npx playwright codegen <URL> が効きます。ブラウザが開き、自分で操作するとその操作に対応するコードが書き出されます。手作業をそのまま実演すれば下書きができるので、最初の 1 本はこれで作り、あとから読みやすく直すのが早いです。

ログイン状態を毎回作り直さない

ここまでで操作は書けますが、ジョブが 5 本あれば 5 回ログインすることになります。遅いだけでなく、実害があります。ログイン試行が増えればアカウントロックや不審ログイン検知に触れますし、MFA があるなら毎回そこで止まります。

STEP 2 の図を思い出してください。Cookie や localStorage を持っているのは context でした。つまりログイン直後の context の中身をファイルに書き出して、次回はそれを読み込んで始めればいい。これが storageState です。

// 1) 一度だけログインして状態を保存する
const page = await browser.newPage();
await page.goto('https://console.example.com/login');
await page.getByLabel('メールアドレス').fill(process.env.OPS_USER!);
await page.getByLabel('パスワード').fill(process.env.OPS_PASS!);
await page.getByRole('button', { name: 'ログイン' }).click();
await expect(page.getByRole('heading', { name: 'ダッシュボード' })).toBeVisible();
await page.context().storageState({ path: 'auth.json' });   // ← Cookie などを書き出す

// 2) 以降のジョブはログイン済みの状態から始める
const ctx = await browser.newContext({ storageState: 'auth.json' });

ID とパスワードをコードに直接書かず環境変数から読んでいるのは、そのままリポジトリに入るのを防ぐためです。auth.json も同じ理由で .gitignore に入れます。セッションには期限があるので、失効したら取り直す前提で組みます。

確認問題 4 手元で書いたスクリプトが完走しました。これを「毎月 1 日に自動で実行される運用」にするには、あと何を決める必要がありますか。3 つ挙げてください。

答えを見る

最低限、次の 3 つです。どこで動かすか（ブラウザが入った実行環境と、そのスケジュール）、認証情報をどこから渡すか（手元の環境変数は使えない）、結果をどこに残すか（撮った画像とジョブの成否）。

3 つ目が抜けると、動いているのか止まっているのか誰にも分からないジョブができあがります。次の STEP の主題です。

STEP 5：手作業運用を自動化する

  1. ✓ STEP 1画面は人が見る前提
  2. ✓ STEP 2ブラウザを外から動かす
  3. ✓ STEP 3待つこと
  4. ✓ STEP 4指し方とログイン状態
  5. STEP 5手作業運用を自動化する

ここが本題です。STEP 1 の 5 工程を、そのまま置き換えます。

置き換えるジョブを書く

実行の形は 2 つあります。@playwright/test のテストランナーを使う形と、playwright ライブラリだけを使ってただのスクリプトとして書く形です。運用ジョブなら前者を勧めます。テストではないのに、と思うかもしれませんが、欲しいものが最初から付いてくるからです——失敗時の再試行、結果レポート、そして後述する trace です。

import { test, expect } from '@playwright/test';

test('月次：権限一覧のエビデンスを取得する', async ({ page }) => {
  const today = new Date().toISOString().slice(0, 10);

  await page.goto('https://console.example.com/members');
  await expect(page.getByRole('table')).toBeVisible();          // 出るまで待つ

  // 中身が空でないことを確かめてから撮る（空の画面を証跡にしない）
  await expect(page.getByRole('row')).not.toHaveCount(1);

  await page.screenshot({ path: `evidence/${today}-members.png`, fullPage: true });
  await page.pdf({ path: `evidence/${today}-members.pdf` });    // Chromium のみ
});

手作業との差が出るのは not.toHaveCount(1) の行です。人は空の表を見れば「おかしい」と気づきますが、スクリプトは白紙でも平然と保存します。人が無意識にやっていた確認を、明示的に書き起こす——これが手作業を自動化するときの本体の作業です。取得だけ移して確認を落とすと、証跡が積み上がっているのに中身は空、という事故になります。

どこで動かすか

ブラウザ本体が入った環境が要ります。CI で動かすなら、実行前に npx playwright install --with-deps chromium でブラウザと OS 側の依存パッケージを入れるか、必要なものが揃った公式のコンテナイメージを使います。スケジュール実行は CI 側の cron に任せ、認証情報はシークレットとして環境変数で渡します。出来上がった画像や PDF は成果物として保存すれば、そのまま証跡の保管先になります。

失敗したときに何が残るか

手作業が失敗したときは、やった本人の記憶しか残りません。自動化の利点はここで出ます。trace を有効にしておくと、各操作の前後の画面、DOM の状態、通信、コンソール出力が 1 つの zip にまとまります。

// playwright.config.ts
export default {
  retries: 1,
  use: { trace: 'on-first-retry' },   // 失敗して再試行したときだけ記録する
};
$ npx playwright show-trace trace.zip   # 操作を 1 手ずつ巻き戻して見る

on-first-retry は、成功したときの負荷を増やさずに失敗時だけ証拠を残す設定です。「ログイン画面に戻されていた」「表は出ていたが列名が変わっていた」が、その場にいなくても分かります。

自動化してよい作業、してはいけない作業

作業判断理由
画面を開いて証跡を取得・保存する自動化する手順が固定で、判断がない
一覧を取得して差分を出す自動化する差分を出すところまでは機械の仕事
差分を見て「この権限は妥当か」を決める人がやる判断そのもの。自動化の対象ではない
画面から設定を変更する・削除する原則やらない失敗時の巻き戻しが効かない。API があるならそちらで

方針としては、取得と提示までを自動化し、判断と変更操作は人に残すのが扱いやすい線です。読み取りだけのジョブなら、壊れても被害は「その月は手作業に戻る」で済みます。

先に確認すること 自動化する前に、対象に API・CSV エクスポート・定期レポート配信がないかを必ず調べてください。画面の自動化は、機械が読める口が無いときの最後の手段です。画面は予告なく変わるので、API があるならそちらのほうが桁違いに寿命が長くなります。また、自社が管理する画面か、利用規約上の扱いはどうかも先に確認します。

確認問題 5 毎月のエビデンス取得を自動化して半年が経ちました。フォルダには 6 か月分のファイルが並んでいます。何を確認すべきでしょうか。

答えを見る

ファイルが並んでいることは、正しく取れたことを意味しません。確認すべきは 6 回とも成功で終わったか（ジョブの実行履歴）と、中身が空でないかです。画面の作りが変わってジョブが失敗し続けていても、誰も見ていなければ気づけません。

だから STEP 5 の図の下段——失敗が人に届く経路——が、自動化そのものと同じくらい重要になります。ついでに言えば「そもそも 6 か月間、誰もこの証跡を使わなかった」なら、自動化ではなく作業自体をやめる相談をするほうが筋です。

確認問題 6（考える問題） 「ブラウザを自動操作できる」と分かると、SaaS の設定変更まで自動化したくなります。それでも読み取りに留めておくほうがよいのは、なぜでしょうか。

答えを見る

正解は一つではありませんが、考える筋は 2 つあります。1 つは失敗の形です。読み取りの失敗は「取れなかった」で終わりますが、変更の失敗は途中まで適用された中途半端な状態を残し、それを画面操作で巻き戻すのは困難です。もう 1 つは記録で、画面操作による変更は「誰が変えたか」が自動化用アカウントの名前でしか残りません。

自動化の範囲は、うまくいったときの得ではなく、失敗したときに何が起きるかで決めるのが安全です。

まとめ：そのまま使える説明テンプレート

30 秒版

Playwright は、本物のブラウザを外から動かす道具です。ページを開き、ボタンを押し、画面を画像や PDF で保存するところまでを、人と同じ経路でやらせられます。ポイントは 2 つで、操作の前に「見えているか・押せる状態か」を自動で待ってくれること、そしてログイン済みの状態をファイルに保存して使い回せることです。おかげで、API を持たない管理画面から毎月エビデンスを取る、といった手作業を定時実行に置き換えられます。テスト用のツールとして知られていますが、仕組みとしては「画面操作の自動化」そのものです。

2 分版（30 秒版に足す分）

出発点は、DevOps を進めても消えない「画面しかない作業」です。対象が API を持たないと、ログインして画面を開いてスクリーンショットを撮る、という工程が人の手に残ります。curl で済まないのは、画面が JavaScript で組み立てられるからで、受け取った HTML には欲しい表が入っていません。だから本物のブラウザに開かせます。

自動化で最初につまずくのは待ち時間です。人は表が出るまで目で見て待ちますが、スクリプトは待ちません。固定の秒数を入れると、速い日は無駄に遅く、遅い日は落ちます。Playwright は要素が見えて操作できる状態になるまで自動で待ちます。次につまずくのが要素の指し方で、構造に依存した指定は画面の小さな変更で折れるので、役割と表示名で指します。さらに毎回ログインすると遅いうえにアカウントロックや MFA に触れるので、ログイン済みの状態を保存して使い回します。その保存ファイルはセッションそのものなので、リポジトリには入れません。

運用に載せるときに増える仕事が 2 つあります。人が無意識にやっていた「中身が空でないことの確認」をコードに書き起こすこと、そして失敗が人に届く経路を作ることです。手作業には人がその場にいるという監視が付いていましたが、自動化はそれを外します。失敗時は trace を見れば操作を 1 手ずつ巻き戻せます。範囲は読み取りと提示までに留め、判断と設定変更は人に残すのが安全です。そして大前提として、API があるならそちらを使います。画面の自動化は最後の手段です。

よくある誤解

「Playwright はテストのツールなので、運用の自動化には使えない」

中身は「ブラウザを外から動かすライブラリ」で、テストランナーはその上に乗っている層です。テストを書かずにライブラリだけを使うこともできますし、運用ジョブをテストランナーの形で書いて、再試行・レポート・trace をそのまま使うこともできます。呼び名に引きずられる必要はありません。

「自動化すれば、その作業はもう考えなくていい」

逆に、考えることが 1 つ増えます。手作業には「人がその場にいる」という監視が暗黙で付いていました。自動化はそれを外すので、失敗を検知して人に届ける経路を別に作らないと、止まっていることに誰も気づけません。消えるのは作業時間であって、責任ではありません。

「自動待機があるから、待ちのことは考えなくていい」

自動待機が面倒を見るのは「指した要素が操作できる状態になるまで」です。どこまで進んだら次へ行ってよいかを決めるのは書く側の仕事で、ページを開いた直後に撮れば白紙が保存されます。何が表示されていれば完了なのかを、確認として明示的に書く必要があります。

次の一歩

この記事では「手作業運用の自動化まで」を優先し、次の話には意図的に踏み込みませんでした。

  • 本来の用途である E2E テスト（アサーションの書き方、テスト設計、並列実行）
  • 画面の見た目の変化を検知するビジュアル比較（toHaveScreenshot）
  • 通信の差し替え（page.route）や、ブラウザを介さない API リクエスト
  • Python・.NET・Java 版のバインディング（この記事の内容はそのまま当てはまります）
  • CI に載せる部分の詳細：GitHub Actions とは、シークレットと権限の扱い
  • 「外部依存を含む処理をどうテストするか」という近い問題設定：pytest と moto をゼロから理解する

次は、いま毎月やっている画面作業を 1 つ選び、npx playwright codegen を起動してその手順をそのまま実演してみるのがおすすめです。自分の手作業がコードとして書き出されるのを見ると、どこまでが機械の仕事でどこからが判断なのかがはっきりします。
