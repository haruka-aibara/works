Prowler をゼロから理解する

「クラウドの設定が正しいか」は誰も教えてくれない、という話から始めて、5 ステップで「他の仕組みとの違い」「入れるとよい場面」「入れたら増える手間」まで自分で判断できるところまで進みます。

この記事の目的

Prowler の解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「Prowler はマルチクラウド対応の CSPM ツールで、CIS・PCI DSS・ISO 27001 などに対応しています」という、中級者向けの前提から始まるからです。なぜ既存の仕組みでは足りないのかが分からないまま、対応フレームワークの一覧だけが増えていきます。

そこでこの記事は、あえて遠回りします。「クラウドの設定ミスは誰も教えてくれない」といういちばん手前の話から始めて 5 ステップで進みます。ゴールは機能を暗記することではなく、自分の環境に入れるべきか、入れたら何の作業が増えるのかを自分の言葉で説明できることです。

この記事の道のり

  1. STEP 1設定ミスは誰も教えてくれない
  2. STEP 2「正しい」の基準を外から借りる
  3. STEP 3基準を実行する道具＝Prowler
  4. STEP 4出てきた結果をどう扱うか
  5. STEP 5入れる判断と、増える手間

STEP 4 まではすべて前提知識です。本題は STEP 5 だけですが、そこに至る 4 ステップがないと「無償だし入れておいたほうがよさそう」以上の判断ができません。

STEP 1：設定ミスは誰も教えてくれない

  1. STEP 1設定ミスは誰も教えてくれない
  2. STEP 2「正しい」の基準を外から借りる
  3. STEP 3基準を実行する道具＝Prowler
  4. STEP 4出てきた結果をどう扱うか
  5. STEP 5入れる判断と、増える手間

クラウドは数クリックでリソースを作れます。そして、危ない設定でも同じように作れてしまいます。S3 バケットを公開にする、セキュリティグループで 0.0.0.0/0 から SSH を開ける、ルートユーザに MFA を付けない。どれもエラーになりません。責任共有モデルでは基盤の安全は事業者の担当ですが、その上の設定が妥当かどうかを判定してくれるものは、標準では何も動いていません。

しかも、作った日は正しくても状態は動きます。検証のために一時的に開けたポート、消し忘れた退職者のアクセスキー、障害対応中にコンソールから触った設定。どれも「後で戻す」つもりで残ります。

では手で確認すればよいか。対象は「アカウント × リージョン × サービス × リソース」です。1 アカウント 100 リソースなら何とかなりますが、アカウントが 20 個あればもう現実的ではありません。そして一度確認しても、それはその日を写した写真にすぎません。

確認問題 「作るときにレビューする」というルールを徹底すれば、この問題は解決するでしょうか。

答えを見る

解決しません。 作成時のレビューは作成時点しか見ていないからです。時間が経って変わった状態は捉えられませんし、レビューを通さずに作られたリソースも残ります。必要なのは「いまどうなっているか」を繰り返し確かめる仕組みです。ただし、ここで次の問題にぶつかります——何をもって「正しい」とするのかです。

STEP 2：「正しい」の基準を外から借りる

  1. STEP 1 ✓設定ミスは誰も教えてくれない
  2. STEP 2「正しい」の基準を外から借りる
  3. STEP 3基準を実行する道具＝Prowler
  4. STEP 4出てきた結果をどう扱うか
  5. STEP 5入れる判断と、増える手間

点検しようとして最初に詰まるのは、何を点検するかが決まっていないことです。「S3 は公開禁止」くらいはすぐ思いつきます。しかし KMS 鍵のローテーション、CloudTrail のログファイル検証、RDS のバックアップ保持期間、IAM パスワードポリシーの再利用防止……と並べていくと、思いつきでは必ず抜けが出ます。そして抜けていること自体に気づけません。

そこで、点検項目を自分で発明せず、公開されている基準を借ります。

  • CIS Benchmark（CIS AWS Foundations Benchmark など）— ベンダー中立の設定基準。監査でもよく名前が出る
  • AWS Foundational Security Best Practices（FSBP） — AWS 自身が定めたベストプラクティス
  • PCI DSS / ISO 27001 / SOC 2 / HIPAA — 業界・制度側の要求事項

ここで押さえておきたいのは、これらが 2 層になっていることです。実際に値を見て合否を決めるチェックと、そのチェックをどう選んで何番として数えるかというフレームワークです。「ルートユーザに MFA が付いているか」という同じチェックが、CIS にも FSBP にも PCI DSS にも、それぞれ別の番号で登場します。

点検内容を機械可読な形で配る、という考え方そのものは Prowler に固有のものではありません。標準仕様としてまとめたものが SCAP です（SCAP をゼロから理解する）。

確認問題 CIS Benchmark の文書を手に入れました。これで点検できるでしょうか。

答えを見る

できません。 配布されているのは人が読む前提の文書で、「確認手順：aws iam get-account-summary を実行し、返り値を確認する」といった調子で書かれているからです。数百項目を人が一つずつ叩くのは、STEP 1 と同じ話に戻ります。基準をそのまま実行できる形にした道具が要ります。

STEP 3：基準を実行する道具＝Prowler

  1. STEP 1 ✓設定ミスは誰も教えてくれない
  2. STEP 2 ✓「正しい」の基準を外から借りる
  3. STEP 3基準を実行する道具＝Prowler
  4. STEP 4出てきた結果をどう扱うか
  5. STEP 5入れる判断と、増える手間

ここでようやく Prowler です。Prowler は、クラウドの API を読み取り専用で叩いて、チェック項目ごとに PASS / FAIL を出すツールです。Apache License 2.0 のオープンソースとして公開されています。

やっていることは 3 つだけです。

  1. 手元にある認証情報でクラウドの API を呼ぶ（読み取りのみ）
  2. チェックを 1 つずつ実行する
  3. リソース単位で PASS / FAIL に深刻度を付けて出力する
pip install prowler
prowler aws

これだけです。エージェントを入れる必要も、クラウド側で何かを有効化する必要もありません。いま自分が持っている権限で見える範囲を、そのまま点検します。AWS なら SecurityAudit と ViewOnlyAccess（どちらも AWS 管理ポリシー）に、一部のチェック用の読み取り権限を足した構成が推奨されています。書き込み権限は要りません。

対応するのは AWS だけではありません。Azure・Google Cloud・Kubernetes・Microsoft 365・GitHub など 20 を超えるプロバイダに対応していて、AWS だけでも 600 を超えるチェック、フレームワークは全体で 50 以上あります。同じコマンド体系・同じ出力形式で扱えるのが、単一クラウド向けのツールとの大きな違いです。

確認問題 AWS には Trusted Advisor も Config も Security Hub CSPM もあります。設定ミスに気づくだけなら、Prowler は要らないのではないでしょうか。

答えを見る

もっともな疑問で、多くの場合そのとおりです。 CIS や FSBP のチェック内容はかなり重なります。違いは 2 つあります。使い始めるのに何が要るかと、もっと大きいのがそもそも何を見ているかです。純正の仕組みが最初から見ていない領域があります。この比較は STEP 5 で正面から扱います。その前に、もっと手前の問題があります——実行したら FAIL が数百件出ました。どうしますか。

STEP 4：出てきた結果をどう扱うか

  1. STEP 1 ✓設定ミスは誰も教えてくれない
  2. STEP 2 ✓「正しい」の基準を外から借りる
  3. STEP 3 ✓基準を実行する道具＝Prowler
  4. STEP 4出てきた結果をどう扱うか
  5. STEP 5入れる判断と、増える手間

初回実行の結果は、たいてい心が折れる量になります。600 を超えるチェックをリソースの数だけ回すので、FAIL だけで数千行になることも珍しくありません。ここからが実際の作業です。

まず、1 件の結果に何が入っているかを見ます。

出力形式は用途で選びます。CSV（表計算で並べ替える）、JSON（OCSF 形式。SIEM やデータレイクに流す）、HTML（そのまま人に見せる）、ASFF（AWS Security Hub CSPM に送り込む）。何も指定しなければ CSV と JSON-OCSF が出ます。

そして、数千行を扱える大きさまで絞ります。順番はだいたい決まっています。

絞り込みは実行時の指定でもできます。フレームワークを 1 つに限定する、サービスを限定する、FAIL だけ出す、といった具合です。

prowler aws --compliance cis_3.0_aws --status FAIL
prowler aws --service s3 --service iam
prowler aws --list-compliance   # 指定できるフレームワークの一覧

最後の「意図的な設定を除外」にあたるのが Mutelist です。「このリソースのこのチェックは意図してこうしている」を YAML に書いておくと、次回から FAIL として数えなくなります。静的サイト配信用の S3 バケットは公開されているのが正しい、といったケースがこれにあたります。

確認問題 Mutelist に書けば余計な FAIL は静かになります。これで運用に乗るでしょうか。

答えを見る

乗りません。 Mutelist は「検討して受容した」と「面倒だから消した」を、同じ見た目にしてしまうからです。誰がいつ何の理由で除外したのかを残さないと、半年後の担当者にはどちらか区別できません。そしてもう一つ根本的な問題があります——直す人が決まっていなければ、どれだけきれいに並べ替えても環境は何も変わりません。

STEP 5：入れる判断と、増える手間

  1. STEP 1 ✓設定ミスは誰も教えてくれない
  2. STEP 2 ✓「正しい」の基準を外から借りる
  3. STEP 3 ✓基準を実行する道具＝Prowler
  4. STEP 4 ✓出てきた結果をどう扱うか
  5. STEP 5入れる判断と、増える手間

ここが本題です。Prowler は無償で、インストールも数分です。だからこそ「とりあえず入れる」が起きやすく、そしてとりあえず入れたものはたいてい見られなくなります。用途から逆算して決めます。

設定ミスに気づく仕組みは他にもある。なぜ Prowler か

用途から逆算するなら、最初に片づけるべき疑問はこれです。AWS には Trusted Advisor も Config も Security Hub CSPM もあり、どれも設定ミスに気づける仕組みです。わざわざ別のツールを持ち込む理由は何なのか。

4 つを同じ軸で並べると、性格がはっきり分かれます。

運用面（上 5 行）だけを見ると「常設の仕組みがあるならそれでいい」に見えます。ですが、本当に効いてくるのは下から 2 行目です。そもそも検知できる中身が違います。

Prowler にしかないチェックがある

Trusted Advisor も Config も Security Hub CSPM も、見ているのは設定項目が基準どおりかです。「暗号化が ON か」「パブリックアクセスがブロックされているか」——設定の状態を確認しています。

Prowler には、それに加えて値の中身を読んで「秘密が直書きされていないか」を探すチェックがあります。

チェック何を見るか
awslambda_function_no_secrets_in_variablesLambda の環境変数に API キー・トークン・パスワードらしき値が入っていないか
ec2_instance_secrets_user_dataEC2 のユーザーデータに認証情報が書かれていないか
ecs_task_definitions_no_environment_secretsECS タスク定義の環境変数に秘密が入っていないか
cloudformation_stack_outputs_find_secretsCloudFormation のスタック出力に秘密が露出していないか
cloudwatch_log_group_no_secrets_in_logsログ本文に秘密が出力されていないか
ssm_document_secretsSSM ドキュメントに秘密が埋め込まれていないか
prowler aws --categories secrets

これらは設定の ON / OFF ではなく、文字列を読んで「秘密らしいか」を判定しています（Yelp の detect-secrets を使用）。純正のマネージドルールやコントロールには、これに当たるものがありません。

似たものが AWS 側にもある場合との違い。 Config には ecs-no-environment-secrets という似たルールがありますが、これはあらかじめ指定したキー名と一致するかを見るものです。DB_PASSWORD という名前なら引っかかりますが、X1 という名前で同じ値を入れれば通ります。なお Lambda のコード内の直書きは Amazon Inspector のコードスキャンでも検出できます。上の表で AWS 純正に該当がないのは、環境変数・ユーザーデータ・スタック出力・SSM ドキュメントといった設定側に置かれた値のほうです。

秘密以外にも、フレームワークとは別の「観点」で束ねた区分があります。--categories に encryption / forensics-ready / internet-exposed / logging / secrets / threat-detection / trustboundaries を指定すると、「CIS の何番」ではなく「インターネットに露出しているものを全部出して」という聞き方ができます。

「カスタムルールを書けばいいのでは」の答え

ここで当然こう思います。Config にはカスタムルールがあるのだから、Lambda を書けば同じことができるのでは？

できます。できるのですが、その「書けば」が本体です。1 つのチェックを自作すると、こういう内訳になります。

データの取得も自明ではありません。たとえば EC2 のユーザーデータは Config の構成項目に含まれていないので、カスタムルールから DescribeInstanceAttribute を自分で呼ぶ必要があります。「Config に記録されているものを評価する」という前提がそもそも成り立たない項目があります。

これをチェックの数だけ繰り返します。秘密の検査だけでも 9 個です。Prowler の価値は「純正で見られないものが見られる」よりも、「見るための道具一式を自分で作って保守しなくていい」と言うほうが正確です。

だから、正直な結論はこうなります。

CIS や FSBP の範囲を継続的に見張るのが目的で、対象が AWS だけなら、Security Hub CSPM を有効化するほうが素直です。 その範囲に限れば、Prowler を足しても同じ項目をもう一度見るだけになります。
逆に言えば、範囲の外に用があるなら話は別です。

入れるとよい場面

次のどれかに当てはまるなら、Prowler を選ぶ理由が立ちます。

  • 設定値の中身まで見たいが、自作したくない：環境変数・ユーザーデータ・スタック出力の秘密の直書きを、カスタムルールを何本も書かずに洗い出したい
  • 「CIS の何番」以外の切り口で聞きたい：インターネットに露出しているもの、ログが取れていないところを、カテゴリ単位で一度に出したい
  • まだ何も入っていない：有効化する前に「そもそも何が起きているか」を知りたい。常設の仕組みを入れる提案をするための材料集めにもなる
  • 有効化できない・したくない：権限がない、短期の検証アカウントで課金を増やしたくない、他社の環境を預かって見ている
  • アカウントに何も残したくない：レコーダーもルールも作らないので、点検したこと自体が環境に痕跡を残さない
  • AWS 以外もある：Azure・Google Cloud・Kubernetes・M365 を同じ出力形式で横並びにできる
  • 成果物をファイルで持ち出したい：監査や取引先への提出物は、コンソールの画面ではなく手元のファイルである必要がある
  • CI で回したい：apply の直後に、その場で判定して落としたい

逆に言えば、これらに当てはまらないのに入れるなら、Security Hub CSPM の劣化版を自前で運用することになります。

そして両方入れるのも自然な構成です。ASFF 形式で出力すれば Prowler の結果を Security Hub CSPM に送れるので、人が見る画面は 1 つにまとめられます。

名前に注意。 2025 年末に、従来の Security Hub は Security Hub CSPM に改名され、「Security Hub」は別の新しいサービスの名前になりました。CIS や FSBP の準拠評価をしているのは CSPM のほうです。検索するときに混ざります。

入れると増える手間

導入コストは「インストールの手間」ではありません。次の 6 つが、入れたあとに毎回ついてきます。

  1. 初回のトリアージ：数百〜数千件の FAIL を「直す／除外する／受容する」に仕分ける作業が、最初に一度まとめて発生します。ここは自動化できません。この時間を確保できないなら、入れても一覧が増えるだけです
  2. 例外の管理：Mutelist は書いた瞬間から腐り始めます。リソースを消したのにエントリだけ残る、書いた本人が異動する。理由と見直し時期をセットで残す運用が要ります
  3. 実行基盤の設計：誰がどこから、どの権限で、どの頻度で回すか。手元の端末から本番アカウントに入るのか、専用ロールを引き受けるのか。定期実行するなら実行場所と結果の保管先も決めます
  4. バージョン追従：更新でチェックが増えるため、環境が変わらなくても FAIL が増えます。「増えた＝悪化した」ではないと説明できる状態にしておきます
  5. API 呼び出し量：全チェックを全リージョンで回すと読み取り API を大量に叩きます。大規模アカウントではスロットリングや実行時間の問題が出るので、範囲を絞る設計が要ります
  6. 誤検知の仕分け：値の中身を読むチェックは、その性質上どうしても誤検知が出ます（MYSQL_ALLOW_EMPTY_PASSWORD=yes のような値を秘密と判定するなど）。Mutelist の出番がいちばん多いのもこのカテゴリです
  7. 直す人の確保：検出は入口でしかありません。修正する担当と、修正が本番に入るまでの経路（チケット・変更管理・IaC の修正）がないと、件数は減りません
Prowler の実行はスナップショットです。 実行と実行の間に開いたポートは、次に回すまで見えません。「常時見張ってくれる」ものだと思って入れると、期待と実態がずれます。

確認問題 「無償だし、とりあえず入れて定期的に回しておけば結果が溜まる」——これは導入理由になるでしょうか。

なりません。 誰がその一覧を見て、誰が直すのかが決まっていなければ、FAIL の山が積み上がって誰も開かなくなります。「次の監査までに CIS の critical をゼロにする」「引き継いだアカウント 5 つの現状を今月中に把握する」のように、出口を先に決めてから入れます。用途が決まっていない道具は、入れた瞬間から負債です。

まとめ：そのまま使える説明テンプレート

30 秒版

Prowler は、クラウドの設定が基準どおりかを点検するオープンソースのツールです。読み取り専用の権限で API を叩き、チェックごとに PASS / FAIL を出します。AWS・Azure・Google Cloud・Kubernetes などに対応していて、CIS Benchmark や PCI DSS といったフレームワーク単位でレポートを出せます。クラウド側で何かを有効化する必要がないので、引き継いだアカウントの棚卸しや、監査・取引先照会への回答に向いています。加えて、環境変数やユーザーデータに秘密が直書きされていないかといった、純正のマネージドルールにはない検査が最初から入っています。同じことを Config のカスタムルールで自作すると、チェックの数だけ Lambda を書いて保守することになります。

2 分版（30 秒版に足す分）

クラウドの設定ミスは、誰も教えてくれません。危ない設定でもエラーにならず、作った日は正しくても状態は動くからです。かといって何を点検すべきかを自分で列挙するのは現実的ではないので、CIS や FSBP といった外部の基準を借ります。その基準を実行できる形にしたのが Prowler です。

ただし、入れると手間も増えます。初回は数百〜数千件の FAIL が出るので、直す・除外する・受容するの仕分けが丸ごと発生します。除外した理由を残す運用、誰がどこで定期実行するかの設計、バージョンアップでチェックが増えることへの説明も要ります。そして Prowler の実行はスナップショットなので、常時の検知は Security Hub CSPM や Config 側の役割です。CIS や FSBP の範囲を AWS だけで見張るなら、そちらを有効化するほうが素直です。ただし範囲そのものが違います。Lambda の環境変数や EC2 のユーザーデータに秘密が直書きされていないか、といった「値の中身を読む」チェックは、純正のマネージドルールにはありません。Config のカスタムルールを書けば実現はできますが、検知ロジックの設計から Lambda の保守までをチェックの数だけ抱えることになります。その一式が最初から入っていることが、Prowler を選ぶいちばんの理由です。

よくある誤解

「Prowler を入れれば継続的に監視される」

Prowler が出すのは実行した瞬間のスナップショットです。定期実行の仕組みは自分で用意する必要がありますし、実行間隔より短い期間の変更は捉えられません。常時の検知が要るなら、それは Security Hub CSPM・Config・GuardDuty 側の役割です。

「FAIL の件数がセキュリティレベルを表す」

対象リソースが多いだけで件数は増えますし、意図的な設計が FAIL になることもあります。バージョンアップでチェックが増えれば、環境が何も変わらなくても件数は増えます。見るべきは総数ではなく、深刻度別の件数と判断済み／未判断の内訳です。

「同じことは Config のカスタムルールでもできる」

できます。違うのは実現できるかどうかではなく、自分で書いて保守する量です。検知ロジックの設計・Lambda・IAM・配布・ランタイム更新を、チェックの数だけ抱えるか、既製の 600 超をそのまま使うかの差です。逆に言えば、自社固有の 1〜2 個だけが欲しいなら、カスタムルールで書くほうが素直なこともあります。

「Prowler が環境を直してくれる」

Prowler は読み取り専用です。修正方法は検出結果に書かれますが、適用するのは人（または IaC などの別の仕組み）です。これは制約ではなく利点でもあります。本番アカウントに書き込み権限を渡さずに導入できる、というのは稟議を通すときの材料になります。

次の一歩

この記事では「入れるかどうかを判断できること」を優先し、次の話には意図的に踏み込みませんでした。

  • 独自チェックの追加と、カスタムフレームワークの定義
  • Prowler App（自分でホストする Web UI）と SaaS 版の違い
  • 定期実行の作り込み：CI・コンテナ・スケジューラからの実行と、結果の保管・差分の取り方
  • 常設側の設計：Security Hub CSPM、FSBP 優先順位の付け方、Config、Trusted Advisor
  • 点検を機械可読にする仕組みの標準：SCAP をゼロから理解する
  • OS・ミドルウェア側の脆弱性：Vuls 脆弱性スキャナー

まずは検証用アカウントで、フレームワークを 1 つ・FAIL だけに絞って回してみるのがおすすめです（prowler aws --compliance cis_3.0_aws --status FAIL）。いきなり全部回すと、最初の一歩で結果の量に埋もれます。
