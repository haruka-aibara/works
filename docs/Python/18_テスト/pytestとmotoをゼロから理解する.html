pytest と moto をゼロから理解する

「確かめたい動きが、本物では作れない」という手前の話から始め、5 ステップで「実リソースを作らずに AWS を呼ぶコードの動きを見る」までたどり着きます。

この記事の目的

テストの解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「moto は AWS サービスをモックするライブラリです」という、中級者向けの前提から始まるからです。モックとは何で、なぜそれが要るのかが分からないまま、デコレータの書き方だけが増えていきます。

そこでこの記事は、あえて遠回りします。題材はセキュリティの検出を Slack に流す Lambda です。「その動きを本物の AWS で確かめようとすると何が起きるか」という、いちばん手前の話から始めて 5 ステップで進みます。ゴールは書き方を暗記することではなく、なぜ本物のリソースを作らずに済ませられるのかを自分の言葉で説明できることです。

この記事の道のり

  1. STEP 1確かめたい動きが本物では作れない
  2. STEP 2pytest は呼んで確かめるだけ
  3. STEP 3外に出ていく線を数える
  4. STEP 4偽物には 2 種類ある
  5. STEP 5moto で AWS をプロセスの中に置く

STEP 4 まではすべて前提知識です。本題の moto は STEP 5 だけですが、そこに至る 4 ステップがないと「AWS をモックする」が何を指しているのか分からないまま、デコレータの暗記になります。

STEP 1：確かめたい動きが本物では作れない

  1. STEP 1確かめたい動きが本物では作れない
  2. STEP 2pytest は呼んで確かめるだけ
  3. STEP 3外に出ていく線を数える
  4. STEP 4偽物には 2 種類ある
  5. STEP 5moto で AWS をプロセスの中に置く

題材はこういう Lambda です。15 分ごとに起動し、Trusted Advisor のセキュリティ検出を取ってきて、DynamoDB の台帳（前回まで何を通知したかの記録）と突き合わせます。台帳にない検出は新規として Slack に通知し、通知済みでも 3 日経って消えていなければリマインド、検出から消えていれば解消として台帳から削除します。

書き上げてデプロイし、手で起動してみます。何も起きません。今このアカウントにセキュリティの指摘がないからです。では通知が正しく出ることをどう確かめるか。

よくやってしまうのが、確認のために S3 バケットをわざと公開設定にしてみる、という手です。実害のある状態を意図的に作ったうえで、検出されるまで待ち、それで見られるのは 3 分岐のうち 1 つだけです。

つまり問題は「動かして確かめること」ではなく、確かめたい状態を自分で作れないことです。欲しいのは「検出がこうで、台帳がこうだったら、どう動くか」を好きなだけ並べられる仕組みです。

確認問題 では検証用の AWS アカウントにテスト用のリソースを一式作って、そこに好きな状態を入れればよいのではないでしょうか。

答えを見る

半分しか作れません。 台帳（DynamoDB）は自分のテーブルなので好きな状態を入れられます。しかし Trusted Advisor の検出結果は AWS が出すもので、こちらから書き込めません。3 分岐のうち入口の半分が依然として手に入らないままです。

そもそも、この Lambda の判断は「検出」と「台帳」という 2 つの値を見て決まっているだけです。値を渡して結果を見るだけなら、AWS は要らないのでは？ ——その「渡して見る」を仕組みにしたのが次の話です。

STEP 2：pytest は呼んで確かめるだけ

  1. STEP 1 ✓確かめたい動きが本物では作れない
  2. STEP 2pytest は呼んで確かめるだけ
  3. STEP 3外に出ていく線を数える
  4. STEP 4偽物には 2 種類ある
  5. STEP 5moto で AWS をプロセスの中に置く

pytest がやることは 3 つだけです。test_ で始まるファイルを探し、その中の test_ で始まる関数を呼び、関数の中の assert が成り立てば緑、成り立たなければ赤にする。それだけです。

STEP 1 の判断部分を、値を受け取って結果を返すだけの関数として取り出します。

# notifier.py
def classify(detected, ledger, now, remind_days=3):
    """検出結果と台帳を突き合わせ、通知すべきものを決める"""
    new = sorted(detected - ledger.keys())
    remind = sorted(
        arn for arn in detected & ledger.keys()
        if now - ledger[arn] >= timedelta(days=remind_days)
    )
    resolved = sorted(ledger.keys() - detected)
    return new, remind, resolved

これを確かめるテストは、呼んで assert するだけです。

# test_classify.py
NOW = datetime(2026, 4, 10, tzinfo=timezone.utc)
ARN = "arn:aws:trustedadvisor:::recommendation-resource/abc"

def test_台帳にない検出は新規になる():
    new, remind, resolved = classify({ARN}, {}, NOW)
    assert new == [ARN]
    assert remind == []
    assert resolved == []

$ pytest -v
test_classify.py::test_台帳にない検出は新規になる PASSED           [100%]
============================ 1 passed in 0.09s =============================

STEP 1 で「本物では作れない」と言っていた 3 分岐は、引数を変えて並べるだけになります。同じ確認を入力違いで繰り返すときは @pytest.mark.parametrize を使います。

@pytest.mark.parametrize("detected, ledger, expected", [
    ({ARN}, {},                              ([ARN], [], [])),   # 新規
    ({ARN}, {ARN: NOW - timedelta(days=1)},  ([], [], [])),      # まだ黙る
    ({ARN}, {ARN: NOW - timedelta(days=3)},  ([], [ARN], [])),   # リマインド
    (set(), {ARN: NOW - timedelta(days=1)},  ([], [], [ARN])),   # 解消
])
def test_検出と台帳の組み合わせで分岐が決まる(detected, ledger, expected):
    assert classify(detected, ledger, NOW) == expected

4 行足すだけで、3 日待つ話も、わざとバケットを公開する話も消えました。境界（ちょうど 3 日目は通知するのか）も 1 行です。

確認問題 ここまでで classify は確かめられました。では同じ調子で、Lambda の入口である handler をそのまま呼べば全部まとめて確認できるでしょうか。

答えを見る

呼べますが、本物の AWS につながります。 handler の中では boto3 が Trusted Advisor と DynamoDB を呼び、Slack に POST します。手元では自分の認証情報で本当にアクセスし、CI にはそもそも認証情報がないので落ちます。

ここで一度、この関数のどこが「外」とつながっているのかを数えてみる必要があります。

STEP 3：外に出ていく線を数える

  1. STEP 1 ✓確かめたい動きが本物では作れない
  2. STEP 2 ✓pytest は呼んで確かめるだけ
  3. STEP 3外に出ていく線を数える
  4. STEP 4偽物には 2 種類ある
  5. STEP 5moto で AWS をプロセスの中に置く

handler を書き出すと、外に出ていく線は 3 本しかありません。

判断を classify に寄せたので、3 本の線に触らないテストはもう書けています。しかし確かめられていないものが残ります。

  • 通知したあと、台帳に正しい形で書けているか
  • 解消したとき、台帳から本当に消えるか
  • 検出が大量にあってページングされたとき、2 ページ目も拾えているか

これらは「外とやり取りする線」そのものの話なので、判断を切り出しても消えません。線を減らすのではなく、線の向こう側を差し替えるしかありません。

確認問題 では 3 本の線の向こう側を「偽物」に差し替えればよさそうです。偽物はどう作るのがよいでしょうか。

答えを見る

ここで分かれ道になります。 「呼ばれたらこの値を返す」と決め打ちした偽物を置くのが最も手軽です。実際それで足りる線もあります。

ただしこのやり方には、テストが緑でも本番が落ちるという特有の失敗があります。偽物には性質の違う 2 種類があり、線ごとに選び分ける必要があります。

STEP 4：偽物には 2 種類ある

  1. STEP 1 ✓確かめたい動きが本物では作れない
  2. STEP 2 ✓pytest は呼んで確かめるだけ
  3. STEP 3 ✓外に出ていく線を数える
  4. STEP 4偽物には 2 種類ある
  5. STEP 5moto で AWS をプロセスの中に置く

1 つめはモックです。「この呼び出しにはこの値を返す」と自分で決め、呼ばれ方を記録します。Python なら unittest.mock で数行です。2 つめはフェイクで、本物と同じふるまいをする軽い実装です。状態を持つので、書き込んだものが読み出しで返ってきます。

モックの弱点は具体的です。DynamoDB の get_item の返り値を、自分の記憶で {"Item": {"arn": ARN}} と書いたとします。本物は型を明示した {"Item": {"arn": {"S": ARN}}} です。テストは緑になり、本番だけ落ちます。モックが確かめているのは本物の仕様ではなく、自分の思い込みです。

台帳のように「書いた結果が次の読み出しに効く」相手も、モックでは表現しづらくなります。put の呼ばれ方を記録できても、「put したから scan で返るようになった」というつながりは再現できません。

確認問題 では DynamoDB のフェイクを自分で書けばよいでしょうか。

答えを見る

現実的ではありません。 キーの型チェック、条件付き書き込み、ページネーション、エラーの返り方——それらしく動かすだけで本業になります。しかもその実装が正しいかどうかを、また誰かが確かめる必要があります。

この「AWS のフェイク」を、Python のプロセスの中で動く形で用意したものが moto です。

STEP 5：moto で AWS をプロセスの中に置く

  1. STEP 1 ✓確かめたい動きが本物では作れない
  2. STEP 2 ✓pytest は呼んで確かめるだけ
  3. STEP 3 ✓外に出ていく線を数える
  4. STEP 4 ✓偽物には 2 種類ある
  5. STEP 5moto で AWS をプロセスの中に置く

moto の mock_aws は、boto3 がリクエストを送る直前に割り込み、AWS に出さずに moto 自身の実装で応答します。コードは boto3 のまま、1 文字も変えません。

準備は conftest.py に置きます。ここに書いたフィクスチャは、同じディレクトリのテストから引数名で呼べます。

# conftest.py
@pytest.fixture
def aws(monkeypatch):
    """偽のクレデンシャルを入れてから moto を起動する"""
    monkeypatch.setenv("AWS_ACCESS_KEY_ID", "testing")
    monkeypatch.setenv("AWS_SECRET_ACCESS_KEY", "testing")
    monkeypatch.setenv("AWS_SESSION_TOKEN", "testing")
    monkeypatch.setenv("AWS_DEFAULT_REGION", "ap-northeast-1")
    with mock_aws():
        yield

@pytest.fixture
def table(aws, monkeypatch):
    """台帳テーブルを作る。テストが終われば消える"""
    monkeypatch.setenv("LEDGER_TABLE", "ta-ledger")
    return boto3.resource("dynamodb").create_table(
        TableName="ta-ledger",
        KeySchema=[{"AttributeName": "arn", "KeyType": "HASH"}],
        AttributeDefinitions=[{"AttributeName": "arn", "AttributeType": "S"}],
        BillingMode="PAY_PER_REQUEST",
    )

偽のクレデンシャルは飾りではありません。設定を間違えて moto の外に出てしまったとき、本物のアカウントに届かせないための最後の砦です。monkeypatch.setenv で入れておけば、テストが終わると環境変数も元に戻ります。

3 本の線のうち、moto が代わりをするのは DynamoDB だけです。残り 2 本は自分で塞ぎます。

外に出ていく線どうするか理由
DynamoDB（台帳）moto に任せる返り値の形も書き込みの規則も本物側が持つ。書いたものを読み返して確かめたい
Trusted Advisor自分の関数の境目で差し替えるmoto はサービスと API 単位で対応する。ListRecommendations は未実装で、呼ぶと 404 Not yet implemented が返る
Slack Webhook自分の関数の境目で差し替えるそもそも AWS ではない。送ろうとした文面を集めれば十分

差し替えの単位は fetch_findings() と post_to_slack()、つまり自分で書いた関数です。boto3 の内部ではなく自分の関数の境目で塞ぐので、AWS の API の形を自分で書き写す必要がありません（STEP 4 の失敗はここで避けられます）。

# test_handler.py
@pytest.fixture
def slack(monkeypatch):
    """Slack への送信を止めて、送ろうとした文面だけ集める"""
    sent = []
    monkeypatch.setattr(notifier, "post_to_slack", sent.append)
    return sent

def test_解消した項目は通知せず台帳から消える(table, slack, monkeypatch):
    yesterday = (datetime.now(timezone.utc) - timedelta(days=1)).isoformat()
    table.put_item(Item={"arn": ARN, "last_notified_at": yesterday})   # ① 状態を作る
    monkeypatch.setattr(notifier, "fetch_findings", lambda: set())     #    検出は空

    notifier.handler({}, None)                                         # ② 呼ぶ

    assert slack == []                                                 # ③ 結果を見る
    assert table.scan()["Items"] == []

STEP 1 では「指摘を直してリフレッシュを待つ」しかなかった解消の分岐が、3 行で作れる状態になりました。しかも table.scan() で本当に消えたことを読み返して確認できています。これがモックとの決定的な差です。

最初に踏む落とし穴 boto3 のクライアントをモジュールの先頭で作ると、moto が起動する前に作られるため差し替えが効かず、本物の AWS に飛びます（Lambda では使い回しのために先頭で作るのが定石なので、よく踏みます）。クライアントは handler の中で作るか、フィクスチャから渡します。

確認問題 このテストが全部緑なら、この Lambda は本番でも動くと言えるでしょうか。

答えを見る

言えません。 moto は API の応答をまねますが、その API を呼ぶ権限があるかは見ていません。実行ロールに dynamodb:DeleteItem を書き忘れていても、moto は素直に消してくれます。タイムアウト、メモリ、VPC からの到達性、サービスクォータも同じく範囲外です。AWS 自身も、設定や IAM まで含めた正確な確認はクラウド上でのテストだと言っています。

moto が消したのは「分岐を確かめるために現実が変わるのを待つ」部分です。権限と設定の確認は、デプロイ後に別途行うものとして残ります。何を消して何が残ったかを言えることが、この記事のゴールです。

まとめ：そのまま使える説明テンプレート

30 秒版

pytest は Python のテストを走らせる道具です。test_ で始まる関数を集めて呼び、assert が通れば緑にする、それだけの仕組みです。moto はそこに足すライブラリで、boto3 が AWS にリクエストを送る直前で折り返し、同じプロセスの中で AWS のふりをして応答します。コードは boto3 のまま変えません。おかげで「台帳にこの項目が残っている状態」のような、本物では待つしかない状況をテストの中で作れます。AWS アカウントもネットワークも要りません。

2 分版（30 秒版に足す分）

出発点は、セキュリティ系の処理ほど「確かめたい状態を自分で作れない」という問題です。新規検出・3 日後のリマインド・解消という分岐を本物で再現するには、指摘が出るのを待つか、わざと危険な状態を作るしかありません。

まず判断だけを関数に切り出せば、その部分は引数を変えるだけで全分岐を確かめられます。それでも「台帳に正しく書けたか」は外とのやり取りそのものなので残ります。ここで置く偽物には 2 種類あり、返り値を自分で決め打ちするモックは、自分の思い込みが間違っていると緑のまま本番が落ちます。moto は状態を持つフェイクなので、書いたものが読み出しに返り、思い込みが入り込みません。

ただし moto はサービスと API 単位の対応です。未実装の API や AWS 以外の宛先は、自分で書いた関数の境目で差し替えます。そして moto が見ているのは API の応答だけで、IAM 権限・タイムアウト・クォータは範囲外です。消えるのは「待ち時間」であって、デプロイ後の確認ではありません。

よくある誤解

「moto を入れれば AWS 上での確認は要らなくなる」

moto が答えるのは API の応答までです。実行ロールの権限不足、タイムアウト、クォータ、VPC からの到達性はすべて範囲外で、moto の中では成功してしまいます。デプロイ後に一度は本物で通す工程は残ります。

「モックと moto は同じもの」

役割が違います。モックは返り値を自分で決めるので、その値が本物と違っていてもテストは緑になります。moto は状態を持つフェイクで、書いた結果が読み出しに反映されます。「書けたことを読み返して確かめたい」相手には moto を使います。

「テストのために本番コードを分けるのは不純」

逆です。外とやり取りする箇所を関数の境目にしておくのは、テスト以前に設計として妥当です。AWS 自身もハンドラは薄いアダプタにして処理の本体を分けることを勧めています。差し替えやすさは、その副産物です。

次の一歩

この記事では全体像を優先し、次の話には意図的に踏み込みませんでした。

  • LocalStack との使い分け
