Rust をゼロから理解する

「このメモリ、もう返していいのか」という問いから始めて、5 ステップで Rust までたどり着きます。

この記事の目的

Rust の解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「所有権とライフタイムによりガベージコレクタなしでメモリ安全性を保証する」という一文から始まります。この説明が成立するのは、メモリの確保と解放・ダングリングポインタ・GC の停止時間といった話がすでに体に入っている人だけです。土台が抜けている状態でこれを読むと、知らない言葉を知らない言葉で説明されることになります。

そこでこの記事は、あえて遠回りします。「プログラムが値をどこに置いているか」という、Rust 以前の話から始めて、5 ステップで Rust までたどり着きます。ゴールは用語を覚えることではなく、Rust が何を解決した言語なのかを自分の言葉で説明できるようになることです。最後に、そのまま口に出せる説明テンプレートを用意しました。

この記事の道のり

  1. STEP 1メモリはいつ返すのか
  2. STEP 2これまでの 2 つの答え
  3. STEP 3所有権 — 持ち主は 1 人
  4. STEP 4借用 — 貸し出しの規則
  5. STEP 5Rust を書く

STEP 4 まではすべて Rust の前提知識です。Rust そのものの話は STEP 5 だけですが、そこに至るまでの 4 ステップがないと STEP 5 は理解できません。逆に言えば、STEP 4 まで進めば STEP 5 はほとんど自明に感じられるはずです。

STEP 1：メモリはいつ返すのか

  1. STEP 1メモリはいつ返すのか
  2. STEP 2これまでの 2 つの答え
  3. STEP 3所有権 — 持ち主は 1 人
  4. STEP 4借用 — 貸し出しの規則
  5. STEP 5Rust を書く

プログラムが値を置く場所は、大きく 2 つに分かれます。

1 つはスタックです。整数やポインタのように、大きさがあらかじめ決まっているものが積まれます。関数に入るときに積み、関数を抜けるときに降ろす。片づけは自動で、しかも順番が決まっているので迷いません。

もう 1 つがヒープです。実行してみないと大きさが分からないもの——ユーザが入力した文字列、件数が変わるリスト——はここに置きます。こちらは「必要な分を貸してください」と頼んで借りる領域なので、使い終わったら返す必要があります。そして、いつ返すかは誰も教えてくれません。

返すタイミングを間違えると、次の 3 つが起きます。返し忘れ（リーク。長時間動くプロセスがじわじわ太る）、二重に返す（管理情報が壊れる）、そして返したあとに使う（use-after-free。解放済みの領域を読み書きしてしまう）。3 つ目が特に厄介なのは、たいていの場合その場では落ちないことです。運が良ければ古い値が読めてしまい、運が悪ければ攻撃者が仕込んだ値が読めます。

確認問題 「確保したら必ず解放をセットで書く」というルールをレビューで徹底すれば、この問題はなくなるでしょうか。

答えを見る

なくなりません。 確保と解放が同じ関数の中で完結するなら守れますが、現実のコードでは値が関数から関数へ渡り、構造体に格納され、複数の場所から参照されます。そうなると「いま誰がこの値を持っていて、最後に使い終わるのは誰か」がソースコードのどこにも書かれていない状態になります。早期リターン・例外・エラー分岐で経路が増えれば、どれか 1 本で解放が漏れます。

つまり必要なのは注意力ではなく、「誰がいつ返すか」を仕組みとして決める方法です。これには歴史的に 2 つの答えがありました。

STEP 2：これまでの 2 つの答え

  1. STEP 1 ✓メモリはいつ返すのか
  2. STEP 2これまでの 2 つの答え
  3. STEP 3所有権 — 持ち主は 1 人
  4. STEP 4借用 — 貸し出しの規則
  5. STEP 5Rust を書く

1 つ目の答えは人間が決めるです。C や C++ のやり方で、プログラマが malloc / free（あるいは new / delete）を書きます。実行時に余計な処理が一切入らないので速く、メモリの使われ方も完全に読めます。代償は STEP 1 で見たとおりで、経路が増えるほど漏れます。

2 つ目の答えは実行中に機械が決めるです。Java・Go・Python・JavaScript などが採るガベージコレクション（GC）で、プログラムと並行して動くランタイムが「もう誰からも参照されていない値」を探して回収します。プログラマは解放を書かなくてよくなり、use-after-free も二重解放も原理的に起きません。

代償は、実行時に判断しているということ自体から来ます。回収のために CPU 時間を使い、タイミングによっては処理が一瞬止まります。止まる長さは入力やメモリの使われ方で変わるため、「最悪何ミリ秒か」を事前に保証しにくくなります。そして GC を動かすランタイムそのものが必要なので、OS カーネル・ファームウェア・ブラウザエンジンのように、その土台がない場所では使えません。

確認問題 GC があれば STEP 1 の 3 つの問題は解決します。では、なぜ 3 つ目の答えが必要なのでしょうか。

答えを見る

GC が「実行時に判断する」という前提を置いているからです。 その前提が払えない場所があります。停止時間が許されない領域（OS・組み込み・高頻度の取引処理）、ランタイムを載せられない領域（カーネル・ファームウェア・WebAssembly の小さなバイナリ）、そして他言語から呼ばれるライブラリなどです。これらの領域はこれまで C / C++ しか選択肢がなく、その結果として use-after-free が残り続けてきました。

そこで Rust は、解放のタイミングを実行時ではなくコンパイル時に確定させるという道を採ります。そのために言語へ持ち込まれた規則が「所有権」です。

STEP 3：所有権 — 持ち主は 1 人

  1. STEP 1 ✓メモリはいつ返すのか
  2. STEP 2 ✓これまでの 2 つの答え
  3. STEP 3所有権 — 持ち主は 1 人
  4. STEP 4借用 — 貸し出しの規則
  5. STEP 5Rust を書く

コンパイラが解放のタイミングを決められるようにするには、「いま誰がこの値を持っているか」がソースコードから読み取れなければなりません。Rust はそれを 3 つの規則で作ります。

  • ヒープ上の値には、持ち主（所有者）がちょうど 1 人いる
  • 持ち主になれるのは、同時に 1 つの変数だけ
  • 持ち主がスコープを抜けたとき、値は自動的に解放される

3 つ目が肝心なところで、free を書かないのに解放されます。書かないのに解放されるという点は GC と同じですが、解放される場所がソースコード上で一意に決まっている点が違います。持ち主の変数がスコープを抜ける行、そこがこの値の最期です。コンパイラはそこに解放処理を埋め込みます。実行時に探し回る処理は存在しません。

すると、次のコードが問題になります。

let s1 = String::from("hello");
let s2 = s1;          // 持ち主が s1 から s2 へ移る（ムーブ）
println!("{s1}");     // ← コンパイルエラー

もし s1 と s2 の両方が持ち主のままなら、スコープを抜けるときに同じ実体を 2 回解放してしまいます。かといって実体をまるごと複製すれば、代入のたびに重い処理が走ります。Rust が選んだのは持ち主を移すという答えで、これをムーブと呼びます。移したあとの s1 は使用禁止になります。

同じことが関数呼び出しでも起きます。引数に渡すのも持ち主を移す操作なので、渡したあとの変数は使えません。

fn main() {
    let s = String::from("hello");
    show(s);              // 持ち主が関数の引数へ移る
    println!("{s}");      // ← エラー：s はもう持っていない
}

fn show(text: String) {
    println!("{text}");
}                         // ここで text の実体が解放される

確認問題 文字列を受け取って長さを返す関数を書き、同じ文字列を 3 回測りたくなりました。上のやり方で書くと、どうなるでしょうか。

答えを見る

1 回目で持ち主を失い、2 回目が書けません。 関数の最後で毎回 String を返して受け取り直せば動きますが、読むだけの関数にまで返り値が生えることになり、現実的ではありません。

ここで足りていないのは、「持ち主は変えずに、中身を見せるだけ」という手段です。それが借用です。

STEP 4：借用 — 貸し出しの規則

  1. STEP 1 ✓メモリはいつ返すのか
  2. STEP 2 ✓これまでの 2 つの答え
  3. STEP 3 ✓所有権 — 持ち主は 1 人
  4. STEP 4借用 — 貸し出しの規則
  5. STEP 5Rust を書く

値を渡す代わりに、値の置き場所を教えるのが借用です。書き方は変数の前に & を付けるだけで、所有権は移りません。

fn main() {
    let s = String::from("hello");
    let n = length(&s);             // 借用：持ち主は s のまま
    println!("{s} は {n} バイト");   // s はまだ使える
}

fn length(text: &String) -> usize {
    text.len()
}                                   // 借りていただけなので解放しない

ここで、貸し出しに規則が付きます。ある値について、同時に成立してよいのは次のどちらか一方だけです。

  • 読むだけの借用（&T）を、何本でも
  • 書き換えられる借用（&mut T）を、ちょうど 1 本だけ
let mut v = vec![1, 2, 3];
let first = &v[0];    // 読むための借用
v.push(4);            // ← エラー：書き換えの借用と同時にはできない
println!("{first}");

push は、容量が足りなければヒープ上の領域を取り直して中身を引っ越します。そうなると first は引っ越し前の——つまり解放済みの——場所を指したままになります。これは C++ でも定番の落とし穴ですが、実際に容量が足りるかどうかは実行してみるまで分かりません。Rust は足りるかどうかを問わず、規則の時点で一律に止めます。

借用にはもう 1 つ規則があります。借りている参照は、貸し主より長生きできません。関数の中で作った値への参照を返そうとすると、値は関数を抜けた時点で解放されるので、返した参照は行き先を失います。コンパイラはこれを拒否します。この「参照が有効でいられる期間」がライフタイムです。

確認問題 借用の規則は、1 つのスレッドで動くプログラムのための規則でしょうか。

答えを見る

違います。むしろ複数スレッドで本領を発揮します。 データ競合とは「複数のスレッドが同じデータに同時に触り、少なくとも 1 つが書き換える」ことで起きる問題です。これは借用の規則が禁止している組み合わせ、そのものです。

つまり所有権と借用を導入した時点で、メモリ管理の問題とデータ競合の問題が同じ 1 つの規則で同時に片づいています。Rust で「恐れなしの並行性（fearless concurrency）」と言われるのはこのためです。ではここまでの規則を持った言語は、書いていてどういう感じになるのでしょうか。

STEP 5：Rust を書く

  1. STEP 1 ✓メモリはいつ返すのか
  2. STEP 2 ✓これまでの 2 つの答え
  3. STEP 3 ✓所有権 — 持ち主は 1 人
  4. STEP 4 ✓借用 — 貸し出しの規則
  5. STEP 5Rust を書く

ここまで来ると、Rust の設計方針は 1 行で言えます。実行時に起きたら困ることを、コンパイル時に起こす。所有権と借用はメモリについてそれをやりましたが、同じ発想が言語の他の部分にも効いています。

代表が「値が無いかもしれない」の扱いです。多くの言語はこれを null で表しますが、null は普通の値のふりをして流通するので、触った瞬間に落ちます。Rust には null がありません。代わりに「無いかもしれない」を型に書きます。

let v = vec![10, 20, 30];

match v.get(10) {                          // 返り値は Option 型
    Some(x) => println!("値は {x}"),
    None    => println!("その位置には何もない"),
}

v.get(10) が返すのは数値ではなく Option で、中身を取り出すには Some と None の両方を書かされます。片方を忘れるとコンパイルが通りません。同じ仕組みが失敗しうる処理にも使われ、そちらは成功（Ok）と失敗（Err）を持つ Result 型になります。例外のように、書かなければ上へ飛んでいくものではありません。

match "42x".parse::<i32>() {               // 返り値は Result 型
    Ok(n)  => println!("数値は {n}"),
    Err(e) => println!("数値にできない：{e}"),
}

実際に動かすところまでは短く済みます。ツールチェーンの導入は rustup、ビルドと依存関係の管理は cargo にまとまっていて、別途ビルドツールやパッケージマネージャを選ぶ必要はありません。

$ cargo new hello      # プロジェクトを作る
$ cd hello
$ cargo run            # ビルドして実行する
$ cargo test           # テストを実行する

そしてコンパイルエラーは、Rust では読むものです。エラー番号（E0382 など）、どの行で持ち主が移ったか、どう直せばよいかの候補までが出ます。rustc --explain E0382 でその番号の解説を読むこともできます。最初のうちは借用チェッカに怒られ続けるのが普通で、それは学び方として間違っていません。

この設計が何を買っているかは、脆弱性の統計にも表れています。Microsoft は自社製品のセキュリティ修正のうち約 7 割がメモリ安全性に起因すると報告しており、Chromium でも深刻な不具合の同程度がメモリ安全性の問題だとしています。CISA などの政府機関がメモリ安全な言語への移行ロードマップを求めているのも、この割合が長年下がっていないためです。Rust が消しているのは、まさにこの一群です。

なぜ「書き換え先」が Rust なのか

近年、既存のソフトウェアを Rust で書き直したという話をよく見かけます。ただし、動いているものを丸ごと書き直せる現場はほとんどありません。実際に起きているのは重い部分・危ない部分だけの差し替えです。すると、書き換え先に選ばれる条件は「速いかどうか」より前に、既存のプロセスの中に混ぜられるかどうかになります。

ここで STEP 2 の「ランタイムを持たない」が効いてきます。Rust は GC も専用のランタイムも持ち込まないので、C から呼ばれる関数と同じ顔で既存のプログラムに同居できます。GC を持つ言語を差し込もうとすると、GC が 2 つ・スレッド管理が 2 つ同じプロセスに同居することになり、部分置換の相手として選びにくくなります。

実際に差し替えが進んでいるのは、この条件に当てはまる場所です。

  • Python の足回り — ruff（linter・formatter）、uv（パッケージ管理）、Polars（データフレーム）、tokenizers。いずれも本体は Rust で、PyO3 経由で Python から呼ばれる
  • 土台側 — Firecracker（AWS の microVM）、Linux カーネルのドライバ、Android や Windows の一部コンポーネント

では「AI 時代の大規模最適化だから選ばれている」のでしょうか。半分は当たっています。同じ処理を何万回も回す使い方が普通になり、実行時間が台数と電力にそのまま乗るようになりました。1 台あたりのコア数も増えたので、並列化しなければ性能が出ません。Rust はこの 2 つに対して、GC の停止がないことと、データ競合がコンパイル時に消えることで噛み合います。需要と供給が同時に揃った、という説明が正確です。

ただし誇張は禁物です。AI の計算そのものが Rust になったわけではありません。GPU 上で動く計算の本体はいまも C++ と CUDA で書かれており、Rust が取っているのはその周りの CPU 側の配管——データの読み込み・前処理・トークナイズ・スケジューリング・API サーバといった部分です。ここは「Python で書くと遅いが、C++ で書くと保守できない」という隙間で、Rust が最も選ばれやすい場所でもあります。なお「AI がコードを書く量が増えるほど、コンパイラが機械的に誤りを弾ける言語が有利になる」という議論もありますが、こちらはまだ効果が測られた話ではありません。

確認問題（考察） あなたが担当しているものの中で、Rust に置き換えて割に合うのはどれでしょうか。置き換えないほうがよいものは、なぜそうでしょうか。

答えを見る

判断の軸は 2 つです。1 つはメモリ安全性の問題が実際に被害になるか。攻撃者が入力を送れる場所で長時間動き続けるもの（ネットワークを受けるデーモン、パーサ、暗号や署名を扱う処理）は割に合いやすい領域です。もう 1 つは停止時間やランタイムの制約があるか。組み込み・カーネルモジュール・WebAssembly など、GC を持ち込めない場所では選択肢がそもそも限られます。

逆に、使い捨てのスクリプト、データ分析、社内の管理ツールのように、落ちてもやり直せばよく既存のエコシステムが充実しているものは、前払いのコストに見合わないことが多くなります。言語を選ぶ判断は「安全かどうか」ではなく、前払いする価値があるかどうかです。

まとめ：そのまま使える説明テンプレート

30 秒版

Rust は、メモリの解放タイミングをコンパイル時に確定させる言語です。ヒープ上の値には持ち主がちょうど 1 人いて、持ち主がスコープを抜けたところで自動的に解放されます。読むだけの参照は何本でも作れますが、書き換えられる参照は同時に 1 本だけ。この規則のおかげで、解放済み領域の参照や二重解放がコンパイルを通らなくなります。ガベージコレクタが要らないので実行時の停止もなく、OS・組み込み・WebAssembly のようにランタイムを置けない場所でも使えます。

2 分版（30 秒版に足す分）

背景には、ヒープのメモリを「誰がいつ返すか」という古い問題があります。これまでの答えは 2 つで、人間が書く（C / C++：速いが漏れる・壊れる）か、実行中に GC が判断する（Java / Go：安全だが実行時のコストと土台が要る）でした。Rust は 3 つ目の答えとして、コンパイラがビルド時に決めます。代償は、コンパイラが判定できる書き方しか許されないことです。

同じ規則がデータ競合も止めます。「読んでいる最中に誰も書き換えられない」は、そのまま複数スレッドでの安全性になるからです。さらに null がなく、値が無いかもしれないことは Option、失敗するかもしれないことは Result という型で表されるので、未処理のケースがあるとビルドが通りません。Rust の学習コストとは、これまで本番で気づいていた問題をビルド時に気づくようにした分の前払いです。攻撃者の入力を受けて長く動き続けるものや、停止時間・ランタイムの制約がある領域では、この前払いが最も割に合います。他の言語からの書き換え先に選ばれやすいのも同じ理由で、GC もランタイムも持ち込まないため、既存のプロセスに重い部分だけを差し込めるからです。

よくある誤解

「所有権は Rust が発明した新しい概念だ」

「誰がこのメモリを解放するか」は、C や C++ でも常に決めていたことです。違いは、それがコメントと設計ドキュメントと開発者の頭の中にしかなかった点です。Rust はそれを型として書かせ、コンパイラに検査させただけで、考えること自体は増えていません。むしろ、これまで暗黙だったものが明示されるので、他人のコードを読むときには楽になります。

「Rust なら安全なので落ちない」

落ちます。配列の範囲外アクセスや unwrap の失敗はパニックになりますし、これは意図された動作です（不正なメモリアクセスを起こすくらいなら止める、という設計）。ロジックの誤り・整数オーバーフローによる計算違い・設定ミスも防げません。Rust が構造的に消しているのはメモリ安全性の問題とデータ競合であって、バグ一般ではありません。

「Python や Go は Rust に置き換わる」

置き換わっていません。Rust 製の道具が増えているのは事実ですが、ruff や uv を使う人が書いているのはいまも Python です。Rust は Python の上ではなく下に入っています。Go とも用途はあまり重なりません。GC の停止を許せるネットワークサービスなら、Go のほうが短い時間で書けて運用もしやすく、そこを Rust にすると所有権の前払いだけ払って見返りが小さくなります。「どちらが優れているか」ではなく、GC を許せる場所かどうかが分かれ目です。

「unsafe を使うと安全性の保証が消える」

unsafe ブロックの中でできるようになるのは、生ポインタの参照外しなどコンパイラが検証できない操作に限られます。借用チェッカが止まるわけでも、型検査が無効になるわけでもありません。ハードウェアや他言語のライブラリを触る以上こうした操作は必要で、意味があるのはそれが数行に囲い込まれ、検索できることです。問題が起きたときに疑う場所が限定されます。

次の一歩

この記事では「Rust が何を解決した言語なのかを説明できること」を優先し、次の話には意図的に踏み込みませんでした。

  • ライフタイム注釈（<'a>）を自分で書く場面
  • トレイトとジェネリクス — Rust での抽象化の作り方
  • Rc / RefCell / Arc — 持ち主を 1 人に決められない構造をどう書くか
  • unsafe と FFI — C のライブラリを呼ぶ、C から呼ばれる
  • 非同期処理（async / await）とランタイムの選択
  • clippy / rustfmt / cargo audit といった周辺ツール

手を動かすなら、The Rust Programming Language 日本語版の 4 章（所有権を理解する）だけ先に読み、rustlings で短い演習を埋めていくのが近道です。いきなりアプリを書き始めると、借用チェッカのエラーの意味が分からないまま手が止まります。
