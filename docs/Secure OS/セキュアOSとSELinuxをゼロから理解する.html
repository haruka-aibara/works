セキュア OS と SELinux をゼロから理解する

root を取られた「その先」を止めるための仕組み。

root を取られたら、止めるものがない

Web サーバが乗っ取られたとする。プロセスは apache ユーザで動いているので、まずはそのユーザで読めるファイルが漏れる。そこからカーネルや setuid バイナリの脆弱性で root に昇格されると、あとは止まらない。/etc/shadow も SSH の秘密鍵も業務データも、全部読める。

なぜ止まらないのか。Linux の通常のパーミッションは任意アクセス制御（DAC: Discretionary Access Control）と呼ばれる。「任意」とは、アクセス権を決めるのがファイルの所有者だという意味だ。所有者は自分のファイルを誰にでも開放できるし、root は DAC のチェックをほぼ素通りする。権限が「誰が実行しているか」だけで決まり、しかも最強のユーザが1人いる。だから侵入が root に届いた瞬間、被害はシステム全体に広がる。

（rwx の読み方そのものは Linux/04-01 ファイルパーミッション にある）

ポリシで縛る — 強制アクセス制御（MAC）

強制アクセス制御（MAC: Mandatory Access Control）は、アクセスの可否をシステム側のポリシで固定する方式だ。所有者は変えられず、root も例外にならない。「この Web サーバのプロセスは /var/www 以下を読むだけ」とポリシにあれば、root 権限を得ても /etc/shadow に手が届かない。

この MAC を備えた OS がセキュア OSである。設計の柱は2つ。

  • 最小権限の原則 — プロセスやユーザに与えるのは、その仕事に必要な権限だけ。「とりあえず root で動かす」をやめる。
  • 管理者権限（root）の分割 — 万能の root を廃し、ポリシを書く人・ユーザを管理する人・監査ログを見る人に分ける。1アカウントの侵害で全部を持っていかれない。

なおTrusted OSは、こうした機能が TCSEC（オレンジブック）などの評価基準を満たすと認められた製品を指す呼び方。セキュア OS はその考え方を一般化した言い方で、対立する概念ではない。

SELinux の中核 — Type Enforcement（TE）

Linux で MAC を実装したのが SELinux。その中心が Type Enforcement（TE）だ。

SELinux はすべてのプロセスとファイルにラベルを貼る。プロセス側のラベルをドメイン、ファイルなど資源側のラベルをタイプと呼ぶ（実体は同じラベルで、どちら側かの違い）。ポリシには「このドメインはこのタイプに何をしてよいか」を allow ルールで列挙する。

効いているのは書いていない組み合わせは拒否というホワイトリスト方式であること。禁止事項を数え上げる必要がないので、想定していなかった攻撃経路もまとめて塞がる。

ロールを挟む — SELinux の RBAC

ドメインをユーザに直接ひもづけると、ユーザが増えるたびに割り当てが膨らんで管理できなくなる。そこで SELinux は間にロールを挟む。ユーザには就けるロールを、ロールには入れるドメインを定義しておき、ユーザは許されたロールを介してしかドメインに移れない。

一般ユーザは管理系のドメインに入れず、そこに紐づくタイプにも触れない。「ロールを切り替えないと管理作業ができない」という形で、前述の権限分割が実装されている。

動作モード

SELinux には enforcing（ポリシ違反を実際に拒否する）、permissive（拒否せずログだけ残す）、disabled（無効）の3モードがある。permissive はポリシを詰めている最中の調査用で、本番の狙いは enforcing。

止まったから無効化する、をやらない

アプリが動かないときに disabled にするのが最も多い運用事故。まず permissive にして拒否ログを集め、必要な許可だけを足すのが本来の手順。提案するときは「侵害されたときに被害が全社に広がるか一台で止まるかが変わる」と言うと、無効化の是非を判断してもらいやすい。
