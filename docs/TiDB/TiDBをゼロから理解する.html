TiDB をゼロから理解する

「MySQL 1 台では書き込みが受け止めきれなくなった」という手前の話から始め、5 ステップで TiDB の使いどころまでたどり着きます。

この記事の目的

TiDB の解説記事を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「TiDB は MySQL 互換の分散 NewSQL で、Raft によるレプリケーションと HTAP を備えます」という、中級者向けの前提から始まるからです。その一語一語が、どの面倒を消すために出てきたのかが分からないまま、構成図のコンポーネント名だけが増えていきます。

そこでこの記事は、あえて遠回りします。「データベース 1 台の限界」という、いちばん手前の話から始めて 5 ステップで進みます。ゴールはコンポーネント名を暗記することではなく、TiDB がどの手間をなくしたデータベースなのかを自分の言葉で説明できることです。

この記事の道のり

  1. STEP 1データベース 1 台の限界
  2. STEP 2自前で分割すると何が起きるか
  3. STEP 3小さく切って 3 つずつ持つ
  4. STEP 4SQL の層と保存の層を分ける
  5. STEP 5TiDB として組み立てる

STEP 4 まではすべて前提知識です。本題の TiDB は STEP 5 だけですが、そこに至る 4 ステップがないと「分散」「Raft」「MySQL 互換」がばらばらの特徴の暗記になります。

STEP 1：データベース 1 台の限界

  1. STEP 1データベース 1 台の限界
  2. STEP 2自前で分割すると何が起きるか
  3. STEP 3小さく切って 3 つずつ持つ
  4. STEP 4SQL の層と保存の層を分ける
  5. STEP 5TiDB として組み立てる

MySQL 1 台で動いている EC サイトがあります。会員が増え、注文テーブルは数十億行になりました。セールのたびに書き込みが詰まり、画面が固まります。

最初に打てる手は 2 つです。1 つはスケールアップ、つまりマシンを大きくすること。もう 1 つはリードレプリカ、つまり読み取り専用のコピーを増やして参照を逃がすことです。どちらもアプリをほとんど変えずに済むので、まずはこれで粘ります。

ところが、この 2 つには共通の天井があります。書き込みを受け付けるのは、結局 1 台だけということです。

確認問題 書き込み先が 1 台なのが問題なら、データを会員 ID で 4 つに分けて、4 台の MySQL に書けば解決するでしょうか。

答えを見る

書き込みの天井は上がります。代わりに別の仕事が大量に生まれます。 分けた瞬間から、どのデータがどの DB にあるかを誰かが管理しなければなりません。それを引き受けるのは多くの場合アプリです——これが次の話です。

STEP 2：自前で分割すると何が起きるか

  1. STEP 1 ✓データベース 1 台の限界
  2. STEP 2自前で分割すると何が起きるか
  3. STEP 3小さく切って 3 つずつ持つ
  4. STEP 4SQL の層と保存の層を分ける
  5. STEP 5TiDB として組み立てる

データを何かのキーで分けて複数の DB に置くことをシャーディングと呼びます。分けた 1 つ 1 つがシャードです。書き込みは台数ぶん分散するので、STEP 1 の天井は確かに上がります。

問題は、分けたことをアプリが知っていなければならない点です。「会員 ID が 1〜100 万ならシャード 1」という振り分けのコードを書き、すべてのクエリがそれを通るようにします。そして、1 台だったころは当たり前にできたことが、次々と難しくなります。

つまり欲しいのは、中では勝手に分かれていて、外からは 1 台の MySQL に見えるデータベースです。分けるのも、引っ越しも、またぐトランザクションも、データベース側がやってくれるもの。そのために必要な部品を、ここから 1 つずつ組み立てます。

確認問題 台数を増やしてデータを分けると、書き込み以外に新しく心配になることがあります。何でしょうか。

答えを見る

どこか 1 台が壊れる確率が上がることです。 1 台なら年に一度の故障でも、30 台あればどれかが頻繁に壊れます。分けたデータの一部が消えたり読めなくなったりしては困るので、「分ける」と同時に「複製して持つ」仕組みが要ります。これが次のステップです。

STEP 3：小さく切って 3 つずつ持つ

  1. STEP 1 ✓データベース 1 台の限界
  2. STEP 2 ✓自前で分割すると何が起きるか
  3. STEP 3小さく切って 3 つずつ持つ
  4. STEP 4SQL の層と保存の層を分ける
  5. STEP 5TiDB として組み立てる

STEP 2 の「会員 ID で 3 つ」は、人が決めた大きな分け方でした。これを逆にします。データ全体をキーの順に並べ、一定の大きさごとに自動で細かく切るのです。TiDB ではこの 1 切れを Region と呼びます。Region が大きくなれば自動で 2 つに割れ、偏れば別のマシンへ自動で移ります。人が分け方を設計する必要はありません。

そして各 Region を、別々のマシンに 3 つずつ置きます。これが STEP 2 の確認問題への答えです。1 台が壊れても、残りの 2 か所にデータがあります。

3 つのコピーの中身が食い違わないように、TiDB は Raft という合意の手順を使います。Region ごとに 1 つをリーダーとし、書き込みは必ずリーダーが受けます。リーダーは残り 2 つに内容を送り、自分を含めて過半数（3 つ中 2 つ）が書き終えたら確定とします。

この「Region に切って、Raft で 3 つずつ持つ」保存の仕組みが TiKV です。中身は、キーと値の組を保存する分散ストア（キーバリューストア）です。

確認問題 TiKV が扱うのはキーと値の組だけです。では、アプリが送ってくる SELECT ... JOIN ... WHERE ... は誰が解釈するのでしょうか。

答えを見る

まだ誰もいません。 保存の仕組みはできましたが、SQL を受け取って「どのキーを読めばいいか」に翻訳する役がいない状態です。しかもその役は、Region がどのマシンにあるかを知っていなければなりません。この 2 つの役を足すのが次のステップです。

STEP 4：SQL の層と保存の層を分ける

  1. STEP 1 ✓データベース 1 台の限界
  2. STEP 2 ✓自前で分割すると何が起きるか
  3. STEP 3 ✓小さく切って 3 つずつ持つ
  4. STEP 4SQL の層と保存の層を分ける
  5. STEP 5TiDB として組み立てる

MySQL 1 台の中では、「SQL を解釈する部分」と「データを保存する部分」が同じプロセスにいました。TiDB はこれを別々のサーバーに分けます。

  • TiDB サーバー：アプリから MySQL の通信手順で SQL を受け取り、実行計画を立て、TiKV に「このキー範囲を読め・書け」と指示する。データを持たないので、何台並べても、どれに繋いでも同じ結果が返る
  • PD（Placement Driver）：どの Region がどのマシンにあり、どれがリーダーかを管理する地図係。Region の分割・移動の指示もここが出す

最後の難題が、STEP 2 で諦めた複数の場所をまたぐトランザクションです。「在庫を減らす（Region A）」と「注文を作る（Region D）」を、両方成功か両方失敗かのどちらかにしたい。TiDB は 2 段階で確定させます。

1 PD から開始時刻の番号をもらう。読むのは「この番号の時点で確定していたデータ」だけにする
2 書き込む全キーに仮の値とロックを置く（1 つでも他のトランザクションとぶつかれば全部やめる）
3 PD から確定時刻の番号をもらい、代表の 1 キーを確定させる。この瞬間に全体が確定したことになる

時刻の番号を PD の 1 か所で発行するのが要点です。マシンごとの時計のずれに関係なく、全トランザクションの前後関係が一列に決まります。アプリから見れば、いつもの BEGIN … COMMIT のままです。

確認問題 TiDB サーバーを 3 台並べたとき、アプリはどれに接続すればよいでしょうか。

答えを見る

どれでもかまいません。 TiDB サーバーはデータを持たないので、どこに繋いでも同じ TiKV を見ています。前にロードバランサーを置いて振り分けるのが普通の構成です。1 台が落ちても接続し直すだけで済み、STEP 2 の「どの ID はどのシャードか」をアプリが知る必要はありません。

STEP 5：TiDB として組み立てる

  1. STEP 1 ✓データベース 1 台の限界
  2. STEP 2 ✓自前で分割すると何が起きるか
  3. STEP 3 ✓小さく切って 3 つずつ持つ
  4. STEP 4 ✓SQL の層と保存の層を分ける
  5. STEP 5TiDB として組み立てる

ここまでを重ねると TiDB の姿になります。データを自動で細かく切って 3 つずつ持ち（STEP 3）、SQL の層と保存の層を別々に増やせて、またぐトランザクションもそのまま書ける（STEP 4）。そのうえで外からは MySQL 互換、つまり MySQL のドライバ・クライアント・多くの ORM がそのまま繋がるデータベースです。PingCAP 社が開発するオープンソースで、自前で運用するほか、マネージドの TiDB Cloud も提供されています。

もう 1 つ特徴があります。STEP 3・4 の TiKV は行単位の読み書きが得意な行指向です。そこへ列指向のコピーを持つ TiFlash を足せます。TiFlash は Raft の仕組みで TiKV から変更を受け取り続けるので、ほぼ最新のデータに対して集計クエリを投げられます。どちらを読むかは TiDB サーバーがクエリごとに選びます。

アプリから見た使い方は MySQL とほぼ同じです。既定のポートは 4000 番です。

mysql -h tidb.example.internal -P 4000 -u app -p

-- 大きな集計テーブルに列指向のコピーを 2 つ作る
ALTER TABLE orders SET TIFLASH REPLICA 2;

では、同じ悩みに対する他の選択肢と比べて、なぜ TiDB なのか。判断の軸は書き込みの天井を誰が上げるかです。

選択肢書き込みの天井アプリ側の負担向く場面
MySQL・Aurora MySQL（1 台 + レプリカ）書き込み 1 台で頭打ちなし書き込みが 1 台に収まるうちは、こちらのほうが素直で安い
アプリ側シャーディング／Vitess台数ぶん上がる分け方の設計・またぐ処理の工夫が要る分け方が自然に決まる（テナント単位など）システム
TiDBTiKV を足せば上がるほぼなし（MySQL 互換）1 台に収まらず、分け方も決めにくい。集計も同じ DB でしたい

表の 1 行目が示すとおり、1 台で足りるなら TiDB を選ぶ理由は薄いです。最小でも TiDB・TiKV・PD の複数台構成になり、1 件の書き込みにもマシン間の往復が挟まるので、小さな規模では MySQL 1 台より遅く高くつきます。

「MySQL 互換」は「MySQL と同じ」ではない。 ストアドプロシージャやトリガーなど一部の機能は使えず、AUTO_INCREMENT の値も連番になる保証がありません。移行するなら、アプリが使っている機能を互換性の一覧と突き合わせてからにします。

確認問題 注文 ID を 1, 2, 3 … と連番で振っているテーブルに、書き込みが殺到しました。TiKV を増やしても速くなりません。なぜでしょうか。

答えを見る

新しい行がすべて「いちばん後ろの Region」に入るからです。 STEP 3 のとおり Region はキーの順に切られているので、連番の新規行は常に末尾の 1 Region に集中し、そのリーダー 1 台が STEP 1 と同じ天井になります。TiDB には、ID の上位ビットをばらけさせて Region を散らす AUTO_RANDOM という列属性が用意されています。

まとめ：そのまま使える説明テンプレート

30 秒版

TiDB は、外からは MySQL に見える分散データベースです。MySQL は書き込みを受け付けるのが 1 台だけなので、そこが天井になります。自前でシャーディングすれば天井は上がりますが、分け方の管理やまたぐ処理をアプリが背負います。TiDB はデータを自動で細かく切って複数台に 3 つずつ持ち、分割も引っ越しもまたぐトランザクションもデータベース側でやります。アプリは MySQL のドライバで繋ぐだけです。

2 分版（30 秒版に足す分）

中身は 3 種類のサーバーでできています。SQL を受け取る TiDB サーバーはデータを持たないので、何台でも並べられます。データを持つ TiKV は、キーの範囲で切った Region という単位を、Raft という手順で 3 台に複製します。3 つ中 2 つが書けたら確定なので、1 台壊れてもデータは消えず、止まりもしません。どの Region がどこにあるかと、トランザクションの時刻の番号は PD が管理します。

さらに列指向のコピーを持つ TiFlash を足すと、業務の読み書きと集計を同じデータベースでこなせます。

ただし、1 台の MySQL で足りる規模なら、構成が重いぶん遅く高くつきます。MySQL 互換も完全ではなく、ストアドプロシージャなど使えない機能があります。選ぶのは、書き込みが 1 台に収まらず、分け方も自分で決めにくいときです。

よくある誤解

「MySQL 互換だから、差し替えればそのまま速くなる」

接続の手順と SQL の大部分が同じ、という意味です。小さなデータでは MySQL 1 台より遅いことも普通にあります。速くなるのは、1 台では受け止めきれない量を扱うときです。

「分散データベースは一貫性を犠牲にしている」

TiDB は Raft で過半数に書けたものだけを確定とし、トランザクションも PD の時刻で順序を決めます。確定した書き込みが後から消えたり、読む場所によって古い値が見えたりはしない設計です。

「台数を増やせば、どんな負荷も分散される」

分散されるのは Region 単位です。連番キーへの書き込みのように 1 つの Region に集中する負荷は、台数を増やしても散りません（STEP 5 の確認問題）。

  • MySQL からの移行ツール（DM）と、変更を外へ流す TiCDC
