# NCO 注意喚起（2026-11-05）不正アクセス対策のチェックリスト

内閣官房国家サイバー統括室「個人情報の漏えい等につながる不正アクセスへの対策について〜ウェブサイトやモバイルアプリに関する基本的な対策の徹底〜」（事業者向け、2026 年 11 月 5 日）を、担当者向けのチェックリストに直したもの。

原文：https://www.cyber.go.jp/pdf/press/261105_taiou.pdf

## 背景（原文の柱書）

最近の漏えい事案で、原因とみられる事例が複数確認されたもの：

- モバイルアプリを開発するときのセキュリティ対策不足
- ウェブサイトなどの設定不備
- サポートが終わったソフトや、既知の脆弱性を放置したソフトを使い続けていたこと
- 自組織や委託先の基本的な対策が足りなかったこと

攻撃者は日本のウェブサイトなどを標的に大規模な調査を行い、侵入できた所から個人情報を盗んだとみられる。
調査や侵害に AI を使っている可能性も高い。

従来の診断で「比較的低い」と評価されたリスクでも、組み合わされて侵入の原因になった可能性のある事例がある。
攻撃を大規模に行いやすくなったため、事業規模に関係なく狙われる。

本文は経営層を含む全員向けの柱書と、担当者向けの「対策例」の箱でできている。
以下は対策例を 1 項目ずつチェックにしたもの。

## 1. 運用・管理段階

### (1) デジタル資産の把握と脆弱性の解消

- [ ] OS・ミドルウェア・フレームワーク・ライブラリの製品名、バージョン、使用箇所を管理している（必要に応じて SBOM / SCA）
- [ ] SBOM を作って終わりにせず、脆弱性情報との照合、影響範囲の特定、修正や緩和までを一続きの運用にしている
- [ ] CISA KEV に載っているものなど、悪用が確認された脆弱性から優先して影響を確認している
- [ ] ベンダー、NVD、JVN の脆弱性情報と悪用動向を集め続け、構成情報と照合している（必要に応じて脆弱性管理ツールで自動化）
- [ ] 対応の優先順位と期限を決める評価基準（深刻度、実際の悪用状況、ネット経由で悪用できるか、システムの重要度、事業への影響）を事前に決めている（参考：SSVC）
- [ ] インターネットからアクセスできるサーバーやネットワーク機器を優先して対処している
- [ ] パッチをすぐ当てられないときは、ベンダーのアドバイザリを確認したうえで機能停止・アクセス制限などの暫定策を取っている
- [ ] パッチや緩和策が効いていることを確認し、恒久対処が終わるまで残りのリスクを管理している
- [ ] 悪用が確認された脆弱性に該当していたら、関連するログで侵害の兆候も調べている

### (2) アタックサーフェスの棚卸しと最小化

原文で挙がっている実例は、公開された管理画面への推測しやすい認証情報の悪用・総当たり・認証回避と、デバッグ用機能やシステム管理用エンドポイントの露出。

- [ ] ネットワーク構成、クラウドの設定、資産台帳から、公開している IP・FQDN・サービス・ポート・アプリ・API を洗い出している
- [ ] ASM で外から見える資産を探して内部の管理情報と突き合わせ、管理から漏れた資産を見つけている
- [ ] 見つけた資産ごとに、管理責任者・用途・公開の必要性を確認している
- [ ] 管理画面・デバッグ用エンドポイント・開発/検証環境・DB 管理機能について、外から届くか、公開が必要かを点検した
- [ ] リバースプロキシ・LB・API ゲートウェイの振り分け（URL パス・ホスト名）、ルールの優先順位、想定外のパスへの既定の転送・応答を確認し、公開すべきでない機能に届かないことを検証した
- [ ] 不要な機能は止め、管理上必要な機能はアクセス元制限と MFA を組み合わせて守っている
- [ ] クラウドストレージのアクセス・外部共有、FW などの不要な通信許可、Web サーバーの意図しないファイル公開を点検した
- [ ] 直したあと、外からアクセスして公開が消えたことを確かめた
- [ ] 新設・変更のたびに露出が増える前提で、公開状況を継続して点検し、台帳や過去の結果と比べて変化を拾っている

### (3) AI の活用などによる継続的な診断と監視

- [ ] 公開前だけでなく、認証・認可・API・個人情報の扱いに関わる重要な変更時と運用開始後も、リスクに応じて診断・点検・監査し、直した結果まで確認している
- [ ] Web アプリ・API・ネットワーク機器・クラウド環境に定期的な脆弱性診断やペネトレーションテストをしている
- [ ] AI を使った診断ツール（攻撃経路の探索、テストケース生成、検証、影響分析、優先度付け）の活用を検討している。AI の結果は根拠を確かめ、最終判断は人がする
- [ ] Web サーバー・API ゲートウェイ・認証基盤・クラウドのログを取り、SOC / SIEM で不審な認証、権限の不正使用、大量のデータ取得を監視している
- [ ] EDR などで端末・サーバーの不審なプロセスや通信を監視している
- [ ] AI を使った監視・運用（大量のログやアラートの横断分析、事象の関連付け、調査の優先順位付け）の活用を検討している
- [ ] 侵害の兆候を見つけたとき、ログやシステムの状態をすぐ調べて、不正アクセスの有無と影響範囲を確認できる体制がある
- [ ] SOAR による手順の自動化や、AI によるアラート要約・情報収集・対応手順の提案を検討している。誤検知や業務影響を考え、検証と人の監督のもとで使う

## 2. 設計・開発段階

### (1) セキュリティ・バイ・デザイン

- [ ] 要件定義・設計で脅威モデリングを行い、認証・認可、暗号化、ログ取得、アクセス制御を要件に入れている
- [ ] 管理機能や運用機能を不用意にネットへ出さないネットワーク構成と、ゼロトラストを踏まえたアクセス制御を設計段階から考えている
- [ ] アプリ・DB・運用管理機能を、ネットワーク上で分けるだけでなく、重要度とリスクに応じてクラウドのアカウントやサブスクリプションでも分けることを検討している
- [ ] 非機能要件（認証・認可、可用性、ログ、監視、障害対応、バックアップ、データ保護）を体系的に決め、要件定義・設計・調達・開発・検収・運用の各段階で確認する項目を決めている
- [ ] 実装時に SAST・SCA で危険な関数、セキュアコーディング違反、OSS の既知脆弱性を拾っている
- [ ] テスト時に DAST・IAST で認可不備・入力値検証不備・セッション管理不備を確認し、自動で拾えないものは手動でも検証して、リリース前に直している
- [ ] 必要に応じて、これらのテストを CI/CD に組み込んでいる

### (2) API のセキュリティ

背景は NICT が注意喚起している「A2B（App-to-Backend）攻撃」。
公開アプリを解析して API エンドポイントの脆弱性や認可不備を見つけ、バックエンドから情報を盗む。
バックエンド API に求められているのは、認証・認可、厳格な入力値検証、認証情報の安全な管理、異常アクセスの検知と制御。

- [ ] リクエストされた機能とデータへの権限を、サーバー側で毎回確認している（BOLA / BFLA、最小権限）
- [ ] API キー・アクセストークン・秘密鍵・DB 接続情報を、ソースコードやアプリのパッケージに埋め込んでいない
- [ ] サーバー側の認証情報はシークレットマネージャーなどで管理している
- [ ] 認証情報の権限を最小にし、有効期限の設定と定期的なローテーションをしている
- [ ] コミット時や CI/CD でシークレットスキャンをしている
- [ ] 認証やパスワードリセットなどの機能にレート制限をかけている
- [ ] 同じ IP・同じアカウントだけでなく、複数 IP からのアクセスも含めて、認証の成否やアクセス頻度から異常を検知できる

### (3) 公開前の脆弱性診断

原文に実例として挙がっている攻撃は、SQL インジェクション、OS コマンドインジェクション、RCE、SSRF、ディレクトリトラバーサル。

- [ ] 個人情報を扱う Web アプリは、リリース前に脆弱性診断やペネトレーションテストをし、直したことを確認してから本番に出している
- [ ] 診断の目的と対象範囲を決めている。対象システムの特性とリスクで範囲を決めている（参考：OWASP ASVS）
- [ ] 製品やプラットフォームの既知の脆弱性だけでなく、自社や委託先が作ったバックエンドの設計・実装に固有の脆弱性も対象にしている
- [ ] 受け入れられるリスクの水準を決め、それを超える脆弱性が残っていたら本番に出さない（セキュリティゲート）
- [ ] 診断結果ごとに修正の責任者と期限を決め、修正漏れを防ぐ仕組みがある
- [ ] 診断を外部に頼むなら、Web アプリ・API・モバイルアプリ診断の実績、手法、体制を確認し、情報セキュリティサービス基準に適合した事業者（情報セキュリティサービス台帳）から選んでいる
- [ ] 自動診断だけでなく、手動の検証や業務ロジックを考えた診断までしてくれるかを確認している

## 3. サプライチェーンを通じた侵害

### (1) 委託先の統制と接続経路

委託先のリモート接続は、攻撃者にとって「正規の認証情報で入れる入口」になり得る。
その場合でも、サービス停止や漏えいの影響を負うのは発注元。
個人情報の扱いを委託するなら、個人情報保護法 25 条で委託先の監督も求められる。

委託先に対策を求めるときは、費用負担や実施方法を十分に話し合い、取引上の立場を使った一方的な押し付けにならないよう留意する、とも書かれている。

- [ ] 委託先が使う VPN・リモートデスクトップ・保守回線を洗い出し、重要度の高い経路から計画的に MFA へ切り替えている
- [ ] MFA が難しい経路は、接続元 IP の制限、作業時だけの接続開放、作業記録の取得で代替している
- [ ] 作業が終わった委託先のアカウントや、付けっぱなしの管理者権限を棚卸しし、無効化・最小化している
- [ ] 発注仕様書や委託契約に、秘密保持に加えて、再委託の手続き、インシデント時の通知義務と連絡先、契約終了時のデータ消去を入れている
- [ ] 委託先を選ぶとき、第三者認証や SCS 評価制度（2027 年 3 月に申請受付開始予定）などの客観的な評価を使っている
- [ ] 境界型 VPN だけに頼らず、委託先の作業員ごとに、認可した端末から必要なサーバー・機能だけへ通信を絞っている

### (2) OSS と外部ライブラリの管理

深刻な脆弱性が公表されると、攻撃者による探索・悪用が短期間で始まることがある。

- [ ] 開発・保守を委託している主要システムに組み込まれた OSS のバージョンと EOL を、平時から把握している
- [ ] ゼロデイや深刻な脆弱性が出たとき、保守事業者任せにせず、すぐ判断できる手順を決めている
- [ ] NVD・JVN をもとに、委託先と連携して自社システムへの影響をすぐ照合できる
- [ ] 影響調査の責任者、委託先との役割分担、経営層への報告基準を決めている
- [ ] パッチ適用、WAF での防御、該当機能の停止などの暫定策を判断する手順を決めている
- [ ] 開発・改修を委託するとき、使うソフト部品の明示と SBOM の提出を契約や仕様に入れている
- [ ] 検収時に、SBOM と設計書を突き合わせ、既知の脆弱性とライセンス違反がないかを確認している
- [ ] 納品後も SCA ツールなどで新しい脆弱性の公表を見張る体制がある

## 結び（原文）

上の対策は今回の一連の手口に絞ったもの。
VPN などネットに出たネットワーク機器の脆弱性、標的型メール、DDoS、AI の悪用による高度化も想定しておく必要がある。

経営トップの判断のもと、システムの特徴と保有情報に基づいてリスク評価をし、そのうえで対策を強化する。
