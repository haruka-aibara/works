セッション管理と入力の扱いをゼロから理解する

HTTP が「前回を覚えていない」ところから始めて、5 ステップで Web アプリの守り方までたどり着きます。

この記事の目的

Web アプリのセキュリティの解説を読んで、途中で分からなくなった経験はありませんか。

それは読解力の問題ではありません。多くの記事は「セッション ID を再発行する」「プリペアドステートメントを使う」という対策の一覧から始まります。この説明が成立するのは、セッション・Cookie・SQL の組み立て方がすでに体に入っている人だけです。名前だけを並べられると、覚えることはできても、なぜそれで防げるのかは分かりません。そして分かっていないと、少し形の違う場面で応用できません。

そこでこの記事は、あえて遠回りします。「HTTP はリクエストのたびに相手を忘れる」というところから始めて、5 ステップで進みます。ゴールは対策の名前を覚えることではなく、「何を・どこで・なぜ」で言い切れるようになることです。

この記事の道のり

  1. STEP 1HTTP は覚えていない
  2. STEP 2番号札を奪う 2 つの型
  3. STEP 3値が命令になる
  4. STEP 4使う場所で守る
  5. STEP 5抜けたときの備え

Web アプリの守りは、突き詰めると ログイン状態をどう持つか（セッション管理）と外から来た値をどこでどう扱うか（入力の扱い）の 2 本しかありません。STEP 1〜2 が前者、STEP 3〜4 が後者、STEP 5 は両方に効く保険の層です。

STEP 1：HTTP は前回を覚えていない

  1. STEP 1HTTP は覚えていない
  2. STEP 2番号札を奪う 2 つの型
  3. STEP 3値が命令になる
  4. STEP 4使う場所で守る
  5. STEP 5抜けたときの備え

銀行の窓口で本人確認を済ませた直後に、もう一度話しかけたら、また一から本人確認をやり直される。HTTP はそういうプロトコルです。リクエストは 1 本ずつ独立していて、サーバは前回の相手を覚えていません。これをステートレスと呼びます。

このままだと、ページを開くたびにパスワードを送ることになります。危険ですし、使い物になりません。そこでサーバは、認証に成功した時点で 番号札を 1 枚発行します。これがセッション ID です。

番号札の運び方が Cookie です。サーバが Set-Cookie で渡すと、ブラウザは以降そのサイトへのリクエストに自動で付けてくれます。利用者は何もしません。

ここから重要な帰結が出ます。セッション ID はパスワードと同じ重みを持つということです。攻撃者はパスワードを知らなくても、有効な ID を 1 つ手に入れれば本人として振る舞えます。

だから ID の作り方に要件が出ます。連番や「ユーザ ID ＋ 時刻」から組み立てた ID が危険なのは、他人の値を計算で作れてしまうからです。暗号論的な擬似乱数で十分な長さを取ること、そして自作せずフレームワークの実装を使うこと。この 2 つです。

確認問題 自分のセッション ID が漏れたことに気づきました。パスワードを変更すれば安全でしょうか。

答えを見る

それだけでは安全になりません。

サーバは「番号札が有効かどうか」しか見ていません。パスワードを変えても、サーバ側でそのセッションを破棄しない限り、漏れた ID はそのまま通ります。

同じ理由で、ログアウト処理が「ブラウザの Cookie を消すだけ」の実装は不十分です。手元の札を捨てても、サーバ側の表に残っていれば、盗まれた札はまだ生きています。破棄はサーバ側で行う必要があります。

STEP 2：番号札を奪う 2 つの型

  1. STEP 1 ✓HTTP は覚えていない
  2. STEP 2番号札を奪う 2 つの型
  3. STEP 3値が命令になる
  4. STEP 4使う場所で守る
  5. STEP 5抜けたときの備え

セッション ID が本人性そのものなら、攻撃者の目的は 1 つに絞られます。有効な ID を 1 枚手に入れること。やり方は大きく 2 通りあります。

  • 知る（セッションハイジャック）：被害者が使っている ID を盗み見る
  • 使わせる（セッションフィクセーション）：自分が用意した ID を、被害者にログインさせる

2 つ目が分かりにくいので、時間軸を並べて比べます。

言い切る形にするとこうなります。何を：セッション ID を新規発行して古い ID を破棄する。どこで：認証に成功した直後。なぜ：攻撃者が事前に用意・固定した ID が、認証済みの状態と結びつかないようにするため。

それでも破られる条件：再発行はフィクセーション専用の対策です。ログイン後に新しい ID が盗聴や XSS で漏れれば、ハイジャックは普通に成立します。

2 つの型は、成立条件がまったく違う

セッションハイジャックセッションフィクセーション
攻撃者に必要なこと被害者の ID を知る（盗聴・XSS・Referer やログからの漏えい）知る必要はない。自分の ID を使わせるだけ
アプリ側の欠陥ID が漏れる経路がある／ID が推測できるログイン前後で ID を変えていない
効く対策推測不能な ID、Secure、HttpOnly、TLS 全面化ログイン成功時の ID 再発行

確認問題 Cookie の属性（Secure や HttpOnly）をすべて正しく付けました。これでセッションフィクセーションも防げるでしょうか。

答えを見る

防げません。

フィクセーションでは、ID はどこからも漏れていません。攻撃者は最初から知っている ID を使わせているだけです。Cookie の属性は「漏らさない」ための道具なので、漏れが関係しないこの攻撃には効きません。

逆も同じで、ID を再発行してもハイジャックは防げません（ログイン後の新しい ID が漏れれば成立するため）。2 つの対策は交換できません。両方要ります。

STEP 3：値が「命令」になってしまう

  1. STEP 1 ✓HTTP は覚えていない
  2. STEP 2 ✓番号札を奪う 2 つの型
  3. STEP 3値が命令になる
  4. STEP 4使う場所で守る
  5. STEP 5抜けたときの備え

ここからが 2 本目の柱、入力の扱いです。

まず、なぜ「入力」が危ないのか。危険な文字を渡されることが問題なのではありません。値として渡したはずのものが、命令の一部として解釈されることが問題です。

なぜそんなことが起きるのか。アプリは受け取った値を文字列に混ぜて、別のシステムへ渡します。データベースへの SQL、ブラウザへの HTML、OS へのコマンド。渡された側が受け取るのは 1 本の文字列で、どこまでが値でどこからが命令かは、区切り記号だけで判断されます。だから値の中に区切り記号を紛れ込ませられると、境界がずれます。

確認問題 それなら、値を受け取った入口で ' や < をまとめて潰しておけば、3 つとも一度に防げるのではないでしょうか。

考えた結果を確認する

防げません。理由は 3 つあります。

1. 入口の時点では、その値がどこへ行くのか決まっていない。同じ値が SQL にも HTML にもシェルにも流れうるのに、潰すべき文字は行き先ごとに違います。

2. 正当な入力が壊れる。名前に ' が入る人はいますし、本文に < を書きたい場面もあります。潰してしまうとアプリが使えなくなります。

3. 経路が 1 つでも漏れれば終わり。入口を全部押さえたつもりでも、バッチ処理や他システム連携で入ってくるデータは入口を通りません。

ではどこで処理すべきか。それが次のステップです。

STEP 4：防御は「値を使う場所」でやる

  1. STEP 1 ✓HTTP は覚えていない
  2. STEP 2 ✓番号札を奪う 2 つの型
  3. STEP 3 ✓値が命令になる
  4. STEP 4使う場所で守る
  5. STEP 5抜けたときの備え

原則はこれ 1 行です。

入口でまとめて無害化せず、値を使う場所で、その場所の作法で処理する。

入力時の検証がいらないという意味ではありません。ただしそれは「型・長さ・書式が仕様どおりか」を確かめるものであって、防御の本体ではないという位置づけです。

SQL に渡すとき：静的プレースホルダ

SQL の場合、そもそも値を文字列に混ぜないで済ませる手段があります。骨格だけを先に DB へ送って構文解析を終わらせ、値はあとから別枠で渡す方式です。

# 文字列連結 — 値がそのまま SQL の一部になる
cur.execute("SELECT * FROM users WHERE name = '" + name + "'")

# 静的プレースホルダ — 骨格と値を別々に渡す
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

バインド機構は、値を SQL 文字列に埋め込まず別枠で渡す仕組み全般を指します。プリペアドステートメントは、その SQL をあらかじめ DB に準備させておく形です。準備の段階でパースが終わるので、値は後から差し込むしかなくなります。

どこで値を差し込むか安全性の根拠と、残る穴
静的プレースホルダDB サーバ側。? 付きの SQL を先に送り、構文解析を済ませてから値を送る構文が確定した後に値が届くので、原理的に値は構文になれない
動的プレースホルダドライバやライブラリ側。内部でエスケープして 1 本の SQL を組み立て、DB へ送る最終的に文字列連結をしているのは同じ。文字エンコーディングの扱いを誤ると引用符を作れる組合せが残り、実装依存の穴になる

どちらにも共通して破られる条件：プレースホルダはテーブル名・カラム名・ORDER BY の並び順には使えません。ここだけ連結で書いた実装が実際によく残ります。可変にしたいなら、外部入力を SQL に混ぜるのではなく許可リストから選ばせる形にします。

HTML に出すとき：文脈ごとのエスケープ

HTML には、SQL のような「骨格と値を分けて渡す」仕組みがありません。だから値を埋め込む直前に、記号を「タグの開始として読まれない形」へ置き換えます。これがエスケープです。

やっかいなのは、埋め込む場所ごとに必要な処理が変わることです。1 種類のエスケープを全部に使い回すと穴が残ります。

埋め込む場所必要な処理（なぜ）破られる条件
HTML の本文< > & " ' を文字参照へ。タグの開始として読まれなくなるこの処理だけを全文脈に使い回すこと
属性値必ず引用符で囲んだうえでエスケープ。囲まないと空白で属性を継ぎ足せる引用符なしの <img src=…> に onerror= を足される
<script> 内HTML エスケープでは不十分。JS の文字列リテラルに値を直書きせず、JSON として渡す文字列を閉じずともテンプレートリテラルやコメントで脱出されうる
href / srcエスケープでは足りない。スキームを http / https の許可リストで確認するjavascript: は文字としては無害なので、エスケープを素通りする

確認問題 テンプレートエンジンの HTML エスケープを、すべての出力に漏れなくかけました。これで XSS は防げるでしょうか。

答えを見る

場所によっては防げません。

いちばん分かりやすいのがリンクです。<a href="ユーザ入力"> に javascript:alert(1) を入れられた場合、この文字列には HTML エスケープの対象になる文字が 1 つも含まれていません。エスケープは何も変えずに素通りし、クリックするとスクリプトが動きます。

ここではエスケープではなく「スキームが http / https か」の確認が必要です。文脈ごとに必要な処理が違うというのが、この STEP の核心です。

  2. STEP 2 ✓番号札を奪う 2 つの型

ここまでが対策の本体です。その上で、どこか 1 か所抜ける前提で被害を狭める層を重ねます。

Cookie の属性 — 1 つずつ塞ぐ穴が違う

セッション ID を運ぶ Cookie には属性を付けられます。「まとめて付けておくもの」ではなく、1 つずつ役割が違います。属性そのものの構文は別記事にあるので、ここは防御の観点で並べます。

属性何を防ぐのか（なぜ）それでも破られる条件
SecureHTTPS のリクエストにしか Cookie を載せない。平文で流れないので、経路上の盗聴で ID を拾われないHSTS がないと最初の 1 回が HTTP になりうる。TLS を張る前の段階で剥がされれば意味がない
HttpOnlyJavaScript の document.cookie から読めなくする。XSS が起きても ID を外部サーバへ送り出せないXSS 自体は止まらない。スクリプトは被害者のブラウザ内で、Cookie が自動付与された状態のまま送金や設定変更を実行できる
SameSite他サイト起点のリクエストに Cookie を付けない。攻撃者のページから勝手に投げられたリクエストが認証済み扱いにならない（CSRF）Lax はトップレベルの GET には付くので、GET で状態を変える実装は守られない。同一サイト内の別サブドメインからは付く
Domain送信先ドメインを絞る。無関係なホストへ ID が飛ばない指定するとサブドメイン全体に送られる。脆弱なサブドメインが 1 つあれば、そこから ID を回収できる。狭くしたいなら指定しないほうが狭い

有効期限
（Expires / Max-Age）		指定しなければブラウザを閉じた時点で消えるセッション Cookie になり、共用端末に残らない消えるのはブラウザ側だけ。サーバのセッションが生きていれば、盗まれた ID はまだ使える。ログアウトはサーバ側の破棄で行う

CSP — スクリプトが動く範囲を狭める

CSP（Content Security Policy）は、そのページで実行してよいスクリプトの出どころをブラウザに宣言する仕組みです。インラインスクリプトを禁じておけば、XSS で <script> を差し込まれても実行されません。ただし既存アプリへの後付けは重く（インラインを全部外す必要がある）、あくまで多層防御の 1 枚です。

WAF — どこに置くか

WAF はリクエストを検査して遮断する仕組みで、判定方式が 2 つあります。

  • ポジティブモデル（許可リスト）：通してよい形だけを定義し、それ以外を落とす。精度は高いが、アプリの全パラメータの仕様を書き出し、改修のたびに追随する必要がある。運用が重い
  • ネガティブモデル（シグネチャ）：既知の攻撃パターンに一致したものを落とす。導入が容易で実際に多いが、知らない形は通る

根本的な限界は、WAF が見ているのがリクエストの見た目だけで、その値がアプリ内でどう使われるかを知らないことです。エンコードやコメントを混ぜた変形で回避されますし、HTTP を通らずに入るデータ（外部連携ファイル、他システム経由のレコード）は素通りします。誤検知を嫌って緩めれば、緩めた分だけ穴が開きます。

WAF を提案するときの言い方

「WAF は脆弱性を直すものではなく、直すまでの時間を買うもの。改修に何か月かかるかと、その間どう検知するかがセットで決まっていないなら、入れても止まりません」

確認問題 WAF を入れれば、見つかった脆弱性の改修は後回しにできるでしょうか。

答えを見る

できません。

WAF が見ているのはリクエストの見た目だけで、その値がアプリの中でどう使われるかを知りません。エンコードやコメントを混ぜた変形で回避されますし、HTTP を通らずに入るデータ（バッチ処理、他システム連携）は検査そのものを通りません。

使いどころは「改修が終わるまでの時間を買う」ことです。改修の期限とセットで初めて意味を持つ道具であって、単独の対策にはなりません。

30 秒版

Web アプリの守りは 2 本柱です。1 つはセッション管理。HTTP は前回の相手を覚えていないので、認証後に発行するセッション ID が本人性そのものになります。だから ID は推測できない値にして、漏らさず、ログイン成功時に必ず作り直します。

もう 1 つは入力の扱い。攻撃の本質は「値として渡したはずのものが、命令として解釈されること」です。だから防御は入口で危険文字を潰すのではなく、値を使う場所で、その場所の作法で処理します。SQL なら静的プレースホルダ、HTML なら埋め込み先の文脈に応じたエスケープです。

2 分版（30 秒版に足す分）

セッションへの攻撃には型が 2 つあり、成立条件が違います。ハイジャックは ID を知る攻撃なので、推測不能な ID・Secure・HttpOnly・TLS 全面化が効きます。フィクセーションは ID を使わせる攻撃で、ID は漏れていないため属性では防げず、ログイン時の再発行だけが効きます。2 つの対策は交換できません。

入口でまとめて無害化できないのは、入口の時点では値の行き先が決まっていないからです。同じ値が SQL にも HTML にも流れうるのに、必要な処理は行き先ごとに違います。入力時の検証は「型・長さ・書式が仕様どおりか」の確認であって、防御の本体ではありません。

Cookie の属性・CSP・WAF は、本体が 1 か所抜けたときに被害を狭める層です。特に WAF は脆弱性を直すものではなく、直すまでの時間を買うものとして位置づけます。

「何を・どこで・なぜ」で言い切る

何をどこでなぜ
セッション ID を再発行する認証に成功した直後攻撃者が事前に固定した ID が、認証済み状態と結びつかないようにするため
セッションを破棄するサーバ側のログアウト処理Cookie を消しても、サーバ側に残っていれば盗まれた ID がまだ使えるため
HttpOnly を付けるCookie を発行する Set-CookieXSS が起きても、スクリプトからセッション ID を読み出せないようにするため
静的プレースホルダを使うSQL を組み立てるアプリ側構文を先に確定させ、入力値が構文として解釈されないようにするため

よくある誤解

「危険な文字を潰す」で考えない

この発想でいる限り、行き先が増えるたびに文字の一覧を作り直すことになり、いつか漏れます。考えるべきは文字ではなく構造です。値と命令が同じ文字列に同居しているなら危なく、分けて渡せるなら安全。SQL で静的プレースホルダが強いのは、この構造そのものを変えているからです。

HttpOnly を付けても、XSS は止まっていない

止まるのは「セッション ID を外部へ持ち出すこと」だけです。スクリプトは被害者のブラウザの中で動いていて、Cookie はそのブラウザが送るリクエストに自動で付きます。ID を読み出せなくても、その場で送金や設定変更のリクエストを投げることはできます。HttpOnly は被害を狭める保険であって、XSS の対策ではありません。

ログアウトは「Cookie を消すこと」ではない

手元の番号札を捨てても、サーバ側の表に「8f3d… は田中さん」と残っていれば、その札はまだ有効です。共用端末やセッション ID が漏れた場面で効くのは、サーバ側でセッションを破棄することだけです。
