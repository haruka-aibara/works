# 検知が本当に鳴るかを攻撃シミュレーションで定期的に確かめる

検知ルールと通知経路は、いつの間にか壊れる。
EventBridge のパターンの typo、Lambda のランタイム切れ、Slack の Webhook の失効。
本物の攻撃が来て初めて気づく、では遅い。

Stratus Red Team（Datadog の OSS）で、攻撃の手口を sandbox アカウントで実際に起こす。
`stratus detonate aws.defense-evasion.cloudtrail-stop` のように1手口ずつ実行し、`cleanup` で片付ける。
鳴るべき通知が鳴ったかを確かめれば、検知の回帰テストになる。

## GuardDuty のサンプル検出結果との違い

`create-sample-findings` は偽の検出結果を作るだけなので、通知経路のテストにしかならない。
Stratus は本物の API を叩くので、「その手口を検知できるか」まで確かめられる。
Config のカスタムルールや自前の CloudTrail 検知も対象にできる。

## 気をつけること

- 本番アカウントでは実行しない。CloudTrail の停止など、片付け損ねると穴が開く手口がある
- 鳴らなかった手口が、そのまま「検知の死角リスト」になる。[GuardDuty の死角](../docs/Amazon%20Web%20Services/04_セキュリティ/検知と可視化/GuardDutyの死角.md) の裏取りに使える
